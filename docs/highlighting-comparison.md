# Comparing terminal syntax highlighting

The checkout-only comparison framework compares emitted terminal cell styles, not palette JSON, browser CSS, parser category names or standalone lexer output. The same neutral source/diff inputs feed application-specific saved-session adapters. A difference is an observation, not automatically a product defect or a requirement to match another application.

## Maintained and generated inputs

- `scripts/highlight-compare/` contains the comparison core and separate reference/application adapters. Register sources in `adapters/index.mjs`; the CLI and collector share that registry and load application code only inside the guarded capture process. Adding a reference source adds its adapter and one registration, not application-name branches to source alignment or a rewrite of existing fixtures.
- `tests/fixtures/highlight-compare/` contains ordinary source files, logical before/after text pairs, feature ranges and provenance. These inputs, framework code and regression tests belong in Git.
- `tests/harness/highlight-compare/` contains independently constructed regression controls for the framework.
- The canonical comparison chapter is included in the published manual, but the generator, fixtures and regression harness are checkout-only and are not npm runtime payloads.
- Generated native sessions, grammar caches, ANSI streams, terminal cell grids, source/role maps and comparison reports are disposable output. They do **not** belong in tracked files or as generated colored-reference fixtures. Collection requires an explicit output destination; retain a run's inputs/identities there when reproducing that run.

The first reference adapter targets OpenCode 1.19.5 TUI. The product adapter targets pi-tidy-ui through an explicitly prepared Pi/Node graph and same-source Occipital helper. Neither reference collection nor fixture parsing executes the example Python code or asks a model to run tools. Completed synthetic `write` and `edit` records exercise saved-session display, not live tool execution or streaming.

## Running a source comparison

Prepare a coherent Pi/Node graph and a same-source Occipital helper using the [testing procedure](testing.md#requirements-and-commands). The following checkout commands consume that descriptor; they do not install dependencies, discover a user helper or execute the Python examples. Real capture currently requires Linux with the documented verified memory/process scope and network-namespace tools. The comparison CLI enters that scope itself; do not nest it inside a second ordinary guard.

Each output path must be fresh and outside tracked source locations. Reference preparation may acquire declared parser assets; subsequent collection and comparison run without public network access. The pinned OpenCode executable is a separate explicit prerequisite, not part of Pi dependency preparation.

```sh
INPUTS=/absolute/path/to/prepared-pi/inputs.json
RESULTS=/absolute/path/to/new-comparison-output

node scripts/highlight-compare/run.mjs prepare --inputs "$INPUTS" \
  --adapter opencode --binary /absolute/path/to/opencode \
  --theme github --variant dark --output "$RESULTS/reference-inputs"

node scripts/highlight-compare/run.mjs collect --inputs "$INPUTS" \
  --adapter opencode --binary /absolute/path/to/opencode \
  --prepared "$RESULTS/reference-inputs/prepared.json" \
  --fixture python-core --theme github --variant dark --columns 180 --rows 150 \
  --output "$RESULTS/opencode"

node scripts/highlight-compare/run.mjs collect --inputs "$INPUTS" \
  --adapter pi-tidy-ui --fixture python-core --theme github --variant dark \
  --columns 180 --rows 150 --output "$RESULTS/pi-tidy-ui"

node scripts/highlight-compare/run.mjs compare --inputs "$INPUTS" \
  --left "$RESULTS/opencode/capture.json" --right "$RESULTS/pi-tidy-ui/capture.json" \
  --output "$RESULTS/comparison"
```

Read `comparison.md` for feature/channel observations and `comparison.json` for complete native style projections. Each capture retains `fixture.json`, original terminal output, pages, maps, readiness and source/runtime identities. Existing output is never overwritten. A failed capture retains its diagnostic evidence but produces no accepted `capture.json`.

## Current execution boundary

The common CLI accepts normalized source and structural diff captures and dispatches comparison by the neutral fixture kind, not the application name. Diff captures retain `diff-map.json`, exact canonical patch rows, per-side source observations and structural surfaces; readable comparisons list each observed color channel and keep geometry separate. An adapter's unresolved readiness still prevents `capture.json`, even with complete physical maps. OpenCode diff collection requires a complete, unwrapped plain-text card, an unambiguous observed unified/split view and repeated completed structural frames with a discriminating theme witness. Unsupported or incomplete captures remain unresolved; pure normalizer tests do **not** establish native integration acceptance. A short one-sided deletion can satisfy both numbered unified and split interpretations under the current observer. That capture remains unresolved rather than selecting the first candidate or treating nominal terminal width as native-view proof. Reference preparation requires an explicit family/variant and binds the selected raw native family assets in its descriptor. The additional language specimens define input coverage only. Native source/diff collection has been validated for Python and neutral text diffs at GitHub Dark; additional fixtures do not establish native capture support for other languages or coverage of other themes.

## Fixture contract

The [fixture provenance](../tests/fixtures/highlight-compare/README.md) documents independently authored, inert language specimens and language-independent diff pairs, including their official versioned references and source-license notices. The manifest names stable fixture/case IDs, target language versions, exact inclusive line ranges and feature lists. Diff witnesses identify original old/new coordinates and structural roles, not expected colors. Shared preparation derives neutral logical rows and a standard three-context-line patch; only application adapters encode saved-tool metadata. The existing patch library from the selected SDK graph validates exact whole-file before/after reconstruction, including unchanged margins outside the displayed hunks. Both raw normalization and persisted comparison re-derive the canonical logical rows from that reconstructing patch and reject missing, extra or altered hunk rows. Diff coverage refers to every declared hunk row and structural witness, not every unchanged line in both full files. The three-row context matches Pi's normal full-card context limit without disguising native omissions as neutral text. Pi's numbered context records use old-file coordinates, even after a net insertion/removal; the native presenter derives the displayed new-file number.

Language fixtures remain intact parse contexts, not full conformance suites. The bounded regression checks exercise selected JSON, YAML 1.2 Core, Markdown dialect-token (including CommonMark inline links/images/code spans/indented code and GFM bare-URL autolinks), JavaScript syntax, TypeScript syntax and CSS parser witnesses; they do not execute fixture source, test runtime behavior, or prove complete language conformance. Files must fit the product's full-source eligibility; a preview or missing viewport is not plain/neutral highlighting. Python 3.14 positive specimens remain parser inputs only. The root TypeScript project excludes this fixture-data directory, retaining its strict runtime/test compiler options; the separate parser checks accept full TypeScript syntax, including non-erasable declarations. The OpenCode source adapter still accepts only `.py`; adding fixture data does not expand native collection or replace the initial one-theme Python/diff acceptance.

## Source coordinates and styles

A physical page retains its detached characters, cell widths, literal foreground/background representations and font attributes. Source maps use exact logical-line UTF-16 ranges; persisted observations use UTF-8 offsets into the original file. Newline bytes remain part of file identity but have no emitted character style. Whole graphemes, actual tabs, CRLF, wide-cell continuations, soft-wrapped ranges and agreement of overlapping pages are checked explicitly. Missing, conflicting or ambiguous positions fail coverage rather than being assigned plausible colors. An adapter may supply an application-specific `sourceMap` (one range array per page and the native tab size/mode); otherwise the shared numbered-gutter mapper is used. The same independent normalizer verifies text, grapheme boundaries and complete coverage in either case. Sources without numbered gutters therefore need only their own adapter's map, not changes to the comparison core.

RGB, indexed and terminal-default colors are distinct. The framework does not guess a default RGB or treat dim/indexed output as a universally defined perceived color. Bold, dim, italic, underline, strike and inverse remain visible observations. The Pi adapter uses four-column tab stops; the pinned OpenTUI code buffer uses a fixed two-column expansion, including inline tabs at odd columns. These are distinct projection modes, not different source bytes. Uniform tab expansions with different native widths retain their geometry separately but are not counted as syntax-style differences. Nonuniform cell styles within a projected tab remain observable; JSON object-key order and font-set ordering do not change a style. A font-only distinction is still a distinction; equal RGB does not prove equal parser classification.

## Structural diff evidence

The opt-in shared numbered-diff mapper separates producer gutter metrics from common role/coverage validation. It supports one-column left/right padding and an optional after-number sign field whose glyph occupies its last column. Pi reserves two sign columns and shares its coordinate-based digit width across panes. Pinned OpenTUI instead sizes each pane's decimal field from the greater of its native virtual row count and displayed file coordinates, and reserves two sign columns only when that pane has added/removed rows. Under the complete-unwrapped-row contract, unified virtual rows equal canonical diff rows. OpenCode split row counts use the original patch's native grouping: context rows plus the greater of removed/added counts in each block, with both context and no-final-newline markers ending a changed block. A marker adds no visible row, but an old-EOF marker between removals and additions prevents those two populations from being paired. The adapter reuses the selected SDK's standard patch parser so this boundary is not lost when neutral logical rows omit marker text. Empty and context-only panes therefore need not share the opposite pane's gutter width. The native [gutter calculation](https://github.com/anomalyco/opentui/blob/0c8c4f7cff2927e3df63a9757a45eff9a343611c/packages/core/src/renderables/LineNumberRenderable.ts) is adapter-specific, not inferred from matching background colors. Native word wrapping is not disabled: a wrapped, clipped or incomplete row fails the full-body and trailing-padding checks instead of being treated as an accepted unwrapped capture.

Diff maps identify the whole visible decimal label, not a matching digit substring: adjacent gutter cells cannot extend its decimal run, without imposing an application's gutter syntax on the shared code. Each persisted line-number and changed-row sign cell must agree with its owning gutter cell at the same physical page, row and column in text, width and canonical style signature. Every retained physical page has its own card-background observation inside the native horizontal interval `[bar, cardRight)`; an anchor must be visible and must not overlap mapped diff roles or alignment padding. Equal uniform card-background profiles may use different sampled lengths across pages; nonuniform profiles must agree exactly and real color changes remain visible. Every full body observation has one page-local source range covering exactly `[0, row.text.length)` at the actual first body column, and the displayed body is the full unwrapped projection. Each source-mapped visible row on each page has exactly one body, gutter, trailing-padding and line-number observation, plus its changed-row sign on that same physical page and row; trailing padding occupies at least one column. Coverage cannot be assembled from different pages. The relaxed length comparison applies only to uniform card-background profiles: source/body foreground, font and other overlapping-paint evidence retain their existing equality checks. Split old/new panes occupy disjoint physical intervals, without requiring a left/right ordering; side tags alone do not establish two panes. For each mapped opposite-side row on every page, an unmatched alignment row retains the complete owning pane, partitioned into contiguous gutter and content ranges without omitted columns. These constraints apply both when normalizing physical pages and when reading persisted comparison inputs. Virtual per-side source offsets in a diff are accompanied by canonical logical-row and original old/new line coordinates; they are not offsets into the complete before/after files.

## Readiness and interpretation

Pi capture uses the existing native frame receipts and producer-owned `whenSettled()` boundary, then observes the current full-card paint through a synchronous `CardSources.visit()` / `ReadyCardPaint.basis()` borrow. The borrowed source must match the fixture's bytes, be complete and currently classified, and belong to the compiled owned-palette group for the effective family, variant and terminal color mode. A neutral fallback, preview, stale source, refused borrow or historical palette is not successful highlighting. Request-time `cardPreparation.outcomes` remain ordered diagnostic history: an initial `waiting` or `neutral` receipt can legitimately survive a successful native publication. Those receipts and aggregate counters do not certify the final paint. Native style byte ranges may contain neutral gaps; successful canonical complete-source and compiled-paint borrows establish completion, while the independent physical source map checks every displayed grapheme. Geometry or color polling does not substitute for producer completion.

For native plain-text Edit cards, the Pi adapter also borrows the exact prepared row descriptors and current compiled structural roles. It decodes those complete ANSI role prefixes with the same xterm implementation used for capture, then checks the screen's structural backgrounds and number/sign foregrounds against that producer paint. The sign's preceding space belongs to the sign style; empty split-side alignment rows use the empty role. Native gutter/text populations establish the observed unified/split view; nominal terminal width alone is not the view identity. Empty changed content retains one physical background witness disjoint from horizontal trailing padding. The second original-size capture after a real width round-trip must expose the same complete canonical rows and structural paint. These checks do not claim syntax-parser readiness for a plain-text diff.

OpenCode preparation acquires its runtime parser assets explicitly; collection copies and verifies those declared size/hash inputs and runs without network access. Preparation also copies the requested native family's raw JSON, the native `opencode` fallback, their pinned metadata and MIT notice from the selected source graph into the prepared output. Collection verifies contained paths, sizes, hashes, source commit/version and requested family before launch; either variant can use the same raw family asset. These are original native assets, not generated pi-tidy-ui palettes. The existing pure native-color resolver interprets their values without invoking product palette generation. Both use private HOME/test-home/XDG/config and a neutral temporary workspace with no foreign `.opencode` ancestor. This matters because native theme discovery walks working-directory ancestors independently of its project-config switch. The initial protocol is bound to the verified 1.19.5 executable and OpenTUI 0.4.5 sources, not an arbitrary future binary. Mutable asset URLs make the recorded runtime hashes important: regenerating output later does not establish byte-identical historical inputs unless those exact inputs are still available.

A fresh private native `tui.json` selects the requested built-in family, disables mouse selection and selects stacked diffs for source capture or native automatic diff layout for structural capture; the observed panes, not terminal width alone, determine the retained view. KV pins Dark/Light, detailed tools and a hidden sidebar. Imported user/assistant metadata selects the pinned executable's locally available `opencode/big-pickle` pair; it does not invoke that model. An invented model ID would produce an unrelated native warning toast. Core `opencode debug config` is not TUI-theme evidence. The native application's own `applying tui config` records must identify only the declared TUI file, whose bytes and retained KV values are checked. Unknown native family IDs are rejected rather than silently accepting OpenCode's default fallback.

For the native completed Write branch, diagnostics metadata and native detail visibility create one nonstreaming CodeRenderable. The pinned KV/Theme providers mount children only after their ready gates; explicit family and mode lock prevent provisional startup theme or unlocked terminal-mode selection. No mouse/selection/dialog/theme gestures or refresh signals are sent. Initial/no-highlight/failure `setText` paths have uniform foreground/font. Only full-source `highlightOnce` completion publishes the styled chunks for this renderable. Consequently a completed native synchronized frame with multiple fg/font tuples among **exactly mapped source characters** witnesses whole-buffer styled publication. Its positive completed-frame index must accompany an explicitly closed current synchronized frame: an older completed-frame count cannot certify a partial new render. Header/gutter colors, background-only differences, arbitrary RGB, quiet time and stable frames do not supply that witness. Preliminary frames remain in raw output but are excluded from normalized source pages. Subsequent page overlap and a forced repeated original-size frame must agree exactly. This is not a claim that a renderable can publish only once in its lifetime. Missing frame markers, source coverage or style distinction leave collection unresolved. The common collector refuses an adapter's non-ready result even when its physical text coverage is otherwise exact; it retains the unresolved readiness and pages, but writes no accepted capture.

For a native OpenCode `.txt` Edit, each retained frame must independently expose the complete canonical hunk and all structural surfaces. A real width round-trip produces a distinct later completed frame; exact overlap checks retain paint changes as failures rather than accepting a convenient intermediate frame. Native direct body/gutter backgrounds, number foreground and sign foregrounds provide structural evidence, not syntax-parser readiness. At least one structurally attributed opaque RGB value per page must identify the requested family/variant against the opposite variant and the native fallback alternatives. A requested `opencode` family is not subtracted from itself. Card padding binds to `backgroundPanel`; sign foregrounds bind to `diffHighlightAdded`/`diffHighlightRemoved`. All compatible structural keys and every mismatching observation are retained; not every emitted color must match its expected native palette value. Authored numeric ANSI theme values resolve through native RGBA semantics and can witness actual RGB cells, but actual indexed/default cells cannot. Transparent colors are not guessed or composited into identity witnesses; absent discriminating evidence leaves readiness unresolved.

Reports describe observed source positions, colors/fonts and separate structural diff surfaces. Source reports count foreground, background and font differences independently, both globally and for the manifest's declared feature ranges. Counts may overlap and are not quality scores; a different whole-card background must not conceal a smaller foreground- or font-only distinction. Exact changed positions retain both native style projections and the changed channels. Reports do not infer that a construct was unrecognized merely because its text has the ordinary foreground; that conclusion requires separate parser/renderer evidence. Raw terminal output and maps remain the audit trail. The framework does not alter the product's parser, palette mapping or painter to obtain a convenient reference.


Every successful `compare` run also writes `comparison.ansi` beside the exact JSON and Markdown reports. It is a bounded, side-by-side terminal excerpt rendered only from the validated comparison report's captured source projections or diff gutter/body/padding/alignment/card cells; it does not invoke another highlighter, infer styles from a palette, or replace the full JSON/raw-page audit trail. Source excerpts preserve source-byte order independently of serialized span order, prioritize a representative captured line from each declared feature range and report omitted lines; long lines and diff samples reflow within fixed pane and row limits without splitting wide cells. RGB, indexed and terminal-default colors plus all captured font attributes are emitted literally, with resets between cells and panes; terminal-default remains terminal-default rather than an assumed RGB value. Captured cell text containing C0, DEL or C1 controls is rejected at this ANSI output boundary so serialized header/card cells cannot inject terminal commands.
