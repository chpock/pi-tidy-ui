# Occipital syntax highlighting: implementation plan

## 1. Status, decisions and scope

This is the implementation plan for the accepted architecture. The operator has now authorized implementation in this directory on `main`, without a worktree; deployment/publication and commits still require separate authorization. Source baseline: `2acc114`. The operator has answered the architectural and user-facing questions A1–A4, including the control menu, standard daemon configuration directories and missing-theme fallback. Engineering details below make those decisions implementable; G0 prototype feasibility evidence is recorded in `.test-artifacts/occipital-implementation/g0.md`, while the gate sections below define the completed G0–G5 acceptance. The maintained [specification](syntax-highlighting-spec.md) records the implemented contract; run evidence and independent findings remain under ignored `.test-artifacts/`. Stop if those gates reveal a blocker or require a new architectural, scope or user-visible decision rather than silently changing the contract. Planning evidence and the historical decision journal are in `.test-artifacts/syntax-highlighting-plan/`; historical proposals there are not additional requirements.

**Validation scope:** protocol correctness, memory accounting and shutdown/recovery of this local highlighting integration. Invalid, oversized, deeply nested or premature messages are controlled fixture cases generated by our own test processes. Runtime experiments use isolated temporary configuration and an explicitly created test Subconscious runtime, not external systems or the user's live services.

### Operator-approved decisions

- The highlighting daemon is named **`occipital`**; the extension is named **`pi-tidy-ui`**. The naming decision originally deferred package/command/documentation changes; that separately authorized refactor is now complete, using `/tidy-ui` and the `TidyUi`/`tidyUi`/`TIDY_UI` namespaces. It does not rename the daemon or change its release lifecycle.
- **General extension settings store accepted:** persist the selected syntax-theme preference across launches in **`<agent-dir>/extensions/pi-tidy-ui/config.json`**, using a reusable extension-level settings reader/writer for future preferences rather than a theme-specific file. The initial persisted preference is the theme only; persisted enablement and additional fields are not approved. Connection/provider choice, initial shared availability, retries, leases and source/parser state stay in memory. The daemon's catalogue/configuration is separate and does not belong in this Pi extension settings file.
- **Control menu:** provide one Pi menu for theme selection/listing, explicit theme refresh, service status and session-local highlighting on/off. All supported user controls are reachable from that menu; no mandatory transport selector, updater or extra permanent UI row.
- **Standard daemon configuration:** keep `occipital` configuration and custom themes under the current user's OS-standard configuration root, resolved through a platform API, independently of Pi's agent directory and replaceable binary caches. The concrete directory contract is below.
- **Unavailable selected theme:** use the current Pi palette and report the error in Pi UI without erasing the saved preference. Distinguish the user's selected theme from the effective rendering profile; no implicit copying/uploading of definitions.
- **Enabled by default:** native syntax highlighting is active when `pi-tidy-ui` is enabled; no separate activation command is required. Provider discovery/acquisition/startup stays asynchronous and does not block input or tool execution. Deliberate disabling is session-local, uses the accepted safe fallback policy, and is not saved in settings; only theme preference is initially persisted. Owned-binary selection follows the local/published version discriminator below; exact release acquisition applies to published packages.
- **Independent versions and releases:** `pi-tidy-ui` and `occipital` have separate release/version lifecycles. An extension-only change must not force a new daemon release, and a daemon release must not force an extension version bump. Protocol compatibility is negotiated independently of either product version.
- **Local versus published delivery accepted:** the extension's own package version selects the delivery contract: exactly `0.0.0` means local development; a real release version means the published package. Local development uses the `occipital` binary colocated with the extension. Native package versions are absent from the repository npm manifest/lockfile; publication selects the nearest `occipital-v*` tag and generates exact native dependencies and matching delivery metadata in the release package. Section 2.1 records the implemented boundary, settled history-based tag selection and verified delivery.
- **Published-package exact standalone version accepted:** a released `pi-tidy-ui` package declares one concrete compatible `occipital` release. If an owned helper is needed, use that exact platform/ABI artifact from trusted local storage or acquire it if missing. Do not select an arbitrary newer compatible cached release, query for latest releases, add a periodic update check or introduce a separate latest-version updater. A usable compatible shared provider needs no local download and remains user-managed; shared protocol compatibility does not require equality with the pinned standalone product version.
- Use **Syntect + two-face**. The complete native one-shot and growing-source capability must also work **without an installed Subconscious runtime**; Pi-core/plain-text fallback alone does not satisfy ordinary standalone operation.
- **A2 topology accepted: option 1.** Without Subconscious, the extension acquires the native binary if needed and owns one persistent stdin/stdout helper per Pi process. In a user-managed Subconscious deployment, clients share its managed highlighter module. **A4 automatic selection is accepted:** prefer a usable compatible shared `occipital` discovered through the supported Subconscious contract; otherwise acquire/start the owned stdio helper. No mandatory manual transport choice. Both modes use one Rust engine and application protocol. Cross-Pi sharing is not required in standalone mode; do not embed/install a private Subconscious router or build a custom shared endpoint. Do not change Pi/AFT.
- **Recovery and return accepted:** after actual shared-connection failure, try bounded reconnection, then use the owned helper; limited exceptional replay is allowed even if abandoned shared work may still be running. Remember in memory whether a usable shared `occipital` was available at initial client startup. If it was and failover was necessary, try to return once per minute for ten minutes; on a verified successful return, stop the owned helper and continue on the shared provider. No such periodic search is started when the client began without a usable shared provider. Details and handoff guards are below.
- **Daemon state is disposable at any time:** a live connection does not guarantee that source sessions still exist. Provider changes, daemon resets and expired/evicted/ended leases all use fresh session generations and the latest caller-owned full source when work is still needed; completed sources use one-shot. Never depend on restoring state from a completed-result server cache.
- The service is optional; retain the current **Pi-core highlighting path for edit/write file sources** as the fallback engine, with exact-result caching. **Bash fallback is its existing entire-command `toolTitle` coloring, not Pi syntax highlighting.** **Operator correction:** the existing synchronous Pi highlighter has no demonstrated responsiveness defect in ordinary use. Do not add millisecond budgets, cold/warm exceptions, language cost allowlists, adaptive cooldown or latency hedges based on one machine's microbenchmarks. Prevent duplicate/repeated work introduced by this integration instead. A1 still preserves full plain text for excessive inputs or output that cannot be retained safely; it does not justify refusing ordinary fallback based on estimated call duration. No additional Pi-core executor is introduced.
- Support finite one-shot sources and growing sources in the first design and first implementation.
- The daemon retains reusable state/results **only for unfinished sessions expecting further input**, with explicit memory and lifetime bounds. It must not cache completed classifications. Re-reading an evicted client result means resubmitting the supplied source, not fetching completed data from the daemon.
- The client starts one-shot/growing sessions and declares logical completion; the server may forcibly expire/evict them and require a restart from the latest full snapshot. Bash argument formation ending, not Bash execution ending, completes its source.
- Many simultaneous clients, many requests and large allocations are first-class constraints. Bound CPU work, memory and admission across clients from the start. There is no resource-constrained-machine requirement; measured protective limits must not be turned into artificially small operating budgets.
- **JSON selected for the current implementation:** no Base64/MessagePack carrier or SDK changes for binary replies now. Keep encoding/decoding at the transport boundary, separate from parser state, source lifecycle, scheduling and canonical classifications, so a future public Subconscious binary-response API can enable another codec without rewriting those components. Do not implement or advertise an unsupported binary format in advance.
- Adopt the scheduling policy in section 7: reuse useful results, coalesce updates and distinguish unavailable/no-start providers from queued, running or uncertain work. Use ordinary cached Pi fallback for file sources when appropriate; Bash keeps its existing `toolTitle` fallback. Waiting alone never launches another classifier within the same installed presentation/source owner. Actual-failure replay and complete presentation reinstallation are the separately accepted exceptions, not latency hedges. Protective plain text remains valid for exceptional resource failure; eventual coloring is not mandatory in that case.
- Separate logical parser source from terminal-cell projection, retaining tabs until after classification and using exact logical-source UTF-8 offsets. Preserve current glyph geometry and original args/results/session bytes.
- Support independent Syntect syntax themes: real probes established useful distinctions beyond Pi's nine syntax roles. Apply the selected theme in Rust and return structured styles rather than ANSI/full scope stacks; preserve pi-tidy-ui backgrounds and Pi's global UI theme. **The accepted default is the current Pi palette**: `occipital` still parses the source, while the client maps category results to Pi's syntax colors. Independent Syntect themes require explicit selection. **The theme catalogue is owned by `occipital`**: bundled and operator-configured `.tmTheme` definitions, with independent client selection by ID and no client definition uploads. User files live outside replaceable binary/npm caches. **An explicitly selected independent theme stays fixed when Pi's UI theme changes**; there is no automatic dark/light pairing or theme-name guessing. Pi-palette mode continues to follow Pi. **Theme files are refreshed explicitly**, without automatic watching/polling or a daemon restart. The menu and OS-standard daemon configuration locations are accepted; their implementation contract is below.
- Growing-source incrementality is **line-oriented**: previously completed lines are not reparsed; the unfinished final line may be reparsed from its saved start-of-line state. The operator explicitly accepted this Syntect limitation during planning.

### Accepted A2 topology and remaining delivery details

The daemon is delivered **as part of released `pi-tidy-ui` packages**, with automatic acquisition of their exact native payload when needed; local `0.0.0` development uses the colocated binary under section 2.1. The operator selected section 2.3 option 1: direct stdio ownership plus optional user-managed Subconscious. No embedded/private router is part of the selected design. The daemon's name is **`occipital`**; the layout below is the engineering baseline for repository organization, subject to the delivery gates. The separately authorized extension/package/documentation naming refactor is complete. Native package identifiers and advertised platforms must be verified at the delivery gates; untested targets are not advertised as supported.

No Rust compiler, missing native payload or unavailable provider may break extension loading, exact text or tool execution. Missing Subconscious alone must not cause permanent Pi-only operation on a supported standalone installation. Exceptional native acquisition/execution failures still use accepted A1 protection. No repository reorganization, package publication/installation or live daemon configuration is authorized by this discussion.

First pi-tidy-ui integration surfaces:

1. Saved edit/write diffs: each available continuous old/new source segment.
2. Numbered source in Created/Wrote write cards, using the supplied source already accepted by their contract.
3. Bash-card **command source**, including arguments appearing gradually. Do not classify arbitrary Bash stdout as shell source.

The classifier contract can accept other explicitly supplied, language-tagged code without knowing about cards. This is not permission to take over native Markdown, assistant prose, editor input, read-tool layout, expanded/native renderers or foreign extensions. Adding those surfaces needs its own source/ownership contract. Input styling, status/footer, tool execution, result bytes and session/model data are unchanged.

### Decision register — closed

All four decision groups are resolved. The final three answers select a menu, OS-standard daemon configuration and Pi-palette fallback with a Pi UI error. No architectural preference question remains open in this revision; implementation authorization and the evidence gates are separate.

**Automatic startup selection:** begin bounded asynchronous discovery at eligible client startup. A shared provider is usable only after authenticated connection, internal-service admission and a compatible `describe` response; installation or a connection file alone is insufficient. If none is usable, resolve/start the owned binary under the version-selected delivery contract: colocated development binary or exact declared published release, without a mandatory mode selector. Connection/discovery failures remain visible in service status and do not disable ordinary pi-tidy-ui. Startup probes never block Pi input or tool execution.

Public Rust Subconscious discovery exists, but the inspected Node SDK 0.21.1 still requires a connection-file argument and exports no equivalent discover helper. G0 must validate a supported bridge or narrowly implement/test the documented public candidate/ownership contract; no arbitrary filesystem/process/port scanning or claim that Node discovery already exists. Respect exclusive explicit/environment endpoint selection. A connection file is not a compatible active highlighter. Authentication/configuration errors are not silently relabeled as normal absence.

Startup selection and an in-flight failure remain different. The operator now explicitly permits bounded exceptional replay after actual connection failure, without claiming that remote CPU stopped. A slow/lost reply alone is still not permission to race expensive parsers. No per-render switching or permanent fleet polling; the finite return window below is the sole approved periodic recovery exception. When a selected theme is unavailable on the active provider, use the Pi-palette profile and notify Pi UI while keeping the saved choice, as specified below; never copy/upload daemon-owned definitions implicitly. Do not add speculative strict-mode/acquisition overrides as extra architecture questions. These decisions do not authorize implementation or pass the discovery/resource gates.

**Recovery after established shared-connection loss accepted:** on an actual channel/process failure, allow a bounded reconnect attempt; if it cannot restore a usable shared provider, acquire/start the owned stdio helper. Preserve valid retained results and protective presentation throughout. Resubmit only still-needed latest full source under a new provider/stream generation, never an uncertain old append or a transcript-wide replay. Coalesce updates and bound retries; late old-generation results cannot replace the new result. Do not kill/restart a shared module owned by Subconscious.

This availability-first failure recovery may repeat an expensive classification while abandoned remote work is still running: disconnect and best-effort cancellation do not prove CPU termination. The operator explicitly accepted this limited failure-recovery exception, not unconditional expensive hedging. A slow reply/timeout alone, including a timeout followed by locally closing the route, is not a reason to race expensive providers. Count recovery replay separately from normal incremental work and startup fallback-to-daemon upgrades; coalesce current demand and retain finite retry/resource bounds.

**Repeated owned-process crash recovery accepted:** after confirmed loss and actual close/reap of the owned process, allow at most **two consecutive automatic owned restarts** before a successful native classification. Only a fully validated source result for the current provider/source authority resets this counter; compatible `describe`, publication, raw RPC success, cached colors, closure/ack metadata and stale results do not. Valid native work may reset it even if local byte pressure cannot retain its colors. On the next crash after both restarts, close/reap the failed process and remain unavailable with safe Pi/plain-text presentation; a deliberate session off/on permits a fresh attempt. This protects against a repeatedly failing helper, not ordinary source size/count or normal requests. Keep this crash chain separate from immediate shared reconnects, source `restart_required`, and the operator-selected shared-return window. A timeout or uncertain result alone is never a confirmed crash.

**Return-to-shared window accepted:**

- Record initial shared availability only after a compatible, authenticated shared provider is actually usable at this client's startup, not from a path/PID or installed Subconscious alone. This is in-memory client-lifetime state, not a persisted user preference and not a flag reset by each source or failed probe.
- Once an initially shared client fails over to an active owned helper, start one recovery window: attempt shared reconnection at 60-second intervals for 600 seconds, nominally at minutes 1 through 10. These are operator-selected values, not calibration candidates. Initial immediate reconnect attempts are separate; failed periodic probes and source updates never restart or extend the window. A genuine later shared-to-local failure after successful return may start a new episode.
- At most one recovery probe is active. Each probe has a finite connection/authentication/catalogue/compatibility deadline; it does not replay source just to test health. Use one controller-owned, unreferenced timer, not one per source/stream. No overlapping or catch-up burst after delayed timers/sleep; missed slots are not replayed and the window is not extended. The tenth scheduled probe may finish within its own bounded deadline, with no further scheduled probe.
- Failed/unusable candidates leave the local helper serving normally. Mere transport reconnection is insufficient: validate a usable compatible highlighter before replacing the active provider. Keep exact text and reusable validated colors; new remote state starts from supplied snapshots, never from local lease/checkpoint IDs.
- On successful return, cancel the recovery timer, stop new dispatch to the owned helper, retire its source/transport generation and terminate/reap that owned process using bounded shutdown. Continue classification on the verified shared connection under fresh generations. No shared source parsing is raced against a still-running local parse: use the owned child's exit as the stop boundary before replacement work. Do not wait for or replay the whole transcript, and never terminate the shared module or peers.
- After the ten-minute window, remain standalone without further automatic shared probes. Initial standalone clients have zero periodic discovery attempts. Stop timers/candidates on success, off, reload, shutdown or owner disposal; late probe completions cannot resurrect a retired owner or switch after cancellation. A handoff that fails before shared readiness keeps the local owner; a failure after it was retired follows ordinary bounded recovery, not reuse of a dead child or old lease.

**General settings and theme persistence accepted:** use a reusable extension settings reader/writer at **`<agent-dir>/extensions/pi-tidy-ui/config.json`**. Initially persist only the selected theme preference (Pi palette versus an independent catalogue theme ID), not expanded theme definitions or provider-specific fingerprints. The extension can use the same store for future explicitly designed settings; this does not add them now. Restore the preference into each client's own state on startup. Saving one client's choice changes the default for future launches, not another already-running client's active theme; no settings watcher or cross-client broadcast is introduced. Do not persist enablement, connection selection, initial shared availability, retry windows, generations, leases or source/parser state. Occipital's daemon-owned theme catalogue and its own configuration remain separate. The settings path is implemented and remains unchanged by the separate completed package/command naming refactor.

**Pi-resolved settings root:** `<agent-dir>` is obtained through the public `getAgentDir()` export from `@earendil-works/pi-coding-agent`, not a literal home-directory path or the package's installation directory. Construct the path with `join(getAgentDir(), "extensions", "pi-tidy-ui", "config.json")`. Delegate environment overrides/tilde handling to Pi instead of duplicating its resolver. Pi 1.1.0 public exports, configuration/environment docs and official extension examples confirm this API; a read-only public-SDK probe passed the default, absolute `PI_CODING_AGENT_DIR` override and tilde override. This proves CLI/environment resolution, not arbitrary per-session configuration of a custom SDK embedding.

**Settings implementation obligations:** use one small shared load/validate/update/save boundary, preserve unrelated keys when changing the theme, and keep reads/writes outside rendering and streaming-update loops. Missing configuration uses the Pi-palette default without requiring a write. Invalid/unreadable configuration must not prevent extension loading, trigger an automatic destructive rewrite or fabricate a successfully saved preference; report the issue with bounded diagnostics. Write failures retain the previous valid disk file and are reported as failures. Validate the known theme preference without storing resolved daemon state; the selected theme can still be unavailable on a particular provider, which is a separate runtime/profile policy. Test round trips, missing/invalid files, unrelated future keys and write failure. Use the schema and write rules below; do not add a settings framework, watcher, lock service, migrations or project overrides.

**Default activation accepted:** native syntax highlighting is enabled automatically with the extension, without a separate activation command. Deliberate disabling applies to the current session and uses the accepted safe fallback policy; do not persist it alongside the selected theme. Keep native discovery/acquisition/startup asynchronous and outside rendering, without blocking input or tool execution. Initiate provider selection from the existing eligible interactive `session_start`/adapter-start path, never the extension factory or an arbitrary first source request; start asynchronous work without awaiting connection/acquisition in the event handler. Record initial shared availability once for the client lifetime. Session-local off cancels native activity; re-enabling uses bounded ordinary selection without overwriting that initial observation or reviving/extending an old recovery episode. Source/theme/menu/status operations never reset the initial flag or window. A genuinely new client after runtime disposal records its own startup observation. Non-TUI loading must not start a presentation-only helper.

**Published-package exact standalone version accepted:** release-package delivery metadata names one concrete compatible `occipital` release, independent of the extension's version. Local `0.0.0` builds instead use the colocated binary as specified in section 2.1. With a usable compatible shared provider, use it without obtaining a local helper. When standalone operation is needed, including accepted failover, resolve only the declared release for the actual platform/ABI from trusted cache or an installed native payload; acquire and verify that exact artifact if it is missing. Reuse it on later starts. A different version already present locally is not a substitute just because it is newer or protocol-compatible. An unusable/corrupt artifact is not a valid cache hit; recovery is bounded and remains exact-version acquisition, not update discovery.

There are no latest-release checks, update timers, separate commands to select an arbitrary newer daemon or mutable global preferred-version setting. The preceding tested-baseline-plus-manual-updater proposal is superseded, not accepted. Changing the extension's declared daemon version changes its next owned launch target; keep artifacts versioned so clients with different declarations do not overwrite one another's running executables. Publishing a daemon release does not force an extension release or alter an existing package: each already-published extension retains its generated exact dependency. A subsequent extension publication selects its daemon release once during packaging. Shared modules remain exclusively user-managed and are checked through protocol/capabilities, not exact equality with the standalone pin. The extension settings file gains no daemon-version field.

## 2. Architecture and ownership

```text
Pi tool argument/result lifecycle
  -> source preparation + asynchronous provider controller
  -> selected transport adapter (accepted A2 option 1):
       standalone: owned persistent helper over stdin/stdout
       managed: public Subconscious SDK/router -> shared module
  -> same Rust application/engine in either deployment
     -> one shared Arc<SyntaxSet> per native process
     -> bounded worker actors, each owning its parser states
  <- profile-tagged source ranges or typed admission/restart/failure
  -> local palette/style projection + existing geometry/layout

No exact result -> show current text; schedule one useful provider under bounded policy
```

In Subconscious mode, the service is an **internal service**, not a tool provider or model-facing tool; one module process serves different project/session routes. The standalone mode uses one persistent helper per owning Pi, not per tool, source or project. It supplies the same one-shot/incremental functionality; only cross-Pi resource sharing and managed supervision differ. Within each native process, share immutable grammar assets and compiled regexes; never clone a syntax set per request, source or worker. Pi-palette mode needs no engine theme. Share immutable theme assets under a separate bound, loading bundled definitions lazily where the public API allows and accounting for the validated configured custom catalogue. Never clone assets per request. Each request/session selects a profile, not a global theme shared by all clients. The client always owns terminal composition. Report generated styles as highlighting results, not final rendered rows or a claim of language-neutral semantics.

**Presentation source ownership — operator-approved simplification:** keep `CardSources` scoped to one installed pi-tidy-ui presentation adapter. A complete restoration/removal and subsequent reinstallation (for example master appearance off/on or rebuilding the adapter on reload) ends those presentation-owned source records and may allocate fresh source keys/versions and repeat highlighting, even if an old native attempt has not conclusively finished. This is an accepted minor duplicate-work defect, not a correctness or integration blocker: the reproduced one-byte control demonstrated an extra classifier call, not text corruption, repeated tool execution or a material UI regression. Avoiding an occasional duplicate during this rare lifecycle transition does not justify a client-wide source-ownership registry/API, a permanently rebound consumer, another payload store, locks or delayed reinstallation. Keep normal disposal, weak collection and stale-generation rejection; do not claim cancelled old work physically stopped. Do not intentionally race classifiers within an installed adapter, rebuild adapters on normal frames, or replay the transcript merely to warm it. This architecture changes neither daemon state nor wire protocol. Decision/evidence: `.test-artifacts/occipital-implementation/g3-ui-host-reinstall-finding.md`.

The Subconscious adapter uses public Rust `ModuleHandler`/`serve`, `RequestCtx` cancellation and route lifecycle hooks. The direct adapter maps owned pipe lifecycle/correlation into the same application operations; do not duplicate the parser/session engine. `SyntaxSet: Send + Sync` is verified in the probe. `ParseState: Send + Sync` fails for Oniguruma capture regions. Therefore:

- Create and retain parser/checkpoint state inside a fixed worker thread.
- Send owned source deltas and plain result data through bounded channels.
- Assign a growing source to one worker for its lease; serialize its updates.
- Keep Tokio/network tasks free of parser state and synchronous parsing.
- No unsafe Send implementation, private parser-field access, unbounded `spawn_blocking`, per-request thread or grammar-set clone.

In Subconscious mode, use the SDK's **complete RouteHandle** as server-derived namespace: it includes connection identity, channel and epoch. For direct mode, use the server's owned pipe/process incarnation, not a caller-asserted cross-process identity. A client stream key is unique only within its transport-owned namespace. Release state on route loss/pipe EOF, connection end or drain, including outer adapter error/return cleanup; the SDK's normal `on_connection_end` hook is not called on every error. Project paths and client IDs are metadata, not authority.

Initial shared-server recommendation: at most two worker actors, or one on a single-core host. Calibrate standalone separately so every Pi does not blindly multiply the shared-server resource allowance. A small count-and-byte-bounded admission layer assigns work with fair per-route turns. Each actor also yields between bounded line/byte quanta, preserving its unfinished one-shot/stream state on that same thread, so a long normal source does not monopolize it. Aging/fair turns allow finite jobs to finish; do not give endless streams absolute priority. One regex call is still non-preemptible. Do not add worker processes unless measured behavior requires an operator-approved architecture change.

## 3. Source and classification contract

A source is a logical code string already owned by the caller, plus a conservative language hint and optional basename; it is not a path to open. Prepare logical source separately from terminal-cell projection. Preserve each surface's existing control/bidi sanitization and newline normalization, but retain **tabs as source characters until after classification**, for file and command sources alike. This deliberately moves file-tab expansion after highlighting; it must not change visible geometry, saved args/results/session bytes or diff pairing. No NFC normalization, file reads or producer guesses.

Language resolution order: explicit supported hint/alias, exact supported basename/extension, then unsupported. First-line recognition may use the supplied source only. Pin/test aliases including Bash, TypeScript/TSX, JavaScript/JSX, JSON/JSONC, Python, Rust, YAML, HTML/CSS, Makefile and Dockerfile; do not claim that every alias is supported until the actual assets validate it. Unknown language falls back rather than guessing prose's language.

Results are structured source ranges, never ANSI, line numbers, wrapping or source text. **Pi-palette profile:** versioned lexical categories preserving useful grammar distinctions; the client maps them into Pi's nine syntax roles. Plain inherits `toolOutput` for files or `toolTitle` for commands. **Independent-theme profile:** native Syntect scope selectors resolve structured foreground/font styles; a bounded table and style-ID ranges preserve those distinctions without a Node scope interpreter. Profiles and their IDs are negotiated explicitly, never guessed from payloads.

Ordinary unscoped identifiers remain plain; richer colors do not invent semantic information. Preserve diff tints, gutters, Multiply backgrounds and card paint in either profile. Unknown/invalid category or style IDs reject the complete response. Do not replace the user's global Pi theme or add another classifier to fill grammar gaps.

Offsets are **UTF-8 byte offsets in the exact logical source supplied to the service**, not raw argument indices, JS UTF-16 positions or terminal columns. Node checks surrogate pairs before encoding; malformed strings remain displayed unchanged and cannot enter an inexact wire stream. Decode checked ranges once. Determine append/no-change/reset on logical source after normalization: a raw CR→CRLF update can have no logical change, and completing a control sequence can require a reset.

Projection expands file tabs at the existing four-column logical stops and Bash tabs at the existing eight-column stops, including `$ ` and soft-wrap effects; generated spaces inherit the tab's style. Prompts, synthetic comments, gutters and diff signs are never parser input. Never insert ANSI inside a grapheme: use the style covering its first scalar for the whole displayed cluster. Preserve existing wide-glyph substitution and wrapping. Compare classifier output to logical source before projection, and projected glyphs to the old renderer afterward. Supplied command/write strings preserve normalized final-newline presence; diff segments preserve their existing available-row assembly without inventing unknown file endings. The generic service preserves whatever line endings it receives; pi-tidy-ui's existing normalization is not a claim of raw CRLF preservation.

Validation before painting: negotiated version/result profile/table, exact generation/source/profile fingerprint, byte length, ordered in-bounds ranges, UTF-8 boundaries, complete partition of the expected replaced region and bounded payload/table. Replacement starts must match the acknowledged tail boundary, and required prior client coverage must still exist. Reject the **whole invalid result**, not just inconvenient ranges. No response may change the code being displayed.

### Accepted long-line highlighting policy

For each LF-delimited source line, including an unfinished final line, classify at most its first **64 KiB (65,536 UTF-8 bytes)**. End the classified prefix at the last valid UTF-8 character boundary not exceeding that budget. All remaining bytes through the end of that line are **Plain**, remain fully present in source/range coverage and are ignored by the parser. Plain coverage uses the caller's neutral text style even under an independent native theme (an explicit `plain` role is allowed in native palettes; other Pi syntax roles are not). This is a coloring-work window, not an input-size rejection, source truncation or provider failure; do not invoke another classifier to fill the skipped tail.

Carry the parser/scope/highlight state produced by the classified prefix into subsequent lines **without resetting it**. The operator explicitly accepts that ignored tail characters can contain syntax that changes continuation state. Consequently, subsequent lines may start with an incorrect context and may be highlighted incorrectly. The prefix itself is classification of shortened parser input, not a guarantee of identical colors to an uncapped whole-line parse. Do not parse the skipped suffix merely to repair state, invent a newline at the cutoff, or switch the rest of the source to Plain: the same prefix policy applies independently to later lines.

One-shot and growing sources use the same policy. Once an unfinished line has saturated its unchanged classified prefix, appending only ignored tail bytes must not reparse that prefix. Track the full source byte count and real line boundaries, extend Plain coverage and preserve exact acknowledgements; do not retain/copy the whole ignored tail as parser continuation text. Commit the prefix-derived state when the real line ends. Rewrites, generation/profile changes and named resynchronization retain their existing invalidation rules.

In this plan, **fresh batch/every-prefix equivalence** means equivalence to a batch implementation of this accepted policy, including its deliberately approximate continuation context. For sources whose lines stay within the window, require ordinary full-Syntect equivalence as before. Regression controls cover UTF-8 cut boundaries, exact full-text coverage, skipped-tail syntax affecting later context, multiple overlong lines and zero new parse calls for ignored-tail-only growth.

A changed definition gets a new fingerprint; the requesting client applies the existing bounded source/profile reset rules rather than mixing old/new styles or sweeping the transcript. Refresh must not restart the shared daemon or other clients; catalogue/reply revision handling must safely expose changed definitions at subsequent use. The bounded publication/revision rules below are part of the implementation contract and require cross-client tests. Automatic file watching and polling are not part of the selected design.

**Catalogue identity, revision and failure rules:**

- Expose stable opaque IDs in separate bundled/custom namespaces, plus labels and definition fingerprints. No lookup converts an untrusted ID into a filesystem path. Use a deterministic custom-file identity within configured roots and reject ambiguous duplicate IDs rather than depending on enumeration order. Changing a file's contents changes its fingerprint, not its ID; renaming/removing it may remove that ID. Final ID encoding is frozen in the schema/vector phase.
- Startup and explicit refresh build a count/byte-bounded candidate from the daemon-owned configuration. Validate the complete candidate before publication; a read/parse/duplicate/limit failure retains the previous valid catalogue and returns a bounded error. On first-start failure, bundled definitions still provide a usable baseline. An intentional file/config-entry removal takes effect only through a successful refresh; a disappeared configured directory/read failure is not silently treated as an empty catalogue. Missing default configuration/themes on a fresh installation is normal, not an error.
- Publish a new catalogue revision only after validation, retaining immutable definitions for already-running work only within in-flight/lease budgets. Independent theme changes are not a change to the Pi category profile. Resolve/check the requested definition fingerprint before parsing; a stale fingerprint returns `profile_changed`, and an unavailable ID returns `theme_unavailable`, both with `execution=not_started`. Affected old-profile leases become restartable, not silently recolored midway. A running old-profile request may finish with its old fingerprint; the client accepts it only while that exact effective generation is still current.
- The refreshing client receives the new catalogue and renews its previously useful retained owners if the effective profile ID/fingerprint changed. Other clients learn changed availability/revisions on their next normal control/source interaction; no watcher, broadcast subscription, periodic polling or forced full-transcript recolor. Idle retained output may keep its earlier colors until a named invalidation/demand. A no-change refresh causes zero source reclassification. Updating an unrelated theme must not reset every stream.
- Account for simultaneous old/new definitions, style tables, selectors and non-evictable scope interning. Bound changed-definition parse attempts/cumulative intern growth before admission, including failed refreshes; do not assume dropping a catalogue reclaims Syntect's global scope repository. If the public implementation cannot uphold these bounds, stop at G1 instead of adding unlimited caches or a new worker topology.

## 4. Communication: one-shot and growing sources, one application protocol

### Transport boundary

Application operations and result validation below are shared by both accepted adapters. For direct mode, add a small byte-bounded, correlated pipe envelope; measure JSON encode/decode and write-drain behavior, keep diagnostics off stdout and close all owned sessions on EOF/crash. A new helper/connection is a new provider incarnation. Do not add a per-source process or a second implementation of stream semantics.

**Subconscious adapter:** the G2 JSON length/style representation uses declared capability `syntax-highlight/v2` and internal service ID `syntax`. G0 proved the public manifest/discovery vocabulary; the application version/capability is now2 so old endpoint-format peers cannot silently negotiate as length-format peers. Open the target through public `routeOpen({kind: 'internal_service', ...})`, then use explicit `request` and owned route handles. The Node SDK's managed `call()` only targets tool/management routes; do not disguise the highlighter as either to reuse that helper.

Load the SDK lazily with handled failures; recommend a pinned optional dependency compatible with Node SDK 0.21.1, selected and tested at G0. A missing/unloadable SDK must not prevent pi-tidy-ui from loading. Resolve a single provider through public discovery/catalog APIs; ambiguity fails closed rather than selecting a random module. Honor the selected public discovery contract and SDK ownership/permission checks; explicit endpoint overrides retain their documented exclusivity. Never publish/log connection-file keys or invent an undocumented locator for the user's fleet. A4 automatic selection is accepted; G0 must verify the concrete supported discovery integration. No private shared endpoint is part of the accepted topology.

The pinned Rust SDK 0.26.3 `HandlerOutcome::Response` uses non-binary response flags; the inspected published 0.26.4 retains this behavior. Node chooses its decoder from those flags. The operator selected **compact JSON for now**, without a Base64 carrier, SDK change, raw private sender or progress-message workaround. Source is ordinary JSON string data. Ranges use a flat numeric array `[byteLength, valueId, ...]` and a negotiated category or result-local structured-style table. Application protocol2 / `syntax-highlight/v2` explicitly identifies this representation and rejects old endpoint-format peers. Each byte length is positive; validation reconstructs absolute UTF-8 endpoints from the acknowledged `replace_from`, verifies exact suffix coverage, character boundaries and adjacent-value coalescing, then retains canonical absolute ranges. The engine and range accumulator keep their existing canonical representation. Packing is confined to Rust JSON serialization and TypeScript wire validation, never guessed from values or confused with canonical UTF-8 offsets. Coalesce adjacent equal values. Profile/table identity remains unambiguous across replacement chunks. Bound and measure actual JSON header/source/array bytes, encode/decode CPU and temporary allocations rather than reserving six bytes per input byte indiscriminately.

**Future codec seam, not a new transport architecture:** Rust engine/scheduler/session code produces typed semantic results and does not choose JSON or binary framing. Centralize bounded JSON encoding/decoding and wire-specific run packing in codec entry points; transport adapters retain correlation, backpressure and delivery ownership. TypeScript validates the decoded application schema and stores canonical UTF-8 ranges independently of the selected codec. Do not scatter `JSON.stringify`/`JSON.parse`, escape expansion estimates or Base64 decisions through the source controller. A future binary codec changes these boundary functions and supported-format compatibility checks, not parsing, leases, retries, range accumulation or UI painting. Advertise only implemented/tested formats; use public format/response APIs when they become available, and keep JSON as the compatible path. No codec plugin framework, unused binary branches/dependencies or extra wrapping layers are needed now. If public transport admission or adequate JSON allocation bounds cannot be established, stop and report that separate blocker.

### Application operations

| Operation | Input and lifetime | Result |
|---|---|---|
| `describe` | No source; normal negotiation or explicit menu catalogue request | Protocol/assets/profile fingerprints, bounded catalogue revision/IDs/labels/definition fingerprints, configuration diagnostic summary, supported modes, admission policies and hard limits/idle/max-age TTL |
| `themes.refresh` | Explicit menu action, no client-supplied paths/definitions | Validate/reload the daemon's configured catalogue; return the current/new descriptor or a bounded error while retaining the last valid catalogue; no daemon restart |
| `highlight` | Client-declared one-shot: one or bounded finite-source batch, keys/versions/profile/admission | Complete classification; temporary work record only, no completed classification cache |
| `stream.open` | Client-declared growing source: key + new generation + initial snapshot/language/profile/admission | Lease, parser revision, full initial classification, finite expiry |
| `stream.append` | Lease/generation, expected parser revision, expected byte count, new source version and appended text; optional final flag | Next revision and replacement classification from the previous provisional-tail start |
| `stream.close` | Owned lease/generation, used for cancellation/release without final text | Best-effort release, idempotent when absent; no persistent tombstone store |

**Catalogue wait on a published provider:** its finite waiting deadline is not a transport-retirement deadline. The client opts into the transports' metadata-only `waitOnly` API for `describe`/`themes.refresh`: reject the expired waiter, retain the last validated catalogue, provider generation and unrelated source requests. Keep the unanswered control slot and bytes until a real correlated stdio reply, actual SDK promise settlement, or transport closure; refuse additional controls while the slot remains occupied rather than queueing them. A late reply cannot publish through the expired waiter. An uncertain SDK rejection after that metadata wait expired releases only the actually settled local control; explicit public route/socket loss or denial still follows ordinary transport termination. Source requests cannot opt into this mode. Startup negotiation and ordinary source deadlines/recovery retain their existing behavior. This split was operator-approved after the real-adapter timeout defect was independently reproduced; do not fix it by lengthening the deadline or suppressing the broker's lifetime observer.

Reset is close/open with a **new generation** and supplied full snapshot, not an arbitrary-edit/checkpoint protocol. No network subscription is required: input growth uses bounded ordinary request/reply. Viewport and Pi terminal palette are not parsing inputs; an independent syntax-theme profile/fingerprint, if selected, is part of session/result identity.

Admission is explicit: `try_now` or `bounded_queue`, with a bounded maximum queue wait. A typed `busy`/`queue_expired` response with `execution=not_started` guarantees no source parsing or parser-revision advance for that entire request/batch. If work starts, a timeout is not this guarantee. Limits/rejections are ordinary application responses through the public SDK, not an invented transport facility. No queue polling, ETA subscription or extra reserve/commit round trip is required. `try_now` cannot jump ahead of another route's entitled fair turn; an existing stream stays on its owning worker even if a different worker is idle.

Missing/expired/evicted/incompatible owned state returns `restart_required` with a bounded reason, including `base_mismatch`; reopen the latest caller-owned snapshot after budget admission. Do not recover by rereading files or looking up completed classifications. No-match route/session errors must not expose another route's state. Serialize mutations and recheck revision/expiry on the owning worker at actual dispatch, not only at ingress. Close/append target the exact lease generation, never just the reusable client key; a late old close/open must not replace or retire a newer generation.

All messages identify protocol version. Source replies include service/assets/effective-profile identity, client source version, generation, parser revision, source byte count and replacement start byte; no caller infers a profile from an error or range shape. Control replies carry the bounded catalogue/configuration metadata, not fake source revisions. `theme_unavailable` and `profile_changed` are whole-request no-start responses, not partial coloring or transport failures; reconcile the profile and resubmit current demand once under a fresh generation/budget rather than retrying the same rejected request. State-changing requests also carry the expected prior revision/byte count. Treat all externally supplied lengths/counts as checked integers within negotiated limits.

### Revisions, races and failures

Distinguish **source version**, **parser revision** and **transport correlation**. A reply may be too old to paint but still acknowledge valid parser progress for a newer append-oriented source. Update the acknowledged parser state/result internally, then send the coalesced latest delta. Do not discard required acknowledgements and subsequently append against the wrong base.

At most one append per source is in flight. Keep one latest waiting snapshot, not every intermediate update. Verify that it extends the acknowledged source before computing/encoding only its suffix. Pi supplies full snapshots, so local prefix verification may be O(prefix); instrument it and do not claim that every client-side step is O(delta). Do not repeatedly UTF-8 encode/hash the full prefix.

Rewrites, shrinkage, language changes, malformed input recovery, source replacement and generation loss start a new stream. An unknown outcome after sending an append is **not safely retried**. Mark the lease uncertain and reject stale presentation. Resynchronization uses the newest complete snapshot under a new generation and a finite retry limit, but expensive replacement work is still gated by a proven settled/no-start attempt or the accepted actual-failure recovery exception. An unknown outcome/timeout by itself never authorizes duplicate expensive parsing, even on a new lease of the same provider. Expired/evicted server leases and evicted required client-prefix chunks use the same bounded recovery. Before restarting, reserve enough client budget for useful coverage and choose growing mode only if input is still unfinished; otherwise use a new one-shot. Without capacity stay in the selected fallback/protective state. `base_mismatch` never means silently appending to whichever state exists.

Subconscious AbortSignal/CANCEL is best effort: it does not prove rollback, interrupt a regex or settle the Node SDK request promise. Direct-mode cancellation must preserve the same distinction; an explicit owned-child exit proves that process stopped, not that a previous reply was delivered. Keep abandoned requests counted until actual settlement/owned connection closure. Apply outer finite usefulness bounds to import/connect/catalog/open/describe as well as data work; `routeOpen` does not accept the request's AbortSignal/timeout. Close late results on retired controller generations. Close only the dedicated highlighter-owned connection, never another extension's client. Late replies install only if all identities/coverage still match. Policy/capability/scope closure is not transient; route generations prevent reusing old handles.

### State loss is an ordinary protocol condition

Neither a live connection, an unchanged daemon PID nor a successful earlier append guarantees retained state. The server may reset all state or lose one lease at any time. Unknown/expired/evicted/ended/reset leases return `restart_required`; changing providers always invalidates old remote leases. Lease/generation identities must not alias fresh state after reset. Reject stale replies/acks rather than attaching them to a replacement stream.

Use one recovery path: invalidate affected remote state, retain caller-owned text and independently valid classifications within budget, and reopen only currently needed source from the latest full snapshot under a fresh generation. If input is complete, use one-shot instead of inventing a continuing session. Resetting one lease does not reset unrelated live sources or repaint the entire transcript. Repeated resets remain subject to admission and finite retry bounds; a normal timeout does not authorize an expensive parallel replay. No file reread, parser-state migration, durable server checkpoint or completed-result daemon cache is required.

### Client-owned logical lifecycle and server-owned physical retention

| Event | Required transition |
|---|---|
| Start a finite source | One `highlight` request; its temporary server session completes on response/error/cancel, no extra open/close protocol |
| Start unfinished command args | Open growing source; append only acknowledged normalized deltas |
| Native `setArgsComplete()` | Mark source logically complete; flush latest snapshot with `final=true` (possibly empty append), then release |
| Completion arrives during an earlier request | Keep one final target, consume valid ack, final-flush under a finite deadline; close if useful finalization cannot complete |
| Tool runs a long time/result-only updates | No retained source lease or new classification work for unchanged completed args |
| Replay/late attach to already-complete args | One-shot; never wait for a completion event that already occurred |
| Rewrite/language/profile change | Retire old generation, reopen latest full snapshot if useful/admitted |
| Abort/error/detach/off/reload | Cancel usefulness, release budget and close best effort; late init/replies cannot resurrect ownership |
| Server expiry/eviction/ended lease/global reset, even on the same connection | Reply `restart_required`; invalidate affected state and reopen latest full snapshot under budget, or one-shot if complete; no fake live lease |
| Provider changes, including standalone-to-shared return | Old leases/checkpoints are not transferable; fresh generations, retained valid results, demand-only resubmission |
| Idle timeout/absolute max age | Server may reclaim regardless of client expectations; no-op append/retry/status does not renew indefinitely |

Observe the actual guarded Pi `setArgsComplete()` seam while preserving its original/descriptors; the baseline reads `argsComplete` but does not yet wrap that method. Execution start/result completion is not a substitute. The server needs one expiry mechanism, no client heartbeat. Once a lease is expired/closed, running work becomes unusable immediately; actual resource release may await a safe parser boundary. Every serve exit (normal or error) shuts down owned actors.

## 5. Daemon incremental algorithm and retained data

Use two-face `extra_newlines()` and feed real line endings within the accepted classified line prefix; never fabricate an ending when the real ending is beyond that prefix. A lease retains:

- Current language/assets/profile identity and confirmed revision/byte count.
- A `ParseState` plus `ScopeStack` before an unsaturated provisional tail, or after its classified prefix once that prefix is frozen; native-theme mode may use `HighlightState`, whose path already contains that stack. A frozen prefix cannot change under append, so promote its continuation rather than retain a second parser checkpoint.
- The unfinished final line's classified prefix (at most 64 KiB), its compact classification/Plain-tail coverage and full byte count, only while more source/finalization is expected; no parser-owned copy of ignored tail text.
- Small revision/expiry/quota metadata, not a recent completed-prefix result cache.
- No full source history, committed-range archive or per-line checkpoint database. Bounded in-flight reply storage is transient transport work, not a cache.

On append:

1. Validate namespace, generation, base revision/byte count and admission before parsing.
2. Extend only the retained classified provisional prefix while it remains below 64 KiB; track full ignored-tail byte counts and real line boundaries without assembling the ignored text.
3. Parse newly complete classified line prefixes from the committed inter-line state and emit Plain coverage for skipped suffixes. Carry the prefix-derived state forward, accepting approximate later context as specified above. Yield between line/byte quanta for fair worker-local scheduling; never move the parser to another thread. These lines are committed once.
4. Clone the resulting inter-line parser and scope/highlight checkpoint to classify a still-changing unfinished prefix. Keep the pre-line checkpoint while the prefix can change. On saturation (including a UTF-8 character that cannot fit), promote the prefix-derived continuation and freeze its classification. Ignored-tail growth and the later real newline do not parse it again. The real line's source/range commitment still advances only at its actual end or finalization.
5. Return classification replacing the old provisional tail and covering the new suffix; leave earlier result chunks unchanged on the client.
6. Advance revision only with a complete accepted result. On cancelled/failed partly mutated work, discard the lease if safe rollback cannot be proven; never leave undocumented partial progress.

The daemon discards committed source/ranges once their bounded response is handed to transport; only the checkpoint, provisional tail and small metadata remain reusable. No completed source classification cache, including after one-shots/finalization, eviction or disconnect. The client owns committed result chunks. Finalization without changed text reuses the current tail classification and releases all lease state; it inserts no fake newline. Actual final newlines commit normally. Parser captures may internally retain earlier text as required continuation state; account for that heap without treating it as a completed-result cache.

This prevents repeated whole-document parsing under normal append. An unfinished prefix can still be reparsed while its classified text changes, but ignored-tail-only growth after saturation performs no new prefix parse. Cloned capture state and exceptional full resynchronization remain separately accounted. Results must equal a fresh batch implementation of the accepted 64 KiB line policy at every accepted source prefix, not uncapped Syntect after a skipped suffix.

Completed/closed/detached/expired/route-ended/crashed-client leases must be released, not merely marked reclaimable indefinitely. Advertise idle and absolute maximum age; refresh idle only on accepted new source progress, not empty retries or status. Under pressure evict idle state first, then bounded active state at safe boundaries if required, returning `restart_required` rather than breaking correctness. One daemon-owned expiry mechanism is sufficient; no per-document heartbeat. No durable database, migration, file watcher, arbitrary edit tree or cross-client source deduplication in the first implementation.

### Presentation and work are separate decisions

The whole current grapheme inherits its first matching scalar's style. Historical colors are never parser/current-source proof; corrected suffix islands are not reused. Live formation interruption retires native work but retains one charged display basis for that owner. Reopening a saved session or restoring a new historical owner instead classifies its available Bash text once as a finite snapshot, regardless of call success, without executing it or changing its incomplete-argument/error flags. Public assistant-stream call identities distinguish live owners, even before the first useful frame; no history scan or persisted color cache. File sources retain their existing complete-line-prefix/exact Pi fallback rules.

Observe already-owned argument/result/finalization/invalidation calls after preserving their originals. Late/replay discovery uses existing weak ownership. A normal render may record a cheap weak demand ticket, not start RPC, import an SDK, prepare/encode/hash whole source or call a highlighter. Work is scheduled after the render returns. Coalesced notices invalidate a Bash layout only for a compatible display effect, not a version/job/lease/completion-only change. Local G1 first-call timings describe their recorded host/runtime, not portable guarantees. Queue/running/uncertain daemon work is not permission to start Pi for the same current source within its installed adapter. The complete presentation-reinstallation exception in section 2 intentionally does not preserve that owner across adapter lifetimes. A file Pi result produced during startup may remain visible through one counted native-provider readiness upgrade; this is not a recurring race.

Its public highlighter can initially return an ordinary uncolored result, indistinguishable from successful plain fallback, while its public `theme.colors` identity stays unchanged after the grammar loads. Retain that exact result until the existing source, palette or presentation-owner identity changes; do not add a private loader/readiness hook, timer, probe or classification-cache reset on general `TUI.invalidate()`. An early non-eager-language fallback may consequently remain uncolored in cold replay. This is an accepted visual limitation, not text loss or a passed identical-color claim. Native-provider readiness and classification validation remain unchanged. Never call Pi's highlighter for Bash fallback, including initialization, session off, unavailability or source admission refusal. Retained Bash colors follow the streaming contract's historical matching-prefix rule; this decision does not replace the daemon classifier or invent a second classifier for Bash. Coalesce latest native source changes and preserve argument completion. No first-snapshot, line, size or time sampling heuristic is needed for Bash.

Keep exceptional size/memory protection, not a guessed time limit: an input beyond the source guard, or a result that cannot fit the shared client retention allowance, remains exact plain text/proven daemon prefix. Never truncate source or repeatedly retry an unretainable result. A real reproduced fallback stall is investigated on the actual workload before changing this policy; a microbenchmark or one slow call does not automatically disable a language. No private Pi imports, Theme replacement, fake theme files or unbounded worker pool.

### Minimal scheduling algorithm

1. Reuse compatible exact results before doing any work. Coalesce source changes, retaining one acknowledged basis and one latest useful waiting snapshot under budget; unchanged logical snapshots create no sample/job.
2. Prepare/validate logical source once outside rendering. Capture source/provider/profile/owner generations. Reject unsupported or over-budget daemon inputs before encoding; do not repeatedly scan/hash the transcript. Process accumulated card demand newest-to-oldest by stable source-ticket creation order, not latest update/retry, without sorting the entire weak-ticket backlog each turn or cancelling/reprioritizing already admitted native work. Process at most the existing two-job limit of card owners per batch and yield to the event loop before another batch, including synchronous and asynchronously queued demand. Keep the host-turn barrier through notifications queued by dispatch even if pending is momentarily empty; an empty one-shot stops rather than polling. The weak continuation does not own cards or source text; no idle polling or millisecond budget. Individual preparation remains synchronous, not preemptible.
3. With a ready compatible provider, prefer its existing fair `bounded_queue` admission. A typed terminal `busy`/`queue_expired` response with `execution=not_started` permits ordinary Pi fallback for the still-current file snapshot (Bash remains `toolTitle`); it is not a transport failure or a reason to poll the queue. `try_now` remains supported where an immediate no-start decision is needed, not selected by a language timing table.
4. During initialization/acquisition, deliberate session disablement or established unavailability, use the public Pi fallback for useful ordinary file source under the source/retention guards, then cache the exact result. Bash instead uses its existing full-command `toolTitle` fallback, without Pi classification. **Session-only native off within the installed adapter is not an exception to the no-duplicate rule**: preserve bounded per-source execution evidence in the canonical controller after releasing the native source/color payloads. A cancelled pending/running/uncertain attempt still forbids Pi classification of that current source until authoritative completion/stop evidence; use its independently valid saved colors or full plain text meanwhile. Missing native state or transport unavailability is not such evidence. Do not suppress unrelated sources globally or add timers/polling to guess completion. The operator selected this policy explicitly during G3 integration; the decision and tiny API control are recorded in `.test-artifacts/occipital-implementation/g3-api-blockers.md`. Otherwise keep all text plain/proven-prefix. Full presentation removal/reinstallation is the separately accepted section 2 exception: normal adapter disposal may release source records and fresh demand may repeat highlighting without a new cross-adapter ownership API. Startup is coalesced and outside rendering; it never waits on a source merely to warm a grammar.
5. Queued, running or uncertain work retains exact text/proven prefix and any independently valid exact Pi result. No elapsed-time hedge, periodic fallback attempt or repeated whole-source parse. Timeout/CANCEL does not prove physical work stopped; never retry an uncertain append against its old base.
6. Keep provider selection stable over an update burst, coalesce latest source changes, and flush final text once. Unchanged file source/palette produces zero Pi calls; Bash produces zero Pi calls in every fallback state. Completion is a guaranteed useful latest-native-source trigger, not Bash process exit.
7. Initial startup and connection-loss recovery use the same availability-wait path. Useful Bash requests deferred while an enabled provider/effective profile is unavailable mark their existing weak card/source slots. On readiness, revisit all marked, still-owned and unpaused/unfrozen requests with their latest revisions through the existing bounded scheduler. No additional strong queue, source copies or history scan; already-current coloring and bookkeeping refusals are not replayed. Metadata-only loss does not reevaluate an unchanged processed Bash revision or relabel its prior refusal as an availability wait; a real source change can create new demand. Retain the existing one bounded latest-file native upgrade with its exact Pi fallback visible, not a full replay of file fallbacks. No periodic recoloring or per-frame retry. Actual-failure replay uses the separately accepted recovery rule.
8. Resource pressure or owner loss stops admission and releases tickets/buffers. Retire leases whose required prefix chunks were evicted; retry only on eligible demand with capacity. No reopen→evict→reopen loop or repeated Pi allocation for a result that cannot fit.

These are source/lifecycle/admission rules, not millisecond acceptance gates. Source/retention guards and protocol/usefulness deadlines remain; Pi fallback has no measured cost allowance or elapsed-time trigger. Validate actual work with counters and real UI/native controls. Do not add progress subscriptions, timing-distribution matrices or queue polling to guess why a reply is late.

| Case | Required decision / invariant |
|---|---|
| Exact retained result, provider now absent | Reuse it; no RPC/native parse merely to check health |
| Multiple useful Bash demands before initial readiness or during connection loss | Mark existing weak source slots; the same ready callback admits all latest deferred revisions in cooperative batches, with ordinary native credit and no ready-result/file-fallback replay |
| Exact snapshot with a new Pi palette | Repaint neutral categories; recount a native fallback rehighlight only when its exact theme-colored output is no longer valid |
| Independent syntax-theme/profile changes | New fingerprint/generation and bounded current-demand reclassification; no hidden completed-result cache |
| Selected theme absent/unsupported on startup, provider switch or successful refresh | Notify Pi UI once per failure episode; retain saved preference and use the daemon's Pi-category profile when available, otherwise ordinary safe fallback |
| Selected theme becomes available again | Reconcile on ordinary provider/catalogue/selection events, restore effective profile with a fresh generation; no poll or transcript-wide sweep |

## 8. Resource model and calibration gates

There is no requirement to support resource-constrained machines. Limits are exceptional-overload safeguards, not targets that ordinary use must fit. Ordinary files, sessions and expected concurrency must not routinely trigger admission refusal or protective degradation; ordinary10 MiB and larger sources are explicitly included. The separately accepted 64 KiB per-line coloring window is an explicit rendering approximation, not overload refusal or evidence that a long line is abnormal. Measured example sizes establish supported cases, not a normal-use ceiling. Source size, encoded message size, output density and simultaneous allocations are separate quantities. The operator authorized replacing the initial1 MiB/8 MiB and64/128 MiB candidates below with adequate protective bounds; they are not acceptance constraints. Audit line/client/queue/count caps as well as byte caps. Add an independent count limit only when its actual requirement is established; do not duplicate byte protection with an arbitrary count ceiling. The TidyUi2048-entry cache thrash is a regression lesson: pressure must not cause eviction/re-dispatch/recomputation cycles on ordinary renders or block Pi's input loop. The operator rejected additional large measurement matrices or gigabytes of traffic solely to collect statistics; use existing calibration evidence and focused correctness/admission/peer-lifecycle controls. Genuinely new API/architecture blockers still require an explicit stop and decision.

Account separately for shared syntax assets/compiled regexes, parser captures/scope stacks, retained tail/results, raw/in-flight source strings, codec encode/decode/transient buffers, queued jobs, replies and SDK ingress/egress queues. `size_of(ParseState)` is **not** its heap size: it can retain captured strings/regions. Exact private parser-heap accounting is unavailable; do not claim a hard process-memory cap from an application payload counter.

The recovery cadence (60 seconds) and scheduling window (600 seconds, at most ten scheduled probes per failover episode) are operator-fixed. They are not lease expiry values. A single bounded control probe must be accounted for alongside source/transport budgets; timers must not keep a retired client alive.

**Operator resource-policy correction:** limits protect exceptional accidental overload, excessive retained state and failure risk; they must not routinely reject ordinary files, clients or requests. There is no resource-constrained-host requirement. The largest measured example is not an ordinary-use ceiling. Do not add redundant count limits where byte accounting already charges every entry, or allow pressure to trigger repeated eviction/re-dispatch/recomputation on ordinary visits. Existing10/32 MiB and wire-format evidence is sufficient: no further large allocation/throughput matrices or gigabytes of traffic for calibration statistics.
