# Unified highlighting and card palettes — refactoring plan

## 1. Status and authority

Original design/prototype baseline: `296199405e508c8066bd0480e2a07ee2e32a4a4a`. Active integration baseline: `7af17b7` after pulling remote `main`; runtime/Rust sources and dependency lock are unchanged, but test discovery, locations and fixed CI obligations were re-read and reconciled. Earlier receipts retain their original identities; they are not relabeled as acceptance of the new baseline. This document records the approved replacement of the original v2 highlighting architecture. The coherent v3 source cutover, removal, required local implementation checks and final evidence/documentation review are complete for the recorded Linux x64 scope. Subsequent fullscreen-transfer and volume-policy acceptance remain separately source-bound; none implies public delivery or all-platform/remote-CI acceptance. The operator has authorized its implementation, including the recommended P1/P2 policies and frozen-display revision, subject to E1–E3. It does **not** describe shipped behavior or authorize commits, tags, publication, deployment or changes to Pi/AFT/Subconscious. The [current specification](syntax-highlighting-spec.md) describes the locally accepted v3 source implementation; future public delivery is the separate R1 gate. The [earlier implementation plan](syntax-highlighting-plan.md) retains historical v2 and delivery evidence.

The operator requested one mechanism, minimal duplicate code, rich Syntect regions, limited Pi-theme fallback, and explicit performance criteria for streaming, theme selection and geometry. Oracle reviewed the architecture and its vocabulary/fidelity risks. Consultation and the preceding proposal are preserved under `.test-artifacts/universal-highlighting/`; they are evidence, not additional hidden requirements.

**Operator-approved palette policy:** when a Syntect theme is effective, **every foreground and background inside a Bash/edit/write card comes from that theme or is derived exclusively from its colors**. This includes plain text, service text, frame, gutters, diff signs, diff backgrounds, output, diagnostic/reminder sections and footers. Do not use Pi colors to fill missing native roles or combine native code colors with a Pi panel. Follow Pi uses Pi's palette through the same presentation interface. The rest of Pi's UI is not recolored.

The original design supplied a dependency/change/test inventory and ordered gates without assuming feasibility in advance. Product decisions P1–P2 were accepted as proposed below; E1–E3 were prerequisites to dependent implementation. Their completed local disposition is recorded under [current readiness](#10-current-readiness). New material findings return to the operator; no implicit alternative engine, binary carrier, scope reduction or compatibility layer is authorized.

## 2. Accepted policies and engineering details to freeze

| ID | Concrete gap and consequence | Accepted policy; engineering convention still subject to its gate |
|---|---|---|
| P1 | The existing file fallback returns **already colored Pi ANSI**, not Syntect scopes. It cannot be recolored faithfully into a native theme. Cold startup, native Off, unsupported source and provider/theme failure therefore need an explicit whole-card policy. | With a retained native palette, keep compatible retained native syntax or render missing classification neutrally using that palette; do not run/use Pi-colored syntax inside it. When no usable native palette has ever been obtained, use an explicitly identified **whole-card Follow Pi fallback**, retaining the saved native choice. Never wait for the daemon to show text. This explicitly changes the old independent-theme file fallback. |
| P2 | Native theme settings are optional; some use indexed colors, terminal defaults or alpha. Missing colors cannot be secretly borrowed from Pi, and terminal-dependent values cannot support an unconditional RGB contrast claim. | Honor explicit native indexed/default colors without inventing RGB; derive missing secondary roles from available native base colors. Additional accepted behavior: freezing a live interrupted source prohibits further **parsing**, not recoloring/reflow of its retained validated scopes. Source lease revival remains forbidden. Per-token syntax backgrounds remain suppressed as today; theme background settings and explicit diff-region background hints feed the card palette. This preserves diff-row ownership rather than allowing a theme's default token background to erase it. Extending per-token background effects would be a separate decision.

## 4. Data and ownership contracts

### 4.1 Theme-independent source

A semantic source basis contains source incarnation/version, grammar/assets/vocabulary identity, parser revision/coverage, immutable ranges referencing full ordered scope contexts, and provisional-tail replacement metadata. It contains no selected theme. Unclassified bytes are a distinct neutral value, not an empty successfully parsed context. Context ID zero must not merge these meanings.

Keep current normalization, language selection, continuous old/new diff segments, missing-context resets, exact UTF-8 offsets and source finiteness. The 64 KiB per-line window remains; the subsequent whole-source volume policy chooses the actual classification prefix before submission. Preserve complete display/tool/session text. The producer never silently truncates an admitted SOURCE while acknowledging full coverage. No file reads or Unicode normalization. Apply all scope operations in order, including clear/restore and multiple end-of-line/zero-width operations; only actual text coverage produces positive-length ranges. Complete-line append reuses its checkpoint; the unfinished classified prefix may reparse. Ignored-tail-only append after saturation adds no parse. No completed-source cache on the daemon.

Keep the existing separate authorities: latest displayed text, acknowledged parser progress, historical matching-prefix display, execution uncertainty and source lifetime. A valid source result may advance parser state and populate semantic data even if the selected theme changed meanwhile. It cannot execute a command or make historical coverage current by assertion.

### 4.2 One rule resolver

Native themes and bounded Follow Pi declarations compile to one rule representation. Reuse Syntect selectors/MatchPower; use one property scorer with exact native strict-greater/tie ordering, inheritance and explicit font replacement. Test against `RangedHighlightIterator`, not solely `style_mod_for_stack`, whose equal-score path differs.

Represent RGB/index/terminal-default, client palette binding and caller-inherit explicitly; preserve bold/italic/underline/faint and native resets. No sentinel colors, private upstream flag bits or JavaScript reimplementation of the Syntect selector engine. Follow Pi declarations reference generic client slots rather than a daemon enum of Pi UI tokens. Markdown mappings include nested headings/links/code/quotes/lists/strong/emphasis, not just innermost scope names. Unknown scopes use the selected theme's default, never invented semantic certainty.

Follow Pi bindings are sampled through public Pi APIs once per palette revision. Palette-only Pi color changes rebind locally without parsing or scope matching. Native rules/defaults never gain Pi bindings accidentally. New contexts request only missing styles outside render; identical contexts across useful cards share entries.

### 4.3 Complete card palette

One ready card-presentation generation couples its card palette and all needed syntax styles. Native mode forbids a role formatter falling back to ambient `theme.fg/bg/style` on a missing slot. A missing native secondary slot is derived from native data before publication; an incomplete result follows P2, not a catch-and-use-Pi path.

| Card region | Native input / derivation | Follow Pi input |
|---|---|---|
| Panel, blank cells, normal text, neutral/unclassified code | Native base background/foreground, including documented default semantics | Existing tool panel/output/title roles |
| Header, path/workdir/description, `$`, overflow and expansion hints | Native accent/comment/base-derived hierarchy with contrast checks | Existing title/dim/muted roles |
| Normal/error frame and footer, diagnostics/warnings | Available native invalid/changed/accent hints or native-base-derived distinguishable styles | Existing border/error/warning roles |
| Bash stdout/stderr and `<system-reminder>` | Native foreground and native-derived secondary/muted foreground; reminder is not warning | Existing output and muted roles |
| Context source and line numbers | Native base + gutter settings, otherwise native-derived gutter/text | Existing panel/dim roles |
| `+/-`, removed/added code and gutter backgrounds | Native `markup.inserted`/`markup.deleted` hints when genuinely defined; derive missing restrained surfaces from native colors | Existing Pi-based diff palette algorithm |
| Inline diagnostics, omissions, empty split halves, padding | Same complete palette, including restored background after SGR resets | Existing corresponding Pi roles |

Use native `ThemeSettings` values such as foreground/background/gutter/gutter_foreground/accent/guide/line_highlight where suitable. Scope-derived diff hints need proof of a matching rule/property; inheriting the generic default is not proof of an authored green/red diff style. Do not require semantic colors to be literally red/green when the selected theme uses other accents.

Reuse the current bounded perceptual color/contrast machinery as appropriate, but change its **input and foreground constraints**: compare against the native colors actually painted, not Pi syntax roles. Do not alter native syntax foregrounds just to satisfy a threshold. When no readable tint can be derived, use the native neutral background. Record exact/derived/terminal-dependent provenance; test actual quantized RGB. Theme-relative contrast non-regression and distinguishability are requirements; universal WCAG compliance of arbitrary user themes is not promised.

Only custom Bash/edit/write card interiors participate. Exterior margins, Pi menus/status/footer/editor, user/queued cards, ordinary summaries and native-delegated/foreign renderers remain Pi-owned. Do not intercept tool output or change terminal defaults to simulate a card palette. A Pi theme or OSC report change must not invalidate a fixed concrete native palette; an intentional indexed/default-dependent theme is handled under P2.

### 4.4 Computation placement and flat rendering

The operator requires keeping Pi's shared Node event loop responsive, not merely moving CPU between languages. Use the following boundary; account for IPC, decoding and allocations as well as Rust execution time.

| Work | Owner | Benefit / constraint |
|---|---|---|
| Parsing, ordered scope operations, context generation and native selector/property matching | Occipital | No Syntect hierarchy/matcher runs in the UI process. Resolve the full stack before emitting flat context-to-style mappings. |
| Reply-local context front coding, unique style-expression table and indices | Occipital | Remove repeated parent paths and identical expressions before transport. Replies remain self-contained; no synchronized persistent dictionary. |
| Complete Syntect card-palette derivation, theme hints and full native-ink contrast checks | Occipital | Native theme size/rule diversity cannot turn into a main-thread palette search. Cache by immutable native definition/derivation identity; same bounded data-job authority as style resolution. |
| Public Pi-role sampling, binding materialization and Follow Pi UI adapter | tidy-ui, once per local palette generation | The current public Pi Theme exists only here. The bounded existing Pi diff-palette calculation uses its limited roles; moving it would create theme-change IPC and break daemon-unavailable Follow Pi. This is an input adapter, not a second scope matcher. |
| Transactional response validation, accounted descriptor interning and style cache ownership | tidy-ui, outside render | A producer cannot validate its own reply on behalf of a consumer. Bound/decode/materialize once; do not interpret scope meaning or traverse descriptors while painting/reflowing. |
| Logical tool presentation, glyph measurement, width reflow and final ANSI painting | tidy-ui, cached independently | Pi provides terminal geometry and glyph behavior; moving final strings/geometry to the daemon would require text/width-dependent IPC, duplicate fallback or an incompatible width implementation. Theme changes reuse geometry; reflow reuses flat semantics/styles. |

The painter consumes flat text ranges → context IDs → indexed styles. Full context descriptors are retained only as compact recoloring/restart input; neither scopes nor style rules are evaluated in a render. A new uncached native theme/rule definition can require one or more bounded missing-style requests. Already retained styles, preview rollback and unchanged-rule Pi binding changes must not. Do not precompute every native theme eagerly: it expands source-startup CPU/payload and competes with useful visible work.

Engineering gates compare native palette preparation and bounded Pi-adapter work separately, plus client decode/materialization and event-loop delay. A Rust implementation alone is not performance proof. Keep the existing limited Pi palette helper as the local adapter; do not introduce WASM/addons, a second matcher or a worker framework merely to deduplicate a small color-math kernel. Native/Follow-Pi adapters must feed the same final palette/style painter and share property/contrast invariants.

### 4.5 Color-free geometry and caches

Keep four named invalidation identities, not one theme/source generation:

1. Semantic source basis: text/grammar/coverage.
2. Rule resolution: grammar vocabulary + contexts + theme/rule fingerprint.
3. Card palette: native definition or Pi binding generation + derivation revision.
4. Layout: source/display revision + width/padding/tab/context/pane geometry.

Final ANSI rows additionally depend on actual displayed palette/style generation. Theme changes reuse logical diff preparation, pairings, glyph measurements and line breaks. Width changes redo local reflow/pane geometry/paint, not parsing or style matching. Height-only clipping selects retained rows where possible. Original tabs retain column-dependent stops; CJK, combining/ZWJ clusters and wide-glyph substitution retain current geometry and first-scalar style ownership.

**Operator-approved width ownership:** never rely on Pi's shared `visibleWidth()` cache to retain useful measurements. The inspected Pi 1.0/1.3 implementation has a 512-entry FIFO; repeated traversal of 513 Unicode strings can miss on every call. Keep reusable width results with the prepared text/geometry owner, including reuse across repaint, theme changes and terminal resize. Initial measurement may use a short-lived, funded duplicate-grapheme memo; do not introduce another global string cache or remeasure unchanged prefixes. Invoke the public Pi API to preserve its terminal-width semantics, reserving controlled measurement scratch before potentially allocating calls. Strings retained by Pi's own shared cache are explicitly outside tidy-ui's logical budget; our own source, measurement, layout and temporary storage retain their existing accounting/lifetime requirements. Do not inspect, patch or flush Pi's private cache.

Do not retain a JS object per glyph or lay out undisplayed omitted diff text. Do not move live transcript rows into a new small LRU: preserve current latest-layout weak ownership and existing source-retention accounting. Geometry references a validated weak semantic-basis handle, not uncharged strong range/context arrays. Eviction invalidates that dependency; detached cached ANSI rows may remain displayable without pinning the semantic payload. Stale arena IDs can never paint through surviving geometry. Zero-parser theme/resize guarantees apply to retained in-budget semantic/layout data; genuine source eviction is an explicit later cold-demand case, not hidden reparse on every resize.

## 5. Protocol contract to freeze before implementation

Use the implemented application version/capability JSON v3 / `syntax-highlight/v3`; retain codec isolation, framing and public transports. Do not ship dual v2/v3 painters/resolvers to avoid a release decision. Reject incompatible shared candidates and follow existing exact-owned selection; never downgrade another user's module or alter immutable published artifacts.

| Operation | Required identity/data | Outcome and authority |
|---|---|---|
| `describe` | Version/capabilities; assets/parser/vocabulary identity; limits; catalogue IDs/fingerprints; resolver/palette schema revision | Bounded metadata only; no source or arbitrary palette-resolution payload in the control lane |
| `themes.refresh` | Explicit existing control | Validated catalogue update; no parser/source generation reset |
| Finite `highlight`, `stream.open` | Source key/incarnation/version, syntax hint, text; **no selected theme** | Source coverage/contexts, parser revision, finite completion or owned lease |
| `stream.append`, `stream.close` | Exact existing lease/generation/base revision/byte authority and delta/finalization | Same acknowledgements/cleanup guarantees, now theme-independent |
| `styles.resolve` | Native ID+expected definition fingerprint **or** bounded structured Follow Pi rules; vocabulary fingerprint; unique needed context descriptors | Typed context-to-style expressions and native card-palette inputs, exact rule fingerprint; **no source text or source-execution proof** |

Cold source or newly encountered contexts can require a source response followed by style resolution. This extra round trip is a known performance risk, not an assumed optimization; E3 must compare it with the current native path before the schema is frozen. A theme hint/composite response is not silently added to fix failed measurements.

A source replacement chunk carries only referenced full contexts with **reply-local IDs**, then positive UTF-8-length/context pairs and exact replace/commit/end boundaries. Encode each ordered context relative to the previous one as `[commonPrefixLength, ...suffixScopeIDs]`; the first prefix is zero and a parsed-empty context remains a positive entry. This only compresses descriptors: it never reduces scope detail. Style requests use the same self-contained descriptor codec, and replies factor exact duplicate style expressions into one table with a flat per-context style index. Check row/header costs, total expanded words/depth/bytes and resulting style/index allocations before expansion, not just compact payload bytes; even an empty context owns a charged record. The client validates the whole response and interns equivalent contexts. No persistent synchronized server/client dictionary or immortal global Map is required. Style requests are self-contained; compiled-rule caches are an optimization, not correctness state.

Portable scope/prefix identifiers come from a deterministic trusted vocabulary tied to actual grammar assets, not process-local Syntect intern numbers. Follow Pi selector paths/exclusions reference trusted entries. Arbitrary request text must not reach `Scope::new`: that repository is process-global and failed requests cannot undo atom allocation. Compatible restarted providers can recolor retained scopes without parsing text; incompatible vocabularies are explicit compatibility failures, never silently rebound IDs.

**Operator-accepted one-shot and volume boundary:** keep finite admitted sources one-shot, without a chunk-feeding mode, extra transmitted-prefix versions/leases, worker or binary carrier. The subsequently approved [volume policy](syntax-highlighting-spec.md#highlighting-volume-policy) explicitly limits classifier coverage to a scalar-safe prefix and DATA envelopes to 512 KiB while preserving full display text. An early 10 MiB prototype observed roughly 192 ms of synchronous Node22 decoding for a roughly 22 MB semantic reply versus 193 ms for v2; those historical observations are not the current bounded producer's default reply size or latency. Oversized raw sources now exercise admission/refusal and release rather than successful unrestricted parsing. Whole-card display preparation/geometry remains outside classification protection, with no fast huge-card promise. Evaluate responsiveness on representative source/card/history/append/theme/resize workloads. Cooperative work cannot interrupt `JSON.parse`, and Rust speed alone is not UI proof.

Freeze before consumers are changed: operation-specific fields/error codes, definitions-before-use, dictionary/range coverage validation, color/attribute encoding, all fingerprints, empty/unclassified values, duplicate/unknown ID behavior, selector defaults/ties, refresh/restart semantics, limits, fault execution meaning and JSON vectors. The accepted contract and shared vectors live in `protocol/syntax-v3/`; they define the implemented v3 fields and allocation/ownership rules. Subsequent public delivery remains the separate R1 gate.

Validation is allocation-atomic for a complete batch. Check scalar UTF-8 boundaries, exact finite coverage, expected source identity and byte lengths before retained materialization. Arena IDs carry an incarnation and cannot be rebound while referenced; release must not create an indefinitely growing sparse array. Definition data, reference sets, style tables, layouts and in-flight encoded buffers all need lifetime/accounting evidence.

## 6. Scheduling, faults and transitions

- Keep one desired palette generation and the existing chronological weak LIFO registry. Style work may serve several owners, but does not introduce another owner/text queue, numeric priorities or history sweep. Share identical live context/rule resolutions.
- Source parsing and style resolution use the same at-most-two physical client-job/byte admission family; style CPU work belongs on the bounded data path, not the small wait-only catalogue lane. Bound/yield context matching on the native scheduler and preserve per-route fairness. Freeze the exact operation accounting at E3.
- A successful parse remains useful through theme churn. A stale style answer may settle its physical reservation, but cannot publish a canceled preview or overwrite a newer generation. Already-dispatched work settles normally; cancellations do not release capacity by assumption.
- A ready palette transition is atomic **per card**, including every edit segment, both panes, frame, footer and neutral appended glyphs. Different cards may update progressively newest-first; do not impose ordered completion or hide unrelated Pi frames.
- Recolor frozen retained contexts without parsing/reopening. Explicitly paused/zero-width cards retain display but admit neither SOURCE nor STYLE and cannot publish held STYLE into the card until a new useful visit. Physical settlement and accounted style caching remain valid, so resume may reuse a settled result without another request. Removal/Off/disposal releases the relevant semantic/palette references, including pending work; late callbacks cannot revive them. Pin an old ready palette only while live display actually needs it; no unbounded theme history.
- Palette errors, cache hits, catalogue responses and resolver-only success do not clear source uncertainty, authorize another parser, advance source revisions or reset the owned-helper crash budget. Only existing validated useful source work may do the latter. A transport loss still affects outstanding source jobs according to their own evidence.
- Preserve initial readiness/reset recovery, bounded owned restart/shared-return policy, route isolation and wait-only metadata semantics. Actual parser-state loss may require a current-source restart; **theme change alone may not**. A restarted compatible daemon can restore missing styles from retained contexts alone.
- Preserve menu preview/Enter/Esc/external-sync behavior, selected vs effective identity, explicit refresh, stable native selection across Pi theme changes and saved-settings schema. Unavailable/native-Off behavior follows P1–P2, not a new quiet fallback. No extra provider acquisition from merely inspecting a disabled menu.
