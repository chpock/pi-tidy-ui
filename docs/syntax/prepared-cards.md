# Prepared cards, geometry and painting

`CardSources` connects an eligible host component to the asynchronous source/style controller and one common literal-style renderer. Full display text, admitted classification text, measured geometry and ready paint are separate representations. The [rendering chapter](../rendering.md) explains common text units; the [source/style chapter](work.md) owns scheduling and fallback permission.

Presentation consumes the existing `CardSources` instance through the per-card `CardPreparationPort` declared in `src/presentation/card-preparation.ts`. Its cold requests use the single logical model in `src/cards/display-input.ts`; scoped visits expose only the current prepared display and paint. This consumer interface adds no runtime wrapper or ownership authority. `CardSources` itself consumes the card-facing and source/Pi capabilities from `src/highlighting/source-ports.ts`, plus narrow current metadata; it does not depend on the application client's implementation. Those capabilities reference one `SourceExecution`; its private `StylePublication` owns semantic display/group validity, not `CardSources` construction or compiled card paint. Escaped semantic readers keep the same weak root identity and reach publication only during a synchronous root-owned call. Registering or queuing a preparation enters that owner's private chronological registry, not a card-owned scheduler. Borrowed display readers and operation-scoped geometry funding preserve their existing validity and release boundaries.

`src/presentation/tool-preparation.ts` owns the presentation-side cold observation: source/service revisions, fixed producer-reader currentness, useful/pause/freeze decisions, preview-turn transitions and coalesced weak palette refresh. It passes the unchanged logical request to the existing preparation owner and rechecks the current observation after synchronous admission. The refresh target is the installed adapter's narrow callback, not a captured component or another source queue. Before reading source/detail inputs it checks readonly execution activity independently of Native On/Off. Original SDK updates still run while stopped. Per-owner metadata distinguishes a deferred Bash update that may change its full layout from an ordinary deferred refresh, without retaining new payloads or discarding a funded prior display. A stopped argument notification compares the previous and current top-level argument values without building a source or service representation. Replaying those values, in the same record or a new one, does not make the paid layout stale or clear an already deferred result or other update. A queued refresh that finds inactive work preserves the pending observation rather than preparing. The first positive, attached visible frame after return schedules the same weak refresh for current file, Bash or pending/error-detail data; warm reflected frames schedule nothing. A deferred Bash update that may change the display cannot borrow the old full layout, so that frame shows the compact summary. Acceptance of the deferred Bash display invalidates the owner and requests a frame even if the palette and command syntax did not change. Completing deferred pending/error details similarly invalidates that owner's rows, because the first return frame may already have cached a fallback with the same SDK identity. Host capture and application palette acquisition remain supplied capabilities.

## The card record separates preparation from usefulness

`CardSources` in `src/syntax/cards.ts` is the only writer of the accepted card. It stores state in a weak map keyed by the host component. The registry ticket holds weak owner/state/consumer references, source keys and detached cleanup obligations. The source controller can schedule the ticket without retaining the component or a duplicate source-text queue.

`updateDisplay` is the cold lifecycle boundary: it prepares what the first frame will need. It rejects inactive execution before constructing a new display, registers the owner before heavy work, obtains geometry funding, builds the replacement display and measurements, and adopts them only if execution is still active and the owner and mutation identity still match. Palette-input and paint acceptance use the same readonly activity projection. Stopping work does not remove ownership of the last funded display or invalidate its retained read capability.

`src/syntax/card-display.ts` decides display and geometry reuse and constructs one provisional Bash or FILE display. It reads prior display, revisions and logical file data; it receives no registration, palette, paint, host or source-work capability. The common builders in `src/cards/bash-preparation.ts` and `file-preparation.ts` take logical values, prior immutable regions and synchronous `CardMeasurements`. File service construction borrows diagnostic/note methods; row construction separately projects context and computes source coordinates. Prepared values and the flat-range reader signature belong to `src/rendering/card-values.ts`.

A synchronous build owns its new measurement receipts and any pending numeric append. A later service failure cannot lose the append rollback handle. Only a complete build can transfer its own measurements, and `CardSources` first rechecks active execution, owner and mutation. The transfer commits any pending append, preserves reused measurements and releases only obsolete measurements; it cannot inspect palette or paint. Unaccepted construction releases its new data whether a grant is refused or a reader throws. The descriptor's operation hold outlives palette funding and notifications, independently of the ticket's accepted hold. A reentrant winner owns its own data; rejection after palette reconciliation does not undo text already accepted and read. Builders retain no callbacks or staging wrapper in the display.

`useful` is a different operation. It marks a prepared revision as worth processing and queues the existing ticket. It does not normalize the source or classify it on the render stack. `prepare`, later invoked through the controller’s registry, constructs source demands and reconciles styles/fallback. A paused owner may retain its last complete paint while a different native group is waiting, but that retention guard requires existing paint. After full-display discard, a retained native SOURCE/STYLE group is not a retained card presentation: renewed admission must compile the missing paint. An accepted, visible successful file view remains useful while its local paint is pending, even if that temporary layout has no frame. Native Off can retire the group behind prior paint; pausing merely because that first layout is unframed would withdraw the very preparation needed to restore the selected neutral presentation. Local publication requests the recovery frame through the existing owner notice. Hidden/detached, zero-width, native-layout and unsuccessful views keep their existing pause/admission guards; usefulness never bypasses SOURCE authority.

An attached file first encountered without an accepted display queues the adapter's existing coalesced weak palette refresh rather than calling `updateDisplay` during rendering or predecessor measurement. Prepared file views also use that refresh for observed palette/color-mode drift. Before admission, the callback rechecks its token, current owner/input, attachment, visibility, selected view and positive usable width. Collapse, hiding, detachment or disposal cannot make an obsolete queued observation prepare an old body. Source/style processing still uses the existing controller ticket; this adds no scheduler or pending-source collection.

An unattempted display is not a funding refusal: its interim frame shows the argument summary without claiming a memory limit. Actual refusal keeps the owned summary with a bounded limitation. Admission or the first transition into refusal invalidates only that owner's presentation and requests a frame; unchanged refusal does not request another. A later ordinary visible frame may retry once through the same coalesced refresh, allowing recovery in the same expansion without a self-sustaining repaint loop.

Logical acceptance does not prove that initial palette input or compiled paint was funded. When a supported file view has accepted text/measurements but no usable paint, retain that data and retry only palette reconciliation and paint at the same display revision. This covers expanded read and supported write/edit previews, without another descriptor-construction grant, measurement or SOURCE/STYLE request. The first usable paint requests a recovery frame. Preserve the refusal episode until a layout is actually accepted: a subsequent geometry denial must not request another status frame. A new admission starts a new episode; unsupported full write/edit views keep their explicit native fallback.

An optional `CardSourceHost.preparation(owner, receipt)` observation reports accepted input (`updated`) and the end of the real preparation (`prepared`), after source evaluation and paint application attempts. The opaque `update` identity couples the concrete owner ticket, supplied source revision and selected local palette identity; output-only changes reuse that source-work identity. The completion includes actual paint publication, per-source outcomes, a count of source demands refused by the existing bookkeeping-admission branch, and the paint operation's `applied` result. That boolean comes from the existing compilation/adoption branch (including an already matching paint token), not a separate readiness predicate; refused funding cannot impersonate successful application merely because older neutral paint remains. Successful Pi classification is synchronous within this operation; a `waiting` native outcome is not completion of SOURCE/STYLE RPC work. Replaced or retired preparations do not acknowledge the obsolete update. `TidyUiOptions.cardPreparation` and `TidyUiRuntimeOptions.cardPreparation` forward these detached receipts with the tool-call ID/name, not the component. The hook observes existing work only, adds no scheduling or readiness store, and its exceptions cannot disrupt card ownership.

The record uses several existing identities:

| Identity | What changes it |
|---|---|
| `revision` | The overall supplied display revision |
| `sourceRevision` | The source-bearing part of the supplied input |
| `serviceRevision` | Output, diagnostics or other service presentation |
| `version` | Local source version advanced when the source revision changes |
| `processed` | Source revision last evaluated by useful preparation |
| `preparedTheme` / `preparedPalette` | Desired theme/public Pi input revision last considered, whether or not funding/admission produced a replacement |
| `mutation` | Validity of an in-progress synchronous preparation or visit |
| Display `geometryStamp` | Prepared regions/measurements actually changed |
| Paint publication / `paintStamp` | New paint ownership versus changed visible effect |

These are not interchangeable counters. `preparedPalette` records the desired input considered, not proof that a matching lease exists; `inputMatches` is the separate lease-validity check. A denied replacement acquisition keeps the prior coherent paint and does not cause repeated preparation on warm visits or unrelated metadata scans. A later source or effective-palette revision can try again. Initial acquisition without any usable paint instead uses the finite same-revision visible-frame retry described above. Same-source file updates retain their descriptor charge and row measurements; new service regions are funded separately before adoption. An output-only Bash update can change service regions while reusing command measurement. Equal-text completion can require source-authority work without changing geometry. A new reader publication can have the same visible paint. Ready Pi effects identity includes the source-slot version: if a mode transition promotes the same text to a new version while its Pi projection is not ready, an already retained neutral scene is repainted when that version's matching projection becomes available, without repeating classification or SOURCE work.

File readers expose source identity separately from service notes. The file-service builder asks the current reader's scoped metadata capability for `note(view)` during a service update, so a note can change while prepared file rows are reused when `sourceRevision` is unchanged. This is conditional: current AFT file source keys still include `truncated` and `noOp`, so changes to those fields can advance the source revision and trigger source preparation. When a new reader replaces an old one with unchanged semantic-source/service revisions, `CardSources` adopts it at the same revision while reusing the display and rows; replacing the borrowed reader also releases its superseded argument/result references.

## Prepare the full display, classify an explicit prefix

For Bash, display preparation obtains the complete normalized command and separately prepares description, output, reminder and footer regions. Missing command/directory data or unavailable prepared paint/layout selects the existing compact argument summary, not native rows or a stale previous display. This bounded interim view does not alter input/result data or add preparation retries. Unchanged regions reuse their measurements. An appended command can use transactional measurement append; a rewrite measures the replacement. Collapsed service sections prepare only the rows needed by their bounded previews while retaining their complete source strings.

For file cards, the [producer adapter](../tool-adapters.md) supplies the validated logical view inside the existing construction grant. Its deferred reader captures the observed arguments/result and phase facts rather than consulting a later mutable host component. `CardSources` constructs visible row descriptors and their coordinates in the underlying logical source fragments. It walks the prepared supplied lines to compute old/next coordinates even when some context rows are not displayed. A file input may select a separate `preview` or `full` view; that mode participates in the source revision, so exposing a previously omitted suffix cannot reuse the bounded preview's syntax classification. Result-title validation is separate and can inspect the saved metadata past the preview bound. Only complete rows from the capped prefix enter preview fragments, descriptors, measurement or syntax highlighting. An accepted full-to-preview transition replaces the full display, measurements and compiled paint with the bounded view, releases their receipts, and removes superseded source keys during preparation; it does not merely clip or pause the old full representation. The owner and current ticket remain live. If the smaller replacement cannot be funded, `CardSources` releases the old full display, compiled paint and measurement receipts before returning refusal, but retains the card ticket, segment keys and controller execution evidence. The host then uses its bounded summary with an explicit limitation rather than invoking Pi's full file renderer. A later retry reconstructs the selected view against the same ticket; stale replies cannot restore the discarded display. `filePreparationOutcome` reports only an already accepted file-display result and does not require PAINT publication: accepted unsupported full metadata can keep its exact native fallback even when palette preparation is unavailable. A refused or not-yet-accepted preparation has no such outcome, so it remains owned instead of inferring that native fallback is safe; only an actual refusal adds a limitation message.

The validated edit/write result type is a call fact, not a source or paint revision. Full preparation can report it once the producer has validated the saved data, even if measurement or paint is later refused. The presentation owner checks that the attempt and call are still current before adopting it. Preview preparation can reuse the label without retaining full rows; it cannot establish the label from an incomplete prefix. This does not change how `filePreparationOutcome` authorizes the existing native fallback.

Read uses this same file record only for its explicitly expanded successful result. Compact read is not a zero-row prepared preview: it has no result-body construction or classification demand. Expanded read prepares saved text parts as a plain code view, with the stock offset or a verified AFT numbered envelope as its row origin. The AFT prefix scan and decode run inside the existing construction grant, not in the compact or render path. Only verified source rows get source coordinates; unnumbered producer-tail rows remain visible neutral regions without classifier input. Its initial construction grant includes returned text and row descriptors before joining/measurement, rather than charging only its small path/argument envelope. The exact saved-text and producer-notice rules are in [read cards](../read-card-spec.md).

The host memoizes source primitives selected by the producer adapter between cold boundaries. Full read identity retains saved text values and decoder-controlling metadata without joining or validating the complete numbered block; object identity and part count alone cannot detect in-place changes. `updateArgs`, `updateResult` and `invalidate` refresh that snapshot synchronously before any re-entrant repaint; unchanged bounded identity keeps the same source token and ordinary render/resize frames do not clean, split or classify it again. Full mode also observes saved content that its parser may use as fallback and diagnostic text when those fields change in place. Image-result eligibility is invalidated at the same boundary, so a same-object write/edit text-to-image mutation returns to Pi's native path without per-frame rescanning. Read keeps its owned text view and separately borrows the host's current public image children; protocol/image rows do not enter this prepared text record.

A temporary detach during Pi's renderer clear/move sequence pauses an accepted file owner without discarding its prepared display or source snapshot. Same-turn reattachment reuses the retained state when inputs are unchanged and refreshes it against the same ticket when input changed while detached. A component that remains detached is retired by the host clear lifecycle; direct rendering during that interval delegates to Pi and does not create an extension card-layout cache entry. Attached ineligibility (for example a native override or a write/edit image result) still releases the owned file display.

The import-free logical file model lives in `src/cards/file-model.ts`; producer readers and shared preparation consume it directly. `src/cards/file-sources.ts` owns one topology-only `visitFileSegments` traversal for cold display coordinates and useful SOURCE joining. It emits the supplied row, side and global segment ordinal: all old-side segments precede all next-side segments, and rows absent from a side do not break its continuity. Ordinals are dense from zero and every segment contains at least one positioned row, including empty-text rows; the useful `FileSource[]` index therefore matches its cold descriptor key. The visitor constructs neither a retained segment graph nor joined text. The display consumer alone computes UTF-16/UTF-8 offsets; `fileSources` joins logical fragments only at useful preparation and does not encode display byte coordinates. Both consumers use the same `cardSourceKey` formatter from `src/cards/preparation.ts`; ticket allocation remains with the card owner. Sharing these rules does not eliminate the two necessary operations at their different lifecycle boundaries.

Continuity matters. A gap or nonconsecutive line position ends a source fragment. Old and next sides have independent fragments; a context row can have coordinates on both. Each descriptor records its fragment key, UTF-16 offset and UTF-8 byte offset. It does not invent missing file contents to join disjoint fragments. The exact saved-format rules remain in the [read](../read-card-spec.md), [edit](../edit-card-spec.md) and [write](../write-card-spec.md) chapters.

For a successful read/edit/write, shebang detection uses the original text of the numbered file line before terminal-control cleanup. Coordinate `1` is authoritative: `old=1` and `next=1` are independently inspected, a write's `next=1` is its first supplied line, and a read may inspect its first returned row only at returned offset1. A recognized hint is copied to every fragment of that side; if only one side is recognized, its hint is shared with the other side, while two recognized hints remain independent. No target-file read or hunk-position guess is involved. See the [complete shebang contract and allowlist](shebang-hints.md).

This identity also controls row painting. In split mode, removed rows and shared context on the left borrow the old source; added rows and shared context on the right borrow the next source. In unified mode, a shared context row is visible once and uses the next source. The side is selected from the displayed cell, not just the diff row kind. Consequently, different old/new shebangs can highlight the same shared text with their respective grammars in split view without duplicating it in unified view.

Useful preparation constructs one Bash demand or the file view’s source segments. Keys remain associated with the card ticket and segment order, and every segment belongs to the same controller group. That grouping does not turn all segments into one unbounded request; individual native work still obeys shared physical admission.

`requestSyntax` in `src/syntax/work.ts` selects the classified prefix before native observation or permitted Pi classification. The full prepared display remains separate. Slot identity distinguishes the Pi-classifier language from the optional explicit Occipital language selector, and also records source version, completion, palette and fallback mode. A file's path-derived Pi language remains available for fallback but is not sent as an explicit native selector; a recognized shebang may supply that selector instead. The controller owns the actual admitted source and its execution evidence. While execution is active and Native is enabled, useful preparation offers that bounded source before provider readiness, including completion changes that arrive while existing paint looks current. Admission is funded independently of RPC readiness: the existing execution owner retains the input and determines useful reconnection; card slots carry no deferred-provider/second-interest flag. Earlier SOURCE retention competes with Pi and presentation data under the same budget and keeps the existing Off/removal/eviction/GC boundaries.

An inactive request returns before source inspection or classification. If early native admission refuses while the provider is non-ready, eligible FILE Pi fallback still uses the existing work-status permission and its own funding. A ready-route native refusal preserves its existing return behavior. Failed admission is neither proof of native execution nor a current exact-source/display qualification; it cannot authorize duplicate Pi work past held/history/withdrawal barriers. An empty observation can update existing input but sustains no SOURCE RPC or acquisition need. Its local source exactness is not complete paint: eligible Pi empty-row preparation remains immediate, invokes no classifier and need not wait for native STYLE publication.

A cold file-display update may precede its useful SOURCE admission, so range readers independently require the current file version and matching basis. Once useful admission replaces an incompatible finite FILE source, its old canonical source/display generation is released rather than retained as a second historical FILE basis, even before the provider is ready. Current file text stays neutral until compatible syntax is ready; it never borrows old-file ranges. This does not change retained Bash-prefix history, equal-content aliases, same-source palette rollback or the card's atomic paint-publication rules.

Bash always requests neutral fallback, never Pi classification. A file can request Pi fallback only when its palette state permits it and the controller grants execution permission. A usable owned palette instead keeps missing syntax neutral in its own role. The complete classification and line policies are owned by [source work](work.md#highlighting-volume-policy).

## From semantic contexts to card paint

A source result provides semantic coverage, not an ANSI string. The controller’s STYLE path resolves missing contexts and materializes concrete roles/styles as described in [source and style work](work.md). `src/syntax/card-palette.ts` owns the consumer-wide requested selection, identity calculations, metadata and accepted STYLE binding revision. `CardSources` acquires and replaces each card's lease and checks its owner and input after acquisition, before writing either. Two live cards can keep different effective palettes during a bundled asset failure; there is still one consumer-wide installed STYLE selection.

`CardSources.refreshPaint` first chooses the needed group or lease and decides whether to keep the complete old paint. Otherwise it compiles under a separate grant and holds the predecessor through every callback. The root alone checks and installs the result.

Its paint token includes the accepted group publication, selected palette and matching Pi projections, not merely the requested choice. `src/syntax/card-coverage.ts` captures source byte ranges and indexed styles from the validated publication. Native style expressions keep their original binding slots and attribute masks so they can be bound to a new palette. Pi fallback ranges keep their literal colors, qualified by the source version and Pi palette. Both forms pay from the same budget before allocation. Neither owns a lease, a parser context or permission to classify. Capture holds one group borrow across all members. The borrow validates the complete group at entry and exit, not once per member.

`src/rendering/card-styles.ts` counts the accepted literals and structural roles, then funds and compiles their normal and diff-surface variants. Within that compilation, detached Occipital literals with the same concrete foreground, background and font attributes share one set of compiled variants, even when they came from different syntax contexts. Pi projections and structural roles retain their existing treatment. The temporary lookup is discarded before publication. This lets the painter join adjacent glyphs with the same style without comparing colors during render. The allowance is 2,560 policy bytes per enumerated style, before sharing. One grant pays for the complete compilation, with separate charges for the structural roles and the range lookup. Native Off releases the lookup and coverage after outstanding reads return; structural roles remain available even if replacement funding is refused. The ready structural roles supply the row backgrounds. Token styles cannot choose a different card surface.

Adoption rechecks owner, mutation, input and previous paint. It discards incomplete candidates and keeps the last compatible paint. A new publication can retain the old paint stamp when visible effects are equal. Acceptance installs the value before notifying the renderer. Predecessor and candidate charges overlap until each operation or borrow unwinds.

The accepted card owns its display ranges, not a live reader into the parser pool. Parser or Pi-projection eviction alone does not change the colors, request a frame for the unchanged card or start another classification. A new width can use the ranges to paint text that was not visible in the old rows. Explicit Native Off withdraws accepted native ranges even if a replacement palette cannot be funded. A changed file version never borrows historical ranges; a changed Bash command may use only its matching scalar prefix.

Source-key and group-ID notices are resolved through the existing ticket maps. They affect only still-owned records. Changed paint invalidates the relevant prepared component, and render requests are coalesced into a microtask. No transcript search is needed to discover which card belonged to a result.

## Measuring once and reflowing numbers

`src/rendering/measured-rows.ts` represents measurement as numeric glyph data. Each grapheme contributes its UTF-16 end, UTF-8 end, display width and flags such as tab/newline/whitespace. A temporary per-measurement memo avoids repeated width calls for identical graphemes during that measurement; it is discarded before returning. The retained measurement owns numeric storage, not a long-lived text-key memo.

Append preparation cannot assume that the old final grapheme remains complete. It remeasures that grapheme and the new suffix, stepping back farther when completing an isolated high surrogate could join the new scalar to the preceding grapheme. The candidate is checked before adoption. Commit transfers reusable capacity or adopts geometrically grown storage; failure preserves the old measurement.

File headings additionally record shared fragment-boundary/separator flags in that same glyph record; other source measurements do not perform this classification. The [shared fragment kernel](../rendering.md#shared-fragment-wrapping) is used by heading layout, inline height reflow and compact text adapters. It does not replace source/diff wrapping. A fragment-policy marker prevents using missing heading annotations as valid input.

Reflow consumes those stored widths and flags through separate Bash and file policies, sharing one packed span/row writer. Bash uses visual-column eight-cell tab stops and optional prompt cells; files use logical-line four-cell tab stops and their existing whitespace-boundary rules. Heading fragment reflow remains separate from both source policies. They produce numeric rows and spans for source glyphs, tabs, replacement glyphs and Bash prompt cells. It does not resample the theme, invoke a classifier or call the width calculator again. Measurements retain their independent lifetime while layouts refer to their valid basis.

For a valid full file card, refusal of a later width-dependent layout geometry grant drops only the failed scene. The already-funded logical display and numeric measurements remain attached to the same owner so ordinary frames can retry geometry without repeating file-source preparation or measurement. A refusal before the logical display is accepted still releases partial construction and retries cold.

The common [rendering pipeline](../rendering.md) owns scene/frame composition. At this boundary, the useful distinction is that new width needs a new arrangement of existing measurements, whereas new source text can require new measurements. A color-only change needs neither.

File paint identity also includes whether each retained source slot is eligible for the current card version. A mode change can advance the card version before preparation promotes otherwise identical source slots; the interim neutral scene must be repainted when those slots become current, even when an owned palette has no Pi projection or the group paint stamp is unchanged. This is a local paint/layout refresh only: it does not itself request new SOURCE or STYLE work. Bash historical-prefix matching is unchanged.

## Reading the paid presentation

`src/syntax/card-read.ts` pins the accepted descriptor, ranges and compiled paint for a synchronous callback. It checks that the same owner and publication still apply before accepting the caller's result. It does not read the parser pool, borrow a palette input, request a grant or compile colors. Escaped accessors are cleared on normal and exceptional return; the cleanup ticket holds charges, not the display payload.

Publication checks complete FILE coverage, language and source version, including a validated alias for equal text. The reader rejects a retained file member if its version no longer matches the card. For Bash, preparation compares the accepted basis with the current command and supplies the matching prefix length. The same common painter maps the accepted style to the requested normal or diff surface.

## Monotonic painting

`paintFlat` in `src/rendering/flat-paint.ts` combines prepared row spans with ordered style ranges. It advances one row/span/glyph cursor as ranges arrive; it does not restart a source scan for each range.

Before a style interval, gaps paint with the neutral style. Within the interval, eligibility is tested at the glyph’s original first-scalar byte offset. A whole grapheme receives that chosen style, including when a validated historical prefix ends inside the grapheme. Prompt spans use their dedicated role; tab/replacement spans use their prepared cell widths. After the final style interval, the remaining glyphs are neutral.

The caller supplies the source-match proof and eligible byte count. The painter does not decide that old Bash text matches current text, or that a file’s classification belongs to its current version. Those decisions happen during preparation and publication.

Output allocation is funded while pieces and joined rows coexist. Each emitted piece encloses its style; final row strings become detached accounted output. An invalid range visitor or geometry lookup rejects the entire candidate and releases provisional pieces/rows. Frame composition consumes accepted paint under its separate [frame contract](../card-frame-spec.md).

## Pi fallback becomes the same kind of paint input

After `requestSyntax` obtains permission to call Pi, it passes the classifier to the stable Pi capability owned by `SourceExecution`. `PiFallbackCoordinator` in `src/highlighting/pi-fallback.ts` performs the funded capture, classification and projection transaction. The returned rows are treated as external data; the pure `preparePiFlat` conversion in `src/highlighting/pi-flat.ts` checks row sequence and visible text against the exact ticket text.

Every visible scalar must match. Row boundaries must correspond to source newlines. Malformed or unsupported escape sequences, changed text, missing rows or an invalid producer visit reject the whole candidate. The conversion does not normalize the classifier’s answer to make it fit.

Accepted foregrounds and font state become immutable literal styles and byte ranges. Background controls are parsed but do not replace the supplied card surface. Detailed font/color interpretation belongs to [Follow Pi](follow-pi.md) and the [color model](../color-model.md).

The result is staged and adopted by the coordinator into the existing root retention entry's `PiProjectionHolder` under the same logical-data budget; no second pool or accounting authority is introduced. Ticket, payload and callback-held charge lifetimes are described in [storage](storage.md#latest-text-acknowledged-basis-and-displayed-text). The original ANSI rows are released. Rendering then uses the common painter, not a second ANSI-row rendering branch. Since these styles contain literal colors rather than reversible semantic scopes, a changed effective fallback palette may require a newly permitted classification. Width changes do not.

## Following one owner through its lifecycle

Consider an eligible completed write card whose supplied file content is already prepared and whose provider is compatible.

1. **Installation/update:** `updateDisplay` creates the full logical file view, visible row coordinates and measurements. It records source and service revisions without waiting for native syntax.
2. **Useful visit:** `useful` queues the existing weak preparation ticket. `prepare` creates the finite source segment demands and updates the controller group.
3. **SOURCE/STYLE:** the controller admits source work, adopts validated semantic coverage, resolves missing styles and publishes one complete group. The card compiles that group and changes its paint stamp only if effects changed.
4. **Warm frame:** the caller uses retained geometry/paint identities and accepted row retention. No source observation or classification is performed merely to redraw the same state.
5. **Resize:** the same measurements are reflowed for the new usable width. Existing style readers paint that arrangement; SOURCE and STYLE identity are unchanged.
6. **Recolor:** desired selection changes through metadata. The controller reuses semantic scopes, requests only missing expressions/palette data or binds cached expressions locally. The card keeps its old complete paint until replacement is ready, then repaints without remeasuring or reflowing unchanged geometry.
7. **Removal:** `remove` deletes the weak-map association and releases the ticket. Unregistration removes its source group; cleanup receipts release measurements, descriptor storage, compiled paint and Pi leases. Late work can settle its physical liability but cannot republish into that owner.

Read starts this trace only on explicit expansion. Collapse discards its owned full display, measurements, compiled paint and syntax demand while the Pi component/result stay live; reopening prepares current saved data, not an old retained full body. Late results cannot revive the discarded presentation. Host-owned image data has a separate lifetime and is not released by this text operation.

For streaming Bash, step 1 repeats with current full command text. Output-only revisions reuse the command measurement. A useful active append schedules current source demand; equal-text finalization can still schedule authority work without rebuilding the command body.

Pause, freeze and restore change this trace differently. Pause retains the owner but stops new useful admission until resume. Freeze ends live source continuation while retaining the exact view eligible for recoloring and reflow. Removal ends ownership. A restored interrupted card is a new owner, not a resurrection of the frozen live parser.

On provider readiness, an eligible restored file with only exact Pi fallback can receive its first native SOURCE through the existing registry. It keeps fallback until its complete native group is ready. Older cards are lower priority, not permanently excluded. Paused, frozen, removed and refused owners retain their existing guards.

## Palette and geometry independence

Only syntax glyph color/attributes change; token backgrounds never replace structural row surfaces. The ready selected palette owns **all** card-interior roles: code/plain/unknown text, padding, numbers/gutters/signs, frames, errors, reminders and service/footer regions. Pi-colored edges are not an owned-palette fallback. Expanded failed read/write/edit details are a separate non-syntax [service panel](../read-card-spec.md#expanded-file-errors), like compact summaries: they use the active Pi UI theme and never acquire a prepared source/code palette. If a bundled owned asset is unusable, an explicit complete Follow Pi input is allowed.
