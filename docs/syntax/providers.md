# Provider selection, preferences and recovery

This chapter describes the extension client, not the daemon process. Construction, useful presentation attachment, provider publication and ready card paint are different boundaries. The [daemon runtime](../occipital/runtime.md) owns native threads/routes; [client requests](requests.md) owns correlation and physical settlement.

## Construction is not activation

The client is assembled before it is allowed to start a provider. `createSyntaxOptions` in `src/application/syntax-options.ts` captures the extension’s agent directory, current working directory and session identity and supplies native configuration to `createNativeAcquisition` in `src/occipital/acquisition.ts`. Application wiring also supplies a producer for the once-only weak UI-warning callback. Native acquisition invokes that producer synchronously only when constructing the local-development factory and retains only the resulting callback, not the producer or its context. Published construction does not read UI. Native acquisition owns platform/package/artifact selection and the existing factories; its interface receives primitive identity/configuration and callbacks, not `ExtensionContext`, settings or UI. Neither step launches Occipital. The captured session identity is metadata for a shared route; it is not a source-text store.

`SyntaxRuntime` in `src/application/syntax-runtime.ts` composes `SyntaxClient` from `src/application/syntax-client.ts` with the public Pi-input owner, then leaves the client disabled. The client owns the existing `SourceExecution` in `src/highlighting/source-execution.ts`; the runtime adds no second source owner. Construction allocates local bookkeeping, including the root's one private STYLE/publication collaborator, not a connection or helper process. That collaborator shares existing storage/provider/clock references and cannot acquire or restart a route. The runtime’s enabled preference and the client’s current eligibility are deliberately separate: an enabled preference cannot activate native work without an active presentation.

The client's `cardSource`, `sourceWork`, `sourceLifecycle`, `sourcePump` and `sourceStatistics` capabilities are typed views of that same execution instance, not wrapper services or independent state stores. Its separate stable `pi` capability is that execution owner's `PiFallbackCoordinator`, sharing its retention pool and bookkeeping authority without owning native execution evidence. The runtime exposes these capabilities without constructing per-visit wrappers, while using the lifecycle view for native activation, suspension and cleanup. Their shared source/job authority and private registry are described in [work boundaries](work.md#execution-and-registry-boundaries).

Attachment supplies that missing condition. `SyntaxRuntime.attach` stores a weak reference to the presentation and schedules a microtask. The microtask checks the live presentation again before enabling the client and starting it. If the presentation disappeared or became inactive between attachment and delivery, startup does not proceed. Application preference readiness precedes menu actions. The runtime's `prepareThemes` can await already-supplied choice data, but cannot read settings or bypass this attachment check.

`ApplicationPreferences` owns initial settings reads, confirmed intent, watch publication and write/cancellation policy. Application wiring supplies `initialTheme` as a decided choice or the actual already-started choice Promise; neither syntax options, runtime nor client receives the settings store or a save callback. `SyntaxClient.start` joins preparation of that input with broker startup. Native source admission remains disabled while supplied choice data is pending; accepting it does not establish that a compatible provider exists. Cards observe both conditions through cached metadata, without constructing source demands. The ordinary extension factory awaits its single initial read before constructing the native client, so that path supplies a decided value without another I/O gap.

The callback path is also separated from the work path. Provider and source notifications reach the runtime through module-scoped weak callbacks. The runtime forwards them only to its current active presentation. Source notifications contain source keys and card-group IDs; they do not carry a captured card or a second copy of its text. The scheduled notification reads current state rather than replaying an old provider snapshot. Explicit Native Off notifies the active presentation after synchronous source retirement, before a subsequent On can hide the withdrawal. This retires card-owned native colors without changing physical request settlement.

## Observing client completion

`SyntaxClient.whenSettled(): Promise<boolean>` passively composes the [source-controller boundary](work.md#observing-completed-work) with preparation of already-supplied initial choice data, startup, provider work and delivered client presentation notifications. The client follows those actual producer continuations rather than taking a one-time snapshot of RPC Promises.

The client shares one pending Promise among callers and retains at most four fixed producer-Promise identities (source, provider, initial-choice preparation and startup). Producer slots belong to the owner, not to a cancellable observation: an unchanged pending Promise receives only one weak observer even across repeated cancellation/resume. A producer callback checks its exact current Promise identity before notifying the current observation. Finishing/cancelling clears the pending completion; slots are replaced with their producers and cleared on disposal. They store no cards, source bodies or history. Native Off, suspension and disposal return `false` to the current observer, never a successful result for its replacement. Native Off does not prevent a new observer from awaiting queued local preparation.

The broker's corresponding `whenSettled()` observes its current operation, requests, an already-running shared-return probe and actual availability delivery. A scheduled future recovery tick is excluded: observation neither advances its clock nor starts startup, recovery or metadata acquisition. Finishing a bounded failed operation counts as finished work, not proof of provider availability, parser success or physical shared computation stopping. Once a compatible route is ready, an admitted useful native target remains owed even when its Pi fallback paint is already ready; current native credit waits and subsequent SOURCE/STYLE work belong to completion. On a terminal or temporary readiness loss, the source controller can drain permitted local/fallback work after withdrawing obsolete native credit interest; a still-running reconnect/factory/description operation continues to hold this client/provider boundary. A later ready publication and work admitted by its actual delivery are included normally. Changed availability metadata remains eligible for ordinary coalesced delivery while an acquisition is pending; a held recovery must not hide its transition until it finishes. Pending-operation admission and completion guards remain independent from that delivery, and settlement still requests the post-guard-clear execution opportunity even when displayed metadata did not change. The existing broker `onChange` is this combined opportunity port, not a promise of one callback per acquisition. Publication and settlement may coalesce; every delivered snapshot must be current, and ordinary warm snapshot/stat/repeated-start reads create neither notices nor acquisition. An unavailable snapshot exposes `recoveryAt` only once the current acquisition guard and other blocking producers are clear. No future recovery tick is advanced or created by observation. Existing request/execution evidence remains authoritative.

This boundary does not wait for terminal rendering, start unrequested work or save settings. Callers still need the tested action's own completion, its normal rendering boundary and separate success/error assertions. Missing completion remains a failure, not a timing-based fallback.

## From a factory result to a published provider

A **candidate** is a transport that has been created but has not yet become the client’s provider. A **published provider** is a candidate whose descriptor has passed broker validation and whose lifetime is now represented by a broker generation.

For shared service, `connectionCandidates` in `src/occipital/discovery.ts` returns a narrow ordered list rather than scanning ports, processes or directories. Explicit selection and `SUBC_CONNECTION_FILE` are exclusive. Otherwise the runtime-directory, home-directory and temporary-directory candidates follow the public discovery ordering, with duplicates removed.

`createSharedFactory` in `src/occipital/factories.ts` tries those candidates sequentially within one absolute attempt budget. `SharedTransport` first loads the public SDK, connects, resolves the syntax capability and opens its internal-service route. Its `ready` promise means that route initialization succeeded—not that the Occipital descriptor is compatible.

The factory therefore hands each ready route to the broker’s negotiation callback. `ProviderBroker.describeCandidate` performs the source-free descriptor request and validation. A rejected candidate is closed before trying another within the same budget. An accepted descriptor is bound to that exact transport; returning another transport cannot reuse it. An already-negotiated candidate does not receive a duplicate descriptor request.

This division keeps compatibility decisions in one place while allowing discovery to continue past a reachable but incompatible service. Candidate creation, descriptor negotiation and provider publication are three separate steps. None proves that source parsing has started.

The broker uses an **epoch**, a monotonically changing local attempt identity, to reject asynchronous results belonging to an abandoned selection or recovery operation. Publication establishes a separate provider generation. Requests and lifetime notifications carry that generation so an old connection cannot retire, debit or publish through its replacement.

Factory cancellation is scoped to acquisition. Once a transport is transferred, the completed factory removes its abort observers. Subsequent lifetime belongs to the broker and transport, not to the old acquisition signal. Late or unused candidates are closed instead of being silently adopted.

## Acquiring and owning the local process

The development/release choice determines which acquisition function is available; it does not replace runtime verification. The release preparation rules remain in [release delivery](../releases.md#extension-delivery).

For an optional installed payload, bootstrap reads bounded package metadata and checks the expected package name and daemon version before deriving its executable path. `acquireNative` in `src/occipital/native.ts` then verifies usable executable access and the declared bytes. An unusable installed payload can fall through to exact cache/download delivery; the installed package is not repaired or rewritten.

Downloaded release executables live at `<agentDir>/extensions/pi-tidy-ui/occipital/<version>/<target>/occipital` (`occipital.exe` on Windows), beside the extension's `config.json`. `<agentDir>` comes from Pi's public `getAgentDir()`, including `PI_CODING_AGENT_DIR`; the default is `~/.pi/agent`. This is pi-tidy-ui's storage convention, not a Pi-wide artifact-cache contract. The directory is independent of the installed extension's source/package location and the development-only colocated executable. Exact verified downloads are reused across sessions and extension installations sharing that agent directory. The former `<agentDir>/cache/occipital` location is no longer read or written; existing files are not migrated or deleted, so a release absent from the new location needs one new download when no installed payload is usable.

### Downloaded-release retention

Every successful exact acquisition—verified installed payload, warm download or new download—awaits one best-effort cleanup of the downloaded-storage root before returning. Keep the caller's exact version directory, including all its targets, and remove other real directories whose names satisfy the same bounded version identity. Unknown entries, ordinary files and directory symlinks are not swept. If another spelling differs only by letter case, compare directory filesystem identities before removal: a case-insensitive alias of the selected directory is retained, while distinct case-sensitive versions remain separate identities. Failed identity checks conservatively leave that entry for a later attempt. Installed npm payloads, the development-only executable, settings and the former cache root remain outside this cleanup. Failed verification, interrupted downloads and cancellation before successful acquisition do not trigger pruning.

The retained version is the current caller's declared release, not the greatest version number: an older extension or rollback can download its older exact release again and prune newer downloads. Cleanup does not alter executable selection. Enumeration/removal failures are ignored independently; a locked Windows executable or inaccessible directory can remain, while cleanup continues for other versions. The next successful acquisition, including a warm or installed hit, retries leftovers. There are no process inventories, usage records, locks, cleanup timers, background sweeps or automatic retry loops. Ordinary removal has no configured retries; its filesystem work shares the existing acquisition deadline.

This is disposable storage, not proof that another process no longer uses a version. On Linux/macOS a running helper normally remains usable after its executable pathname is removed; occupied disk blocks can remain until it exits. Windows may refuse deletion until the executable is no longer mapped. Concurrent different-version sessions can remove each other's cached or in-progress files, so retention is not a hard one-directory guarantee. A missing release is downloaded on the next acquisition, requiring network access. If deletion races an acquisition or the interval between verification and process launch, the current startup can fail: existing provider handling does not guarantee an immediate reacquisition/relaunch. Explicit native re-enablement or a new session may be needed. This occasional loss of native availability is an accepted retention-only trade-off, not an additional startup-recovery mechanism.

Relative paths are anchored before asynchronous work. Their internal parent-directory components are not collapsed across symlinks: doing so could make verification refer to a different location from the one the operating system later executes. Acquisition checks files through bounded streaming reads rather than loading an entire executable into memory.

Download handling validates the declared origin and allowed redirects, counts actual received bytes and hashes those bytes while writing a private temporary file. Publication exposes a complete validated executable. Concurrent cold clients may download the same immutable artifact independently; an already-valid completed publication wins. This does not require a lock service or stale-lock recovery.

Process ownership adds a different constraint. The owned factory maintains one module-level slot spanning factory and broker owners. Its absolute attempt budget includes waiting for the previous slot, acquiring the executable and launching it. It checks the slot again after acquisition because another caller may have launched while this one awaited delivery.

The slot is released only after the transport’s actual `close()` promise settles successfully. An expired wait, a sent termination signal or an `ended` notification is not interchangeable with that settlement. Thus a bounded cleanup wait can finish unsuccessfully while the earlier helper still prevents another launch.

## Providers and lifecycle

An eligible interactive adapter starts asynchronous selection automatically. Print/JSON/RPC loading, an inactive extension or constructing the client does not start a helper. A failed installed presentation revokes that activation after restoring native UI and removing its card work. The ordinary client disable path cancels pending acquisition and closes that client's route; it does not rewrite the saved preference. Terminal start can resume terminal colors but cannot re-enable that provider without a successful presentation attachment. A successful replacement follows the existing activation and cleanup rules. Development version `0.0.0` uses only the colocated build, with a missing-build warning/fallback as specified [below](#binary-compatibility-and-delivery). Real-version packages select as follows:

1. Try a user-managed compatible Subconscious internal service using the public SDK/discovery contract. A connection file alone is not proof that Occipital is available.
2. If none is usable, resolve the extension-declared **exact** owned Occipital release for the actual OS/architecture/ABI. Verify the installed payload or exact cache bytes; otherwise acquire that declared artifact. Never substitute a newer cached version or query a latest release.
3. If neither provider is obtainable, keep the [ordinary fallback](work.md#rendering-and-fallback). Native availability does not gate tool execution or input.

Initial startup and automatic failure recovery have separate broker entry points. `start()` selects the initial route; after a published route fails, the broker retires it and becomes unavailable without acquiring a replacement. Source execution is responsible for calling guarded `recover()` only when a useful visit can re-enter. That boundary preserves the existing weak owner/source state rather than introducing a broker work queue. Metadata-only loss does not reevaluate an unchanged processed Bash revision or turn its prior refusal into an availability wait; a real source change can create new demand. No extra strong owner/text queue or conversation-history scan is used. Already-current native coloring is not reparsed, and the existing bounded restored-file native upgrade/retained Pi fallback policy is unchanged. Paused owners wait for a new useful visit; frozen live aborts, removed/collected owners and bookkeeping refusals are not revived by readiness.

[Source and style work](work.md#scheduling-contract) owns the single chronological preparation/dispatch registry, its quotas, cached-local progress and publication constraints. Provider selection does not create another card queue.

The extension and Occipital versions/releases are independent. Compatible shared-service versions need not equal the standalone pin. Owned processes have one client owner and are closed/reaped on retirement; shared clients close only their own route/connection and never terminate the shared module or peers.

Automatic unavailable acquisition is demand-driven: transport events retire and close their route, but do not start a reconnect loop. The broker exposes an absolute monotonic `recoveryAt` only while it is unavailable and a fresh acquisition can be requested; there is no timer-backed retry. Its exported `DEFAULT_PROVIDER_CLOCK` is the single production clock, and tests or an owning runtime may inject their clock through `ProviderOptions`. The client's cached provider snapshot is a presentation projection, not recovery-time authority: equal displayed metadata can suppress its replacement, while execution receives the ordinary opportunity and reads the broker's live deadline.

The broker has no lifetime owned-restart cap. Every automatic acquisition cycle is admitted no more than once per **60 seconds**, measured from the first actual factory invocation in the cycle. A cycle that tries shared twice and falls back to owned consumes the same one interval. Success, metadata, raw RPC traffic, stale results, cache reads, terminal stop/start and explicit Off/on do not erase or duplicate the absolute deadline; validated useful current classification remains a truthful metric, not a reset. Initial startup and healthy terminal-resume selection are not charged. A future-due ordinary On is visible in `recoveryAt` and does not hold a minute-long Promise. Persistent optional absence can be retried by later useful visits, without a permanent stop or broker retry timer.

`ownedRestarts` counts actual automatic replacement factory invocations using previous-owned selection, not initial standalone acquisition, shared-to-owned takeover, normal terminal return or handoff selection. It is cumulative for the broker lifetime and has no cap/reset role. Physical close starts are counted before the first deduplicated transport close; bounded cleanup success/failure remains separate from a later actual-owned-stop receipt.

On a useful guarded recovery visit after confirmed established shared loss, the broker permits bounded reconnect and owned takeover. Record whether shared service was usable at initial startup. Only an initially shared client that fails over gets one independent return window: one probe per **60 seconds for 600 seconds**, at most one active probe, no catch-up burst or extension from failed probes/source changes. A successful verified return retires and reaps only its owned helper before new shared source work. Initial standalone clients have no periodic shared probes. Off/disposal clears candidates and recovery timers.

Daemon state is disposable. Replies must match provider/source/style-selection generations and exact replacement coverage before publication. Lease expiry/state reset and stale responses cannot paint another source/version. A transport end does not by itself prove that a shared parser did not run.

## Recovery is a transition, not a fresh constructor call

`ProviderBroker` holds one bounded acquisition intent: initial selection, healthy working-route resume or automatic failure, with its original selection seed and first failure cause. Every published failure retirement retains the actual previous shared/owned kind for the next bounded round, including non-loss transport endings. Ending an old shared-return preference episode is independent of that seed: shared reentry still permits its two shared attempts before owned takeover, while previous-owned reentry goes directly to one owned factory. Automatic recovery of a published failed route never replaces that previous-kind seed with initial discovery; cold startup and deliberate Native On use ordinary initial selection. If an initially shared route's previous-shared round falls back to owned after the old preference episode ended, that owned publication starts the normal fresh bounded shared-return episode. Shared republication itself starts no such episode. Published loss retires the generation, synchronously reports its generation and first authoritative retirement origin, then closes only that route. `provenLoss`, transport-end, `workerUnavailable(generation)` and guarded `exhaustedRoute(generation)` do not acquire a replacement. `workerUnavailable` and exhaustion report only the broker-owned route; they never stop the shared service or peers. An exhausted-route request is ignored while the route is stale, a request is pending, an operation/probe is active, or owned-resource ownership does not match. The caller must first record its own terminal job evidence; the broker does not infer execution outcomes.

Only a later guarded `recover()` can start unavailable selection, after the predecessor operation has settled and the absolute deadline is due. Recovery does not proceed while ready, initializing, suspended, disabled, probing or cleaning an unproved owned exit. The broker does not own source-job evidence: source execution must apply its unsettled-work and unknown-execution guards before requesting useful reentry. If an asynchronous predecessor cleanup is still outstanding, that useful visit completes cleanup only; another fresh useful visit is required before factory work. Unpublished-candidate actual close completion and ordinary operation/probe guard clearance publish a coalesced `onChange` opportunity even when the displayed availability reason is unchanged. These notifications are weak, read current state, and never themselves acquire a provider. Observer exceptions cannot skip cleanup.

Owned recovery additionally requires actual exit. An old cleanup promise can later deliver an owned-stop receipt for its original generation, even after the broker’s bounded cleanup wait expired. That receipt is useful execution evidence for the source controller; it does not independently start recovery or publish a provider. The optional `onRetired(generation, origin)` callback delivers retirement before request cancellation or close; an earlier transport `endReason` takes precedence over the requested cause.

Shared-return probes run while the owned provider remains active. A successfully negotiated shared candidate initiates handoff, but shared source authority is not published until the owned helper has actually closed. If the candidate becomes unusable during handoff, the broker follows its bounded fallback path without creating a new return window.

Intentional terminal suspension uses this transition machinery without treating the stop as a crash. It always retires an active route, including an idle one, and checks both the broker’s pending-request count and the transport’s pending records: a metadata caller whose wait ended may still leave physical control work outstanding. It marks the interrupted generation before cancellation so late outcomes cannot manufacture ordinary recovery or publication authority. The existing `suspend()` return of the interrupted generation remains only for pending client migration/removal; it is not a new compatibility contract.

These mechanisms implement the recovery bounds below; they do not expand them. In particular, cleanup after an uncertain ending cannot turn that ending into confirmed loss, and a new provider cannot erase an earlier shared request’s unknown execution.

### Execution authority and conservative recovery

Request disposition, transport lifetime and retained paint answer different questions:

| Evidence | Meaning and boundary |
| --- | --- |
| Local typed `RequestFailure.execution` | Whether that one client attempt started; not the source's entire work history. A trusted pre-dispatch refusal is distinct from an arbitrary thrown error. |
| Validated remote fault/acknowledgement | Disposition of the corresponding correlated native operation, not unrelated previous attempts. |
| Pending physical SOURCE or queued useful demand | Prevents a competing Pi classifier even when no retained result exists. |
| Per-source owned/shared unknown-work guard | Survives payload release, provider replacement and Native Off when required. Missing data or a later successful request does not settle earlier shared uncertainty. |
| Broker-owned stop receipt | Actual reaping of the matching owned-helper generation can clear that owned evidence only; it cannot clear an earlier shared attempt. |
| Retained ready paint or STYLE success | Display/style evidence, never proof of SOURCE completion or parser permission. |

Transport endings record their **first** authoritative origin: `lost` (confirmed loss), `closed` (owner close), `uncertain`, or `denied`. Cleanup cannot upgrade uncertainty to loss. Shared route-close notifications for connection loss/reload/restart/crash and typed socket/stale-route failures can prove loss. Conversely, the public SDK may wrap both real EOF and its local read timeout as a pending-request `SubcError` with `closeReason: connection_lost`; that wrapper is intentionally classified `uncertain`. Unknown future route-close reasons are `denied`. Useful guarded acquisition can retry any unavailable cause at the broker's absolute deadline, without upgrading that first origin or treating connection replacement as proof that prior shared work stopped. Error-message text is neither execution evidence nor recovery authority.

Recovery budgets are independent:

| Mechanism | Bound and trigger |
| --- | --- |
| Parser-state resynchronization | First useful reconstruction immediately, subsequent starts on the same surviving card node at least60 seconds apart, including across success; no lifetime cap. Compatible growth/finalization preserves pending reconstruction. A proven incompatible rewrite/new syntax is ordinary work, retaining the node deadline for subsequent loss. |
| Evicted unchanged demand | One explicit retry permission followed by a current full-source observation, never a retry from every render. |
| Automatic broker reentry | One automatic factory cycle per 60-second absolute interval from its first factory invocation; no lifetime cap. Later useful visits retry persistent absence. Validated classification and successful recovery do not reset the interval. |
| Established shared reconnect | At most two attempts before the existing takeover/fallback path. |
| Shared factory / metadata / cleanup wait | Five seconds each. |
| Owned factory | Fifteen seconds. |

Acquisition/control waits are engineering bounds, not parser/regex/usefulness deadlines. Expiring a cleanup wait does not prove owned exit or free unsettled physical work. Parser retries and metadata reconciliation neither start a provider acquisition cycle nor alter its separate absolute pacing deadline.

### Intentional terminal suspension

The owned public terminal `stop`/`start` boundary also governs native syntax work, independently of terminal-color preferences. Before native stop, suspend SOURCE/STYLE/preparation admission and retire any active route, including an idle one; cancel pending startup/probe work. Capture whether requests were physically pending (including CONTROL work whose waiter already ended), then notify the execution owner before cancellation. This does not restart the session or clear ready paint, parsed scopes, style caches or measured geometry.

After successful native start, finish cleanup and reacquire through the existing bounded provider path. The returned resume Promise joins current cleanup and any ordinary activation started by that cleanup within the same active lifecycle epoch; it neither starts automatic failure recovery nor waits for a future service deadline. If a bounded cleanup wait has already expired, resume can finish unavailable while actual owned exit remains unproved. A later successful actual close exposes the normal useful-reentry opportunity rather than starting acquisition from stale demand. A healthy route interrupted deliberately resumes its previous selection immediately without spending or resetting an automatic-failure interval. Resuming an automatic failure does not acquire: the original absolute deadline remains in force, and another useful visit after it becomes due is required. If a failure factory had already started before interruption, its interval remains charged; interruption before the first factory does not fabricate a charge. Owned replacement requires actual exit of the old helper; signal delivery or a close timeout is not proof. Close only this client's shared connection, never the shared service. The operator explicitly accepts that old shared computation may briefly overlap bounded replay after this deliberate interruption.

Mark interrupted requests so their late success or failure cannot publish or manufacture ordinary failure authority. Keep their physical job/byte reservations until settlement. Revisit current useful demand through the existing chronological queue, with latest text and fresh incremental leases rather than replaying an old append packet. Complete compatible scopes and ready styles remain reusable; pending STYLE does not require reclassification of complete source. Hidden/frozen/removed owners, Native Off and disposal retain their admission rules. Native Off clears deliberate replay intent, not ordinary unknown-execution evidence: Pi fallback still requires its existing no-start/settled/owned-stop proof.

This is a narrowly scoped replay exception for observed deliberate handoff, not a general timeout retry policy. An ordinary uncertain/denied/closed end, including cleanup still in progress before suspension, remains unavailable until a useful guarded recovery visit. There is no lifetime crash-restart cap; automatic acquisition still observes the existing absolute interval, while intentional stops neither reset nor consume it. Existing bounded shared reconnect attempts and the independent initial shared-return window remain in force. No SDK deadline suspension or Pi signal handler is introduced. An unobserved process pause, such as raw `SIGSTOP` or OS sleep, runs no terminal-stop callback: captured-result validity, deadlines, physical settlement and useful recovery still follow their ordinary rules when execution continues, without acquiring deliberate-stop replay authority. This does not add terminal-color repair or signal/sleep monitoring for those pauses. Native external-editor/renderer stop/start uses the observed boundary.

Repeated suspension during reacquisition preserves the **current** recovery/interruption origin, taken from the active provider or in-progress transition, not historical `initialShared`. An interrupted automatic cycle retains its already-consumed interval charge; a stopped cycle that never invoked its first factory does not. The original absolute shared-return deadline also survives interruption; restarting acquisition does not restart its 600-second window. Without a recovery origin, resume follows ordinary fresh shared-first selection.

Explicit Native Off/on clears suspend-specific origin/return intent and establishes ordinary fresh initial-selection intent, while preserving the automatic-acquisition deadline. If reacquisition terminates unavailable, deliberate-replay priority stops blocking otherwise-proven Pi fallback; ordinary pending work, frozen state and owned/shared unknown-execution guards remain authoritative.

See [suspension validation](../testing.md#terminal-defaults-and-lifecycle) for real job-control and pending-request controls.

### Ownership exception

Temporary hidden/expanded/unsupported presentation and native highlighting off retain the same adapter's canonical work evidence. Complete adapter removal/reinstallation, including master off/on or reload, disposes its consumer and may allocate fresh source keys. An occasional repeated highlight while old work remains unsettled is explicitly accepted there; no cross-adapter owner registry or delayed installation is introduced. Normal cleanup, weak collection and rejection of late old-owner colors still apply.

Pi's synchronous transfer of the same components between fullscreen and regular renderers is not adapter replacement: preserve source keys, parsed scopes, ready palette/styles and measured geometry. This includes the final `fullscreenExitOutput: "transcript"` redraw. Renderer clear pauses work immediately; a weak microtask attachment check disposes only subtrees that remain detached. Ready unchanged demand does not repeat SOURCE/STYLE, classification or measurement on reattachment; changed text and equal-text finalization retain their own authority updates. Ordinary removal and adapter unload retain immediate cleanup.

## Selected, effective and ready palettes

`SyntaxClient` keeps one **selected** family/Follow-Pi preference and its remembered Dark/Light variant. `resolveTheme` in `src/themes/selection.ts` resolves that pair against the local owned-palette manifest and derives the concrete **effective** palette. A family ID is never used as an effective asset/lease/paint identity. `CardSources` separately owns the **ready** palette and semantic styles currently displayed.

Follow Pi and the 32 owned TUI families' 64 concrete variants are resolved locally; neither the picker nor effective palette selection depends on a daemon catalogue or provider readiness. An unknown but structurally valid saved theme ID remains selected, resolves temporarily to Follow Pi and produces one bounded issue for the unresolved choice. Changing the selected kind/family or resolving that choice ends the warning episode; changing only its remembered variant does not restart it, and provider metadata does not end it.

A card’s ready presentation can lag behind the effective choice. Selecting another palette does not make incomplete replacement input or styles displayable. The existing ready paint remains authoritative until the [work controller](work.md) can publish a complete replacement. Palette choice is independent from the enabled SOURCE/STYLE preference: Native Off can still prepare and display an owned palette's neutral card roles, but does not promise offline recoloring after semantic payloads have been released.

Initial choice adoption is revision-guarded. If a preview, saved-preference application or confirmation happens while supplied initial data is pending, that earlier input cannot overwrite the newer applied choice. The application preference owner separately protects confirmed intent against an earlier initial read. Preview changes the session choice without saving. Confirmation is admitted by the application preference owner and applies the choice before persistence; persistence failure initially leaves that session choice in place and reports failure. Popup rollback and cross-process settings publication belong to the [settings chapter](../settings-menu-spec.md).

## Menu and preferences

Bare `/tidy-ui` opens the shared [settings popup](../settings-menu-spec.md):

- **Code color theme:** Follow Pi plus the 32 bundled TUI theme families, searched by family label or stable family ID. A scrolling public `SelectList` keeps the selected row visible. Arrow/wheel navigation and search preview the highlighted palette without persistence; Enter or a completed mouse click confirms once and returns to the first page. Cancelling or disposing an unconfirmed list restores its entry choice. Each visit has its own rollback point; late replies cannot reapply an abandoned preview. Coloring uses the existing coalesced, newest-first two-owner batches, so large histories update gradually. Selected/effective differences are explained only when needed.
- **Code color variant:** a separate Dark/Light confirmation using the same selected preference and save path. Follow Pi keeps the remembered variant while dimming and disabling the control; navigation skips it and activation is inert.
- **Status & troubleshooting → Highlighting service details:** cached provider/lifecycle, daemon/protocol/standalone versions, selected/effective palette and bounded last issue. No source text, discovery or new source work.
- **Use Occipital highlighting:** native-only preference, restored across reload and master off/on. Disable closes owned resources without stopping a shared module. The preference is saved alongside the confirmed code theme and terminal-default preference; appearance and diagnostic capture are process-local.

Opening/status/cancelling cannot enable a disabled provider. Follow Pi and the bundled palette list remain available without a live helper. Preference preparation has an explicit completion boundary. Closing confirmed pending work is not rollback, but retired runtime/syntax owners cannot publish late actions. Feedback is UI-only, never a conversation/model message.

`syntaxTheme` is either `{ "kind": "pi" }` or `{ "kind": "theme", "id": "<theme family ID>" }`, with a separate top-level `syntaxThemeVariant: "dark" | "light"`, in `join(getAgentDir(), "extensions", "pi-tidy-ui", "config.json")`. Missing/unsupported variants mean Dark; only exact `"light"` selects Light. Known legacy concrete IDs are recognized as family aliases without inferring their suffix's variant or rewriting on read. Every confirmed theme/variant change saves both canonical keys in one existing queued patch. Pi resolves the agent directory and its `PI_CODING_AGENT_DIR` override. Only the confirmed family/variant choice, terminal-default preference and native-highlighting preference persist; no provider, retry, lease, source or expanded palette data is saved.

Missing configuration defaults to Follow Pi, native highlighting On and terminal-color application Off without writing. Explicit saved switches retain their values. Invalid/unreadable files and failed/cancelled saves report bounded errors rather than rewriting them or claiming success. Updates preserve unrelated fields and share one serialized writer within the installed extension. Native directory events propagate the last published settings into running Pi instances; metadata-gated reads replace periodic polling/read/hash. Appearance and capture retain only two process-memory booleans across `/reload`, defaulting On in a new process. During an unconfirmed preview, external confirmation updates the Esc rollback choice without interrupting the preview; Enter confirms the local choice. See [settings policy](../settings-menu-spec.md#changes-from-another-pi) for lifetime, invalid-file and concurrency rules. No database, migration or cross-process lock service is added.

A valid owned palette remains fixed across Pi theme changes. If a bundled asset cannot be read or validated, report one bounded issue and retain the prior complete card paint; when no prior paint exists, prepare a complete Follow Pi input instead. While that fallback is active, actual public Pi color changes produce a new fallback input, but do not retry the failed asset. The unchanged failed asset is not reread on warm visits. A later explicit palette selection or output-mode change can attempt owned input again; no provider metadata or catalogue refresh is involved.

## Binary compatibility and delivery

The current consumer requires the exact [v4 capability and structural revisions](../occipital/protocol.md#version-identities-and-carriers) and [resolver/font interpretation](follow-pi.md#typography-strikethrough-and-compatibility). The currently published Occipital 0.2.0 / pi-tidy-ui 0.1.1 pair uses v3 and is incompatible with this working-tree contract; identical product names or a valid executable hash do not establish protocol compatibility. Published artifacts remain immutable.

Exactly extension version **`0.0.0`** selects development: only `<extension-root>/occipital` (`occipital.exe` on Windows) may start. It does not use shared discovery, native npm payloads, a release cache, downloads or compilation. If the local build is missing, a `[pi-tidy-ui]` UI warning identifies the extension and Occipital is not used. Files retain cached Pi fallback; Bash retains whole-command `toolTitle`. Protocol admission and actual owned-process cleanup still apply. The extension root, not the current project directory, owns the binary.

Real-version packages use shared-first selection, then the exact independent daemon declaration generated during release preparation. Missing or incomplete selected releases fail preparation rather than falling back to an older release. Runtime does not inspect Git/latest or build Rust. Optional native packages contain the executable, LICENSE/third-party NOTICE and metadata, not a duplicated JS client or startup installer. If the optional payload/SDK is omitted, exact declared cache/download delivery remains available.

[Release delivery](../releases.md#extension-delivery) owns version selection and byte admission; [supported platforms](../releases.md#supported-platforms) owns the OS/architecture policy for the entire extension, including the current Windows ARM64 exclusion. The installed Pi/Node host's requirements apply in addition to the helper's ABI requirements.

See [syntax validation](../testing.md#syntax-and-palette-validation) for counters, physical cells, exact data/replay and compatible-helper controls.
