# Bash streaming: display and work contract

This contract explains how Bash cards keep complete current text and useful colors while source parsing, style resolution and tool lifecycle advance independently. It complements the [card format](bash-card-spec.md), [syntax pipeline](syntax-highlighting-spec.md), [render-cache contract](render-cache-spec.md) and [diagnostic contract](debug-logging-spec.md).

## Design rationale

A growing one-line command has no committed line prefix until it ends. Its existing colors are provisional, so retaining only committed-line styles would erase all highlighting on each update. Retaining the previous rendered rows would avoid that erasure but hide new characters. Instead, the renderer projects historical styles onto the matching prefix of the complete current text. Those styles are presentation evidence, never authority to continue a parser or start duplicate work.

Argument completion, request acknowledgment and parser-lease cleanup can change work state without changing any displayed character or style. Separate display-effect identity prevents those transitions from rebuilding an unchanged body, while native lifecycle callbacks and required finalization still run.

## User-visible invariants

1. **Always show the complete latest display-normalized command.** Do not wait for classification, freeze old rows, delay streamed characters or alter native arguments/model/session data. The existing `blockText` normalization, prompt, tabs, wrapping and frame geometry stay authoritative.
2. **Waiting is not a reason to erase colors.** A new revision, queue entry, in-flight RPC, acknowledgment, lease transition, finalization or formation error cannot by itself turn an unchanged colored prefix into whole-command `toolTitle`.
3. **Reuse historical styles for the matching prefix, including provisional styles.** When text is appended, retain the last validated style of matching old characters. New graphemes without applicable styles use the ready palette's command-neutral role (`toolTitle` under Follow Pi). Each current grapheme is indivisible and takes its first scalar's style: if that scalar matches the basis, the whole grapheme inherits it, including any newly appended combining/joining scalars. A fresh accepted classification may legitimately change token styles.
4. **Corrections invalidate from the first mismatch onward.** Match the scalar prefix; a current grapheme whose first scalar lies beyond that prefix is neutral. The indivisible-grapheme exception above applies if a mismatch occurs inside the current grapheme. Do not reuse arbitrary equal suffixes, search for repeated text islands, or color new text using old byte offsets.
5. **Retained styles are display history, not current-source proof.** They may temporarily be lexically outdated after appending text. This is the explicit trade-off for continuity. They do not validate new source text, provide a parser checkpoint, authorize Pi/native parsing or reset a crash budget.
6. **Bash never uses Pi's classifier.** With no compatible retained styles, display the entire current command in the ready palette's command-neutral role. The first native color upgrade is expected; repeated loss of colors solely because another result is pending is not.
7. **Formation failure freezes source work, not the ability to display.** Stop abandoned parsing and close its lease; keep compatible cached styles/scopes for the command still present. Retained scopes may recolor or reflow without parsing. Never execute incomplete arguments or revive a lease to recover colors.

The no-flicker guarantee concerns scheduling/authority transitions of the same retained presentation. It does not prohibit real native token-style changes, changed text, explicit native disablement, actual cache eviction or complete presentation-owner replacement. A theme change retains the last ready display until its replacement is accepted, rather than inserting a neutral-color frame. It does not promise perfect current lexical coloring while a newer classification is pending.

## Separate facts, not separate source owners

The existing source/controller remains the single owner of native work and retained source data. Expose three distinct facts without introducing a second source-owner system or a general readiness framework:

- **Latest display target:** current normalized command and display identity; width and other presentation arguments remain layout concerns.
- **Validated display basis:** acknowledged immutable source text, complete validated semantic coverage and ready styles/palette, grammar/vocabulary identity and a display-effect stamp. Coverage includes the provisional tail, not only `committedBytes`; requested theme is not parser identity.
- **Work authority:** latest useful native demand, in-flight captures, uncertainty, completion, lease/recovery state and parser permissions.

The controller stores an acknowledged basis separately from the latest desired snapshot. Its canonical read-only basis view pairs ranges with the exact text they classified, without duplicating full strings, encoded buffers, classifications or caches in the host. A view clipped to the newest demand's committed prefix would omit provisional styles needed for historical display reuse.

Reading a view does not observe a new demand, acquire credit, dispatch a request, change fallback permission or keep a Pi component alive. No current-version/exactness decision may be inferred from availability of the view alone.

## Projection and compatibility

When the prepared command or validated display basis changes, verify their matching scalar prefix outside rendering. Cache the eligible UTF-8 prefix length together with the current source revision and basis geometry identity. Rendering consumes only that guarded proof and applies prepared styles to current graphemes according to their first scalar; it does not rescan either text. After the first mismatch or basis end, remaining graphemes are neutral except for the already-started matching grapheme. Theme, width and unchanged-frame changes reuse the proof when those identities still match.

This transition-time display comparison grants no parsing authority. Do not add a whole-source hash, diff, matching-suffix pass, second normalization or eager per-callback encoding. Classification, source admission/normalization for RPC, source encoding and dispatch remain outside `render`. Use the already prepared normalized command and a borrowed validated basis, without retaining another source copy.

- Compare display-normalized text, never raw streamed JSON or raw ANSI/control characters.
- Match Unicode scalar boundaries; preserve the existing first-scalar style ownership of a displayed grapheme. A mismatch cannot retain a partial UTF-8 sequence or split a surrogate pair. A newly appended combining mark or ZWJ sequence can enlarge a matching grapheme: the entire current grapheme inherits its matching first scalar's style, with no ANSI inserted inside it. This is the explicit exception to new-text neutrality; current glyphs and geometry always win.
- Keep logical source offsets distinct from prompt columns, expanded tabs and soft-wrapped rows. Description, cwd and output are never classified as command text.
- Display reuse requires the same presentation/source owner and language. Keep the actual validated display profile distinct from the requested profile: selecting another theme, its failure or temporary metadata absence does not erase an owned display basis. Parser coverage follows source/grammar identity; current-theme style publication separately requires the requested rule/palette fingerprints. Track exact logical-text aliases separately from the classification's original version, so an equal-text revision does not lose retained display. Provider recovery cannot treat a different theme's display as completed requested work.
- Matched Follow Pi style bindings may be materialized against the current public palette without parsing or another scope match. While an independent RGB theme is pending, show the old theme as retained presentation, not as proof of the new theme. Replace it when a valid current result arrives. If a finite, exact original result is still retained when a preview is cancelled, reuse it without another classifier request; do not resurrect its old stream lease or release obsolete physical jobs. Retain one ready display basis, not a history of rendered source snapshots; accounted styles may be shared by live context/rule identity. Validate reply profile against the current selection before publication, even when its next preparation batch has not run yet.
- Width/padding changes rebuild geometry only; they do not create a new logical source or native request.

Warm layouts use the existing cache signature and a primitive display stamp. They do no compatibility traversal, normalization, source-buffer allocation, parser work or new diagnostic emission.

## Scheduling and lifetime

Preserve the existing useful-demand boundary and coalescing. Real argument callbacks cheaply record current identity; they do not each become a native request. A normal render may record the existing weak useful-demand ticket; preparation/admission/encoding/dispatch remain outside it. Do not add a viewport subsystem or call an already visited component necessarily visible.

- Keep at most the existing in-flight source capture and latest waiting demand per source. Repeated/identical updates coalesce; metadata-only description/cwd/result changes do not parse the command.
- Initial startup and later connection loss share one availability-wait path. A useful Bash demand deferred specifically because an enabled provider/effective profile is unavailable marks its existing card/source slot. On compatible readiness, revisit all such live weak tickets through the existing dispatcher, using each owner's latest revision. Do not scan conversation history, retain owners/text in a separate queue, reclassify already-current sources or replay every file fallback. Frozen, paused, removed, collected and bookkeeping-refused owners are not revived; a paused owner requires a fresh useful visit. Metadata-only loss does not reevaluate an unchanged processed Bash revision or relabel its prior refusal as an availability wait; a real source change can create new demand.
- An explicit code-theme selection or changed effective profile ID/fingerprint renews all previously useful retained owners, including completed Bash and file sources, through the same weak-ticket scheduler. Track prepared/requested theme revision independently of text revision. Offline choices remain pending for readiness; ordinary same-profile recovery does not renew completed work. The last validated display remains while another profile is pending, including file cards; it does not become current-profile parser proof. Files with an exact retained display need no intermediate Pi classification. No conversation scan, source copies or strong owner queue. Live-frozen owners admit retained-scope recoloring but no parsing. Explicitly paused owners admit neither SOURCE nor STYLE and cannot publish held STYLE until a new useful visit; genuine settlement and accounted style caching still occur, allowing reuse on resume. Removed/collected owners stay retired.
- `SourceController` owns one chronological LIFO work registry, selecting both card preparation and native dispatch newest-first. Register each existing weak card ticket before heavy preparation; its native segments share that entry. Standalone sources register once on first admission. Retrying or changing theme does not move an entry. There is no separate sorted card queue or numeric priority. Skip busy/protected work and publish each valid result independently: LIFO is admission preference, not an ordered-completion barrier. Already dispatched native work keeps its physical reservations.
- Prepare no more than the existing two-job credit limit of card owners in one batch; yield to the event loop with a weak one-shot continuation before another batch. Synchronous or asynchronously queued notifications cannot replace that continuation with an immediate microtask chain. Keep the barrier even when the pending set is momentarily empty after a flush; the one-shot continuation stops without further scheduling if no demand arrives. Native RPC admission still obeys controller/provider/global byte and job limits. There is no idle polling, time budget or new queue/payload store. One individual source preparation/classification is not preemptible and has no hard latency guarantee.
- The same registry has a resumable cursor: do not copy/reverse and scan the whole registry again for each two-owner batch. A theme notification marks one global refresh revision; inspect weak tickets lazily. Full native credits defer new-owner/theme preparation, not live text changes or independently permitted file fallback. Repeated previews keep only the latest requested profile; metadata/preparation alone does not rebuild unchanged file colors.
- A theme-only change supersedes style publication, not parser identity, without aborting the two already dispatched physical jobs. Successful SOURCE replies remain useful; stale STYLE replies settle their reservations without publishing abandoned colors or resetting the source-success counter. Other cancellation paths still forward correlated terminal evidence to the canonical decoder rather than manufacturing transport uncertainty. A started error or genuinely unknown outcome retains its existing protection.
- A prepared empty command may own local empty semantic coverage and a ready palette without sending SOURCE. That local revision is not a native parser checkpoint. When real text arrives, retire that local semantic generation through the normal restart/retained-display path and begin a fresh native parse at revision 1; only a validated live lease authorizes later append revisions. Preserve physical unknown-outcome evidence and strict revision validation. Empty registration that has not prepared coverage needs no extra generation reset. This also applies after clearing an earlier parsed command, or while its empty-palette STYLE reply is in flight.
- Within the [admitted highlighting prefix](syntax/work.md#highlighting-volume-policy), append continues the existing native stream; corrections use the existing bounded source-restart rule. Reaching the cumulative byte/line coverage boundary makes that actual classification prefix finite and settles its lease, even if argument formation continues. Growth only in the neutral remainder never grants another allowance or SOURCE/STYLE request. Historical display styles do not change parser-basis selection. Parser-generation replacement must not delete a compatible historical display basis merely because the old parser stream is retired. Retain one charged display basis while the latest replacement demand is prepared; do not accumulate a history of snapshots.
- Finalization remains mandatory for an existing stream, even with no appended bytes. It settles authority and releases the native lease. It is not an unnecessary RPC merely because the cached tail needs no parsing. A classification prefix already finalized at its coverage boundary has no continuing lease to reopen when the real command later completes; classification completion is not argument or execution completion.
- Live abandonment stops continuation/new SOURCE requests for that installed call owner and retires/closes parser leases through the existing transport authority. It does not forbid acceptance of valid already-requested colors: if `abc` was ready, the displayed command grew to `abc123`, and its STYLE response arrives after interruption, apply that correct response without another SOURCE request or lease revival. Retaining the older display identity is not a product requirement. Normal ownership, current-text/matching-prefix, profile and atomic-publication checks still apply; obsolete, foreign or removed-owner replies cannot publish. Genuine physical obligations settle regardless of whether paint can publish.
- A restored terminal card is a new static display source, including an interrupted call with incomplete Bash arguments. Classify its available text once as a finite snapshot under ordinary useful-demand/provider admission; do not reopen a continuing stream, execute the command, alter argument-completion/execution/error flags, or require persisted colors. Cache the result for ordinary frames/geometry changes. A public assistant-stream tool-call identity distinguishes live owners from restored owners, even when a live abort precedes the first rendered frame. Remember only primitive IDs for the current message until the next assistant message, agent end or session replacement; never scan history or retain message bodies. Embedders without this semantic identity preserve the conservative live-error behavior.
- Work retirement and presentation-owner removal are different operations. Display eligibility is independent of permission to admit new work: an abandoned command can remain an owned display without being a live source demand. Owner removal, full adapter disposal and GC release the retained display data; abandoned calls must not require a live daemon lease to keep their colors. Geometry-only changes, including a temporary zero usable width, do not replace the source owner or discard its basis. They may withhold new useful demand without freezing the call as terminal.
- Retained active/frozen views remain charged to the existing bounded source-retention budget. Borrowing cannot keep uncharged payloads alive after pool removal. No new count caps, full-source copies or pressure-driven replay loops.
- Genuine eviction may remove historical styles, with an explicit reason. An abandoned live owner never resumes parsing because its frozen view was evicted; new-owner static restoration is the separately authorized case above.
- Cancellation, rejection and missing provider state are not proof that an RPC did not start. Existing unresolved captures/credit/fallback evidence remain held until the existing completion or actual owned-process cleanup authority resolves them. Other sources continue independently.

Freezing source work and retiring a display owner are separate transitions in the existing controller/consumer. This keeps one budgeted display basis without a second display service or ownership registry.

## Notifications and layout invalidation

Work-state notifications and display changes have different effects. Continue delivering all genuine settlement, permission, credit, lease and recovery facts. The Bash host does not invalidate a layout solely because such a notification arrived.

Invalidate only for current text/presentation/geometry changes, palette/profile effects, retained-style loss, or a classification/basis change that can affect projection. In particular:

- admission/waiting with no new display coverage does not discard the already correct neutral layout;
- setting argument completion without text/style change does not discard the command layout;
- accepting a completion-only cached-tail result preserves the layout while updating acknowledgment/completion/lease state;
- changes that genuinely color new characters, revise styles or make a different basis applicable still request the required repaint;
- error/output changes can rebuild the card while retaining the command's compatible display basis.

Maintain a display-effect stamp alongside canonical retained data, separate from request/source revision and native authority. Determine compact classification effects during the already required decoded-range installation, comparing the touched normalized style spans when necessary; do not add a second whole-source scan, hash, speculative row build or equality cache. Equivalent captured text/styles with changed completion metadata keep the stamp. Zero parser-call counters, equal row counts or equal source length alone are not style-equality proof.

Keyed observers carry work notifications; consumers use the primitive display stamp to decide whether presentation changed. Work settlement therefore remains observable without turning every notification into a repaint.

## Error presentation and diagnostic coverage

Use known native lifecycle facts, not a generic `isError` bit, to describe failure:

- final error with known incomplete arguments and no execution: **`[error: incomplete tool call]`**;
- known execution failure: preserve the existing applicable exit-code/timeout/`execution failed` policy;
- unknown phase: a generic tool-call failure, not an invented execution or provider diagnosis.

Keep the producer's error/output text unchanged as ordinary card output. `WebSocket closed 1000` is not a daemon failure and does not reveal the closure's cause. pi-tidy-ui does not patch Pi's provider client or mask an incomplete response.

Logs describe current facts with separate fields for display basis/version, latest target revision, historical/provisional reuse, actual work phase and initial demand outcome. A record cannot present an initial `waiting` outcome as the current execution state or imply that a generic settled fallback veto means Pi was used for Bash.

Do not emit one identical lifecycle record per `updateArgs`. Use existing source/preparation/publication records for source progression, actual phase/geometry/result changes for lifecycle, and aggregate already counted callback/source-update totals at completion/error or explicit snapshots. Preserve description/cwd changes that genuinely affect layout without logging their content. Records follow semantic changes rather than timed sampling; errors are not dropped.

Role/stop-reason fields come only from public semantic-boundary events. Do not scan session history, read raw messages, dump provider errors/stacks, or add private provider hooks. A no-op shared-selection callback under local-only policy is not actual discovery, and missing optional Git-backend paths are not runtime failures. No JSON journals/indexes, extra clocks, per-frame records or record-level filesystem checks.
