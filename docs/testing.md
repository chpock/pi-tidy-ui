# Testing and coverage

This is the maintained guide to reproducing pi-tidy-ui checks, not a journal of past runs. Use a repository checkout; the npm package contains runtime code/documentation, not the harness or fixtures. Visual behavior is specified in the [presentation contracts](README.md#extension-host-and-presentation); the root [user guide](../README.md) explains everyday use, and integration boundaries are described in [architecture](architecture.md).

Current [platform support](releases.md#supported-platforms) is GNU Linux x64/ARM64, macOS x64/ARM64 and Windows x64. **Windows ARM64 is temporarily unsupported for the entire extension** because of disproportionate verification cost. Windows ARM64 stays in the central platform catalogue but is disabled unless repository Actions variable `CI_WINDOWS_ARM64=true`; enabling that platform or citing a historical pass does not establish restored support.

## Requirements and commands

- Node.js >=22.19.0. CI selects exact Node 22.19.0 and 26.7.0.
- An explicitly prepared Pi dependency graph. The compatibility matrix selects minimum Pi 1.0.0 and the exact version resolved once from npm's public `latest` dist-tag during workflow planning, never an independently moving tag or an installed CLI. CLI, SDK, TUI, AI/core, extension imports, type checks and child probes must use the selected coherent graph; Pi-family package version strings need not all be equal.
- For native preparation: provisioned Rust **1.99.0**, including rustfmt and Clippy, and platform compiler/linker prerequisites. User Cargo configuration is not an input.
- For physical CLI tests: POSIX, declared Python 3 with PTY support and the prepared CLI. Python runs with `-I -S`, excluding environment/user/global site startup customizers. No model credentials are needed: the driver uses an offline scripted provider.
- The Linux suspend entries under `cli/native/syntax/linux/` and `cli/shared/syntax/linux/` require real shell job control plus `/proc` stopped-helper evidence; they are platform-inapplicable elsewhere. Four independent transport/terminal-mode files each run SOURCE, STYLE and incremental append serially: all twelve semantic cases, 45-second case bounds and actual 4.5-second stopped intervals remain. They prove bounded wake recovery, physical current/new cards and idle/warm reuse; they do not mock request settlement or defer an already-delivered reply.
- For actual native/owned-syntax CLI tests: a verified same-source Occipital artifact. Only selected shared tests additionally require an explicit Subconscious host executable. Only selected installed-profile tests require `--integration`. Neither prerequisite is imposed by unrelated footer/editor/card tests.

### Ordinary feature work

Start with one explicit graph (Linux, Node 22.19.0, Pi 1.0.0), not the operator's Pi or the entire compatibility matrix. A fresh Git clone with its reachable release history/tags is sufficient: no historical `.test-artifacts`, repository `node_modules`, installed Pi or personal transcripts are needed. The preparer itself uses Node built-ins and installs the selected graph into its owned runtime; do not install a second graph in the checkout first. Provision Node/npm compatible with each other, Git and the platform tools below. On local Linux graphical sessions, wrap **all fallible test commands below** in the [verified ordinary scope](#local-memory-containment-and-assertion-diagnostics); raw runner examples show selection arguments, not permission to run uncontained.

```sh
npm run test:prepare -- --pi-version 1.0.0 --output /absolute/path/to/feature-inputs
INPUTS=/absolute/path/to/feature-inputs/inputs.json

# Tight edit loop: refresh sources without reinstalling/copying the sealed dependency tree.
node scripts/test/prepare.mjs --refresh-inputs "$INPUTS"
npm run test:group -- --inputs "$INPUTS" --groups footer --layer node

# Feature acceptance: types + common product SDK/logic/GC + smoke + affected real CLI.
npm run test:feature -- --inputs "$INPUTS" --features footer --refresh --output /absolute/path/to/footer-receipts
```

Replace `footer` with a comma-separated combination of `summaries,bash,edit,write,user,queued,editor,footer,layout,lifecycle,activity,settings,terminal-colors,logging,syntax,native,shared,profile,harness,delivery`. A coupled test belongs to one file but may be selected by multiple domains; the command de-duplicates it. `--features ''` is the common baseline. `--affected-only` is a local composition/debugging option that omits the common baseline and default type stage, not a CI selection mechanism or replacement for feature acceptance. Add `--check-types` to retain types with that local option. CI independently runs its fixed complete suites; a local feature command is not equivalent to full CI.

`--refresh`/`--refresh-inputs` recheck the selected Node/host, manifest/lock, complete owned dependency bytes and neutral runtime ancestry. They remove old source files (including deleted tests) before copying current sources. Each runtime owns its source inventory; failed replacement preparation cannot overwrite the surviving runtime's inventory, and an interrupted refresh retains attempted additions for later cleanup. The runner rejects that incomplete inventory before launching children; successful refresh restores execution. Legacy unsealed descriptors retain byte-checked execution but cannot refresh without one fresh preparation. Reports count dependency installations/copies and source copies. Changed graph inputs require preparation again; changed native inputs require a new verified helper. Refresh does not relabel an old helper's provenance or regenerate a source-bound consumer archive closure; after source changes, prepare that closure again before consumer execution. It requires a sealed graph from the current preparer; older inputs need one fresh preparation.

The 2–3-minute end-to-end target applies to the **local feature loop only**, not full CI. It is a guideline, not a timeout or pass condition; justified variation is acceptable. Include preparation and prerequisite costs, distinguish owned-cache/source-refresh runs from cold setup, and report longer required integrations rather than hiding them. Do not run full compatibility acceptance for a local presentation-only edit. The [structural catalogue](../scripts/test/catalog.mjs) discovers executable membership; feature subdirectories select local groups, not source-impact CI routes.

### Provision optional inputs from a fresh clone

Ordinary types/product/footer/editor preparation needs neither Rust nor a native/shared service. Physical CLI needs declared Python 3 (standard-library PTY on POSIX) and Bash for real job-control cases. If selecting another Node executable, `--node` selects that actual runtime; `--tools /absolute/tools.json` may supply an absolute `npm` JavaScript CLI entry compatible with it. No tool path or private tools map from a historical run is a prerequisite.

Native tests additionally need the pinned Rust **1.99.0** sysroot with rustfmt/Clippy and the host C/C++ compiler/linker. Provision it separately, never during test execution. For example, using an already provisioned explicit Rustup executable, install into fresh owned stores (not user defaults):

```sh
TEST_ROOT=/absolute/new-test-input-root
mkdir -p "$TEST_ROOT"
export RUSTUP_HOME="$TEST_ROOT/rustup" CARGO_HOME="$TEST_ROOT/cargo"
/absolute/rustup toolchain install 1.99.0 --profile minimal --component rustfmt --component clippy
RUST_ROOT=$(/absolute/rustup run 1.99.0 rustc --print sysroot)
# Supply --rust-root "$RUST_ROOT" --build-native to preparation, then execute offline.
```

For Linux x64 shared integration, use the same pinned public input as CI. This is explicit **preparation/network acquisition**, not runtime discovery or a download from inside a test:

```sh
mkdir -p "$TEST_ROOT/shared-host"
curl --fail --location --output "$TEST_ROOT/shared-host/host.zip" \
  https://github.com/cortexkit/subconscious/releases/download/subc-core-v0.20.83/ck-subc-linux-x64.zip
printf '%s  %s\n' c905fd8c5eba045c38fb61dd0c6c0ffc8254ae2cb0be50ef1017cde5470e62c4 \
  "$TEST_ROOT/shared-host/host.zip" | sha256sum --check
unzip -j "$TEST_ROOT/shared-host/host.zip" ck-subc -d "$TEST_ROOT/shared-host"
chmod 700 "$TEST_ROOT/shared-host/ck-subc"
# Supply --shared-host "$TEST_ROOT/shared-host/ck-subc" to preparation.
```

Shared fixtures explicitly set `port: 0` in their private `subc.jsonc`, in addition to private HOME/config/runtime/discovery roots. The pinned host [supports OS-assigned loopback ports and publishes the actual bound port](https://github.com/cortexkit/subconscious/blob/subc-core-v0.20.83/crates/subc-daemon/src/bootstrap.rs#L1438-L1501); no find-free-port probe, retry or cross-run lock is needed. The simultaneous real-host control `tests/cli/shared/syntax/shared-host-isolation.cli.test.mjs` verifies distinct published ports, independent helper processes and real traffic while both hosts remain live. Leaving the production default port implicit makes otherwise-private fixtures collide during parallel file execution.

All private Subconscious test-host launchers use [`sharedHostEnv`](../tests/fixtures/shared-host-environment.mjs), which composes the existing sanitized `childEnv` with `SUBC_CGROUP_PLACEMENT=disabled` and **`TOKIO_WORKER_THREADS=2`**. This explicit integration-fixture budget keeps hosts and managed helpers inside the verified aggregate scope and avoids multiplying CPU-count-sized async worker pools when independent files run concurrently. [Tokio's worker setting](https://docs.rs/tokio/1.52.3/tokio/runtime/struct.Builder.html#method.worker_threads) otherwise defaults to available cores; the fixture does not pin CPUs or change ordinary Node/Cargo, Occipital's existing worker/actor policy, production/user host settings or benchmark conditions. Shared integration therefore certifies the real host with two Tokio async workers, not its CPU-derived default pool size. Required concurrent hosts, physical jobs and peer progress remain real; the aggregate 2 GiB/128-task limits are unchanged. The environment regression checks polluted callers and an actual child, including that ordinary child environments do not acquire this host-only policy.

Suspend evidence records monotonic stopped/resume boundaries and asserts at least 4.5 seconds actually stopped. The fixture waits to a monotonic deadline, rescheduling only a positive remaining interval: a nominal `setTimeout(4500)` can return a fraction of a millisecond early. This keeps the existing 4-second request deadline plus full 500 ms margin, without shortening the pause or increasing the 45-second case bound.

That asset recipe establishes Linux x64 input provisioning only; other platforms require their own explicitly verified host input and are not covered by this archive. `--integration` installs the tracked audited `tests/fixtures/integration-profile/{package.json,package-lock.json}`; `--archives` prepares the consumer closure described below. Missing selected prerequisites fail before cases, never become successful skips.

### Clean-state harness acceptance

For changes to the harness itself, use a separate **real Git clone**, including the history/tags needed for native version stamping. Start with no generated artifacts, installed dependency tree, Pi settings or operator caches. Follow the ordinary preparation and verified-scope commands above/below, run types plus representative product/harness and real offline-provider CLI, then explicitly provision/build the optional native/shared lane and run it. Repeat prepared execution with `--network-isolated` on Linux. First installation may acquire declared public inputs; clean clone is not an air-gapped install.

The maintained tiny admitted-fixture controls exercise the **actual** `execute` API and runner CLI at jobs=1/2, including production resource preloads. Parent-held peer gates prove serialization/bounded overlap without speed thresholds; rejection, cancellation, abrupt startup and SDK-bootstrap failure preserve peer evidence. POSIX SIGINT/SIGTERM controls start two workers with real descendants and verify interruption reports, reaping and root cleanup; they do not establish Windows signal acceptance. Native-build fixture controls remain fixed jobs=1 and use inert Rust, not compiler acceptance.

This is a standalone acceptance procedure, **not** a discovered `tests/harness` case, automatic feature prerequisite or extra CI job. Never recursively clone/download/build native dependencies from a network-isolated ordinary test. A clone of HEAD cannot prove uncommitted candidate changes: before commit authorization, overlay only the reviewed intended source files/deletions, record the resulting exact source identity and label it prospective-clone evidence. Do not copy generated state or create a commit just for that proof. Final committed-clone evidence needs the separately authorized source commit.

### Prepare broader inputs, then execute

Preparation owns dependency resolution, allowed public-network acquisition and native building. It records source commit/tree identity, native-source `nativeTree`, exact Node executable/version, selected Pi packages/lock, declared tools and required artifact hashes in `inputs.json`. It materializes a test tree with its own dependency graph without changing repository manifests/lockfiles or user installations. Preparation uses owned npm/Cargo stores and clean configuration, not user credentials, proxies, `.npmrc`, Cargo config or incidental caches. Unsupported Node engines fail preparation rather than merely warning. Prepared source copies, including Cargo's working directory, live outside the checkout and its ancestor configuration search; the original checkout is not rewritten.

`npm run test:prepare -- ...` invokes the same preparer. Its default output is `.test-artifacts/harness/1.0.0` (or the selected Pi version); explicit separate outputs avoid mixing host/runtime inputs. For the broader native/Rust/shared/profile/consumer union, with the pinned Rust sysroot and shared host already provisioned:

```sh
node scripts/test/prepare.mjs --pi-version 1.0.0 \
  --rust-root /absolute/path/to/rust-1.99.0 --build-native \
  --integration --archives --shared-host /absolute/path/to/ck-subc \
  --output /absolute/path/to/prepared-pi-1.0.0 \
  --run-root /absolute/path/to/runtime-parent

npm run check -- --inputs /absolute/path/to/prepared-pi-1.0.0/inputs.json
npm test -- --inputs /absolute/path/to/prepared-pi-1.0.0/inputs.json
npm run test:native-release -- --inputs /absolute/path/to/prepared-pi-1.0.0/inputs.json
npm run test:rust-check -- --inputs /absolute/path/to/prepared-pi-1.0.0/inputs.json
```

Use separate output directories for each Node/Pi selection. To reuse the verified current-source helper in a second host graph, set `PI_VERSION` to the exact alternate version recorded by CI (not a tag/range):

```sh
node scripts/test/prepare.mjs --pi-version "$PI_VERSION" \
  --native-inputs /absolute/path/to/prepared-pi-1.0.0/inputs.json \
  --integration --archives --shared-host /absolute/path/to/ck-subc \
  --output /absolute/path/to/prepared-pi-alternate
npm run check -- --inputs /absolute/path/to/prepared-pi-alternate/inputs.json
npm test -- --inputs /absolute/path/to/prepared-pi-alternate/inputs.json
```

Run the expanded Pi/Node matrix when host/runtime contracts change and for full compatibility/release acceptance, not after each ordinary feature edit. A → B → A controls detect cross-version contamination. These examples select checks, not a claim of full compatibility acceptance. Execution rejects a changed tested commit/tree; source-only refresh is described below.

| Preparation option | Meaning |
| --- | --- |
| `--node ABSOLUTE_EXECUTABLE` | Record and use that actual Node executable/version, including children |
| `--tools FILE` | JSON of explicit absolute prerequisite tool paths, including the npm CLI JavaScript entry when needed |
| `--offline --npm-cache DIRECTORY` | Use explicitly supplied npm content cache, with no public dependency fetch; non-baseline offline preparation also requires its previously resolved exact manifest/lock in the output directory |
| `--registry-inputs INPUTS_JSON` | Reuse a prepared consumer closure only after matching its source snapshot, selected host/runtime and archive/document/lock integrity; required for offline `--archives` |
| `--native-inputs INPUTS_JSON` | Reuse a recorded helper only after matching tested commit, `nativeTree`, size and hash |
| `--native-artifact DIRECTORY` | Admit a staged current-commit CI artifact; modified local native sources require a new `--build-native` instead |
| `--rust-root SYSROOT --build-native` | Fetch locked dependencies during preparation, stamp the selected daemon version in a disposable native source tree, then build offline with the pinned compiler |
| `--cargo-cache DIRECTORY` | Copy declared Cargo registry/Git artifacts into the owned Cargo home, not user configuration |
| `--integration` | Prepare the locked, audited third-party profile for full terminal coverage |
| `--archives` | Prepare the integrity-checked transitive npm archive closure for the local consumer fixture |
| `--shared-host EXECUTABLE` | Record the explicit isolated shared host and its hash |
| `--run-root DIRECTORY` | Parent for disposable execution roots; must be outside the tested checkout, with no ancestor `.git` or `.cargo/config[.toml]` (default is the fixed system temporary parent, not inherited TMPDIR/HOME) |

Windows consumer CI explicitly supplies `--run-root "$RUNNER_TEMP"`: owned runtime/source/consumer trees use the declared runner storage, not inherited TEMP/TMP or a hardcoded drive. Native compilation keeps its established path policy. Neutral Git/Cargo ancestry checks apply to both. The execution environment deliberately keeps `UV_THREADPOOL_SIZE=4`: controlled 4/16-thread comparisons did not establish a consistent cross-platform benefit or remove the Windows unpack bottleneck, so higher concurrency is not assumed to improve these workloads.

Preparation without native options supports types, product logic/SDK, smoke and affected UI/card/fallback-logging groups. Requirements come from discovered structural categories, not source-file impact or suite names alone. The complete `unit` union contains actual native and installed-profile integration tests and therefore needs their inputs; use `product`, groups or a feature command for local feature work. Every ordinary executed Occipital helper must match the tested commit and native source snapshot, not just `--version`. There is no published-binary fallback. A cached artifact is usable only when its recorded source and bytes still match.

Execution starts a fresh sanitized process tree **before** importing host/production modules, with owned HOME, agent/config/session/temp/cache roots outside the tested checkout and controlled tool PATH. Node startup controls, credentials, proxy settings, user Git/npm configuration and service-discovery state are not inherited. This guarantee concerns the spawned test tree, not the caller's already-running shell/npm process. The bootstrap validates actual Node identity, host manifests, CLI location and SDK/TUI class identity. Direct `node --test` or fixture invocation without the harness context is not a supported shortcut.

This is reproducible-input isolation, **not a security sandbox against malicious dependency code**. Environment allowlists, sentinels and network namespaces do not deny all host filesystem access. npm installation lifecycle scripts are disabled. Kernel memory/process containment is a separate safety boundary; neither it nor a passing hermeticity check certifies arbitrary dependency code as safe.

For changes to preparation, bootstrap, environment sanitization or child-launch boundaries, compare the relevant checks using identical prepared inputs under clean and deliberately polluted caller environments. Pollute fixture-owned HOME/Pi settings/extensions/auth, competing Pi/PATH entries, Node startup/module lookup, terminal/locale, Git/npm configuration, proxies, service discovery and caches as applicable. Use observable startup/configuration sentinels; require unchanged selected coverage and semantic results, no unintended execution/access effects inside the spawned test tree, and unchanged fixture configuration. The caller's already-running process is outside that guarantee. Compare outcomes and concrete counters, not timestamps, PIDs, temporary paths or timings. Exercise A → B → A when host-graph isolation is affected. This is harness validation, not a requirement to execute these controls for documentation-only changes.

Reports retain selected files and explicit filters, every observed test case, counts, runtime/host/source identities and setup/harness/product failure classification. Disposable execution environments are removed after success/failure; the report directory remains available for inspection. Each `scripts/test/run.mjs` invocation writes an atomically replaced `report.json`, a `*.progress.jsonl` stream for run/step start and completion, and—when Node's test runner executes cases—a `*.tests.jsonl` event stream. A timeout or external termination therefore leaves the last valid report plus complete progress records even when no final summary can be written. A POSIX regression holds a test with a real live timer, force-kills its separately owned whole process group and verifies the persisted start event remains readable and is reconstructed as an unfinished case. A never-settling Promise alone is not a valid hold: Node may cancel it when the event loop has no live work.

The Node event reporter records test dequeue/completion with workspace-relative file, test name, nesting/line where supplied by Node, status and Node's measured `duration_ms`. The final run report includes every completed case, currently active cases, the 20 slowest tests and 20 slowest suites; the console prints the top 10 slowest tests. A trailing incomplete JSONL record is identifiable and does not invalidate preceding events. `test:feature` additionally keeps its own `report.json` and `progress.jsonl`, atomically recording the currently running stage, its start/end time, status and selected child report/progress filenames. When a child runner throws after writing a classified report, the feature report preserves that child failure status/reason; only an exception without a classified child report becomes `harness-failed / runner-exception`. Native-build test runs use the same per-case reporter. For stable Rust `libtest`, individual cases and the Cargo step duration are recorded, but libtest does not expose reliable per-case elapsed times; the report states this limitation rather than inventing timings. Durations are measured on the current machine/run and locate bottlenecks; they are not portable performance thresholds.

On POSIX, interruption terminates the test process group, including descendants; Windows uses explicitly declared `taskkill /T`. Native build inputs and prepared dependency stores remain available for subsequent runs. Failed preparation removes only its newly allocated runtime tree; earlier successful inputs and explicit caches remain available. Runtime ancestry is checked again before execution, so later parent Git/Cargo configuration cannot become an undeclared test input. Physical selected-CLI/Python-startup controls belong to the harness CLI group, not the portable node layer. The optional `PiTerminal({ jobControl: true })` fixture uses the declared Bash and Python tools to launch Pi as a real foreground job after the shell prompt. Suspend checks must observe Bash's stopped-job state before `fg`, not rely on signaling an orphaned PTY group. Cleanup resumes/terminates the separately owned job group as well as the shell; complete validated group-ID records prevent empty/partial startup files from becoming process-group-zero signals. Reports explicitly distinguish inapplicable platform entries from performed checks; missing required inputs never become green skips.

Native-build controls use a **separate Pi-free descriptor**, not `prepare.mjs`'s general Pi inputs:

```sh
node scripts/test/prepare-native.mjs --rust-root /absolute/path/to/rust-1.99.0 \
  --output /absolute/path/to/native-build-inputs
npm run test:rust-harness -- --inputs /absolute/path/to/native-build-inputs/inputs.json
```

`native-harness.mjs` uses the existing `prepare-native.mjs` descriptor (schema 1 / kind `native-build`) and Node's test runner for all `.test.ts` / `.test.mjs` files under `tests/native-build/`. It verifies the selected Node, pinned Rust and unstamped source snapshot without installing Pi. Its real `checkCargoAncestry` control proves that a poisoned ancestor config is effective in the positive control but absent from the neutral materialization. Producers run this suite once **before stamping**, separately from workspace product tests and later artifact admission. Node consumers run no native-build controls and provision neither Rust nor MSVC.

On Linux, append `--network-isolated` to `scripts/test/run.mjs` (or through npm's `--`) to use declared bubblewrap with a real network namespace, for example `npm run test:harness -- --inputs /absolute/path/to/prepared/inputs.json --network-isolated`. Local fixture endpoints remain real; public egress is denied for children too. `test:harness` checks trusted connection-file ancestry, exactly one successful local HTTP request and a public socket failure of `ENETUNREACH`. This is not a `fetch` mock. Elsewhere the built-in flag fails explicitly: equivalent OS/container enforcement requires platform-specific verification. Prepared-local inputs and sanitized environments alone do not establish OS-enforced egress isolation; current non-Linux CI has that verification gap.

## Make shortcuts

GNU Make/POSIX-shell entry points route checks to the same runner. `make` prints help only. Supply absolute `INPUTS`; there is no helper discovery or implicit preparation during test execution. Optional `JOBS=N` forwards the same file bound for ordinary test/feature/focus/product/native/CLI/release targets; fixed type/Rust/consumer targets reject it instead of silently ignoring it. GNU Make's own `-j` is not a substitute for the runner's single bounded file pool.

| Target | Scope |
| --- | --- |
| `make deps PI_VERSION=1.0.0 PREPARE_OUTPUT=...` | Prepare exact host dependencies; no implicit native build |
| `make build RUST_ROOT=... CARGO_HOME=...` | Explicit offline locked local release build and colocated copy; requires pinned sysroot and owned prefilled Cargo home with no user config |
| `make check INPUTS=...` | Strict selected-host TypeScript |
| `make check-native INPUTS=...` | Offline Rust fmt, then strict all-targets Clippy |
| `make test INPUTS=...`, `make test-gc INPUTS=...` | Same unit/SDK suite with mandatory GC and same-source native inputs |
| `make test-focus INPUTS=... TEST_FILES=... TEST_PATTERN=...` | Local comma-separated unique basenames or structural paths and optional regex; GC/truecolor retained |
| `make test-rust INPUTS=...` | Offline workspace tests and doctests |
| `make test-rust-harness INPUTS=...` | Native-build discovery including real Cargo ancestry/isolation; requires the separate `prepare-native.mjs` descriptor |
| `make test-native INPUTS=...` | Real same-source helper controls |
| `make test-syntax INPUTS=...` | Short physical syntax CLI; required prepared shared host |
| `make test-terminal INPUTS=...` | Main physical CLI/replay subset; required locked integration profile |
| `make test-release INPUTS=...` | Inert packaging/release regressions |
| `make test-installed INPUTS=...` | Same-source clean consumer with prepared archives and fixture-local registry/download |
| `make test-published INPUTS=... RELEASE_REF=refs/tags/pi-tidy-ui-vVERSION` | Explicit external published-delivery verification, extension releases only |
| `make pack-check` | Development-package dry run, no publication |

Neutral native snapshots and `nativeTree` cover the Rust workspace, pinned Cargo/toolchain/config files and shared `protocol/` inputs. The protocol JSON vectors are compiled into Rust tests with `include_str!`; they must survive GNU/Make snapshot creation and changes to them invalidate native input provenance even when `.rs` files are unchanged. This does not add Pi or `node_modules` to native inputs. Repository JSON uses `*.json text eol=lf`: Git retains text diffs while Windows checkouts preserve the same LF bytes required by raw-hashed native palette fixtures.

The extension has no TypeScript bundling step. `make build` does not select/stamp a release, download inputs, install tools or start services; it disables Rustup automatic installation and checks Cargo/rustc against `rust-toolchain.toml`. `CARGO_TARGET_DIR` selects its build directory and `RUST_TARGET` an explicit target triple. A merely present colocated helper is not test provenance; use prepared native inputs. Native calibration examples are not implicit prerequisites.

```sh
make check INPUTS=/absolute/path/to/prepared/inputs.json
make test-focus INPUTS=/absolute/path/to/prepared/inputs.json \
  TEST_FILES='bash.sdk.test.ts' TEST_PATTERN='^bash timeout'
make test-focus INPUTS=/absolute/path/to/prepared/inputs.json \
  TEST_FILES='syntax-work.test.ts,syntax-host.test.ts'
make test-release INPUTS=/absolute/path/to/prepared/inputs.json
```

`tests/harness/delivery/makefile.test.ts` executes the actual Makefile and GNU wrapper in disposable trees with inert executors, asserting arguments, phase order, outputs, failure propagation and real ABI admission. These are orchestration controls, not actual Rust/CLI acceptance. POSIX/GNU Make applicability is reported separately; platform inapplicability is not missing-input acceptance. `NODE`/`NPM` select existing executables, not runtime installers.

## Test selection and cadence

During the edit–test–fix loop, use affected node/CLI groups and strict types as relevant. Before delivery use common product checks plus affected integrations (`test:feature`); run offline Rust checks when native behavior is affected. `npm test` remains the complete ordinary Node/SDK/GC union, excluding separately executed inert delivery and native-build controls; `test:product` is the native/profile-independent product baseline. `test:native-release` is the inert delivery/release/Make union, not Pi-sensitive packaging or actual helper acceptance. The complete physical union is `--suite cli`; `terminal` and `syntax-terminal` remain local subset aliases. GC and truecolor are supplied by construction; a missing actual `global.gc` or required native/shared/integration input fails instead of dropping checks.

```sh
node scripts/test/run.mjs --inputs /absolute/path/to/prepared/inputs.json \
  --suite groups --groups bash --layer node --pattern '^bash timeout'
node scripts/test/run.mjs --inputs /absolute/path/to/prepared/inputs.json \
  --suite unit --files queued-cards.test.ts,spinner-scheduler.test.ts
node scripts/test/run.mjs --inputs /absolute/path/to/prepared/inputs.json \
  --suite groups --groups footer --layer cli
node scripts/test/run.mjs --inputs /absolute/path/to/prepared/inputs.json \
  --suite groups --groups editor --layer cli
```

Local `--groups` composes feature domains and `--layer node|cli` limits execution. `--files` accepts comma-separated **unique basenames or structural paths relative to `tests/`** (for example `product/footer/footer.sdk.test.ts`), not globs or checkout paths; ambiguous basenames fail. Fixed type/Rust/consumer commands cannot be replaced with unrelated files, and native-build controls require their dedicated runner. Prerequisites follow discovered categories even through a local alias. `--pattern` selects test names; `--skip` forwards an explicit skip regex. Prefer `--skip` for exclusions: a negative name pattern can match a parent test and include the supposedly excluded child. Focused/excluded coverage must be reported, not called a full run. Ordinary Node and CLI suites default to file concurrency **2** and retain `--expose-gc`. Controlled physical suspend pairs established real stopped-interval overlap and lower wall time; jobs=4 exceeded the unchanged aggregate 128-task limit in both full Node and suspend trials, and the intermediate Node jobs=3 also exhausted that envelope. Neither is a supported default. An explicit larger job bound is an experiment within the same resource envelope, not permission to raise its limits. `--jobs N` overrides the positive-integer file-worker bound through direct, npm group and feature entry points. It does not enable concurrent subtests or parallel feature stages and does not bound the number of PTYs/helpers a file starts. Feature types → Node → CLI remain serial; the same requested jobs reaches only its ordinary Node/CLI stages. Fixed type/Rust/consumer entries reject `--jobs`; the separate native-build runner retains jobs=1. Reports retain requested and effective jobs. Explicit jobs=1 is a focused diagnostic/control configuration.

Full physical CLI execution is time-expensive. For local work, use affected groups during editing and relevant integrations before delivery, not automatically every terminal case after every edit. Documentation-only work needs links/claims/diff checks, not product execution. Harness/workflow changes need checks appropriate to their execution and coverage contracts, not only workflow lint. These local choices do not narrow CI.

### Diagnostic test performance results

Ordinary runner results include diagnostic performance data, not only pass/fail. Existing `durationMs`, `slowestTests`, `slowestSuites` and stage/whole-run elapsed times locate slow cases without double-counting parent/child durations. Native consumer geometry controls compare complete source-work observer snapshots across theme/rollback, not a duplicated hand-maintained subset that drops newly added counters. `report.resources.files` adds per-file worker elapsed time, user/system CPU milliseconds and maximum RSS bytes, plus `largestWorkers`, `slowestFiles` and observed file-worker overlap. Feature stage records retain the child jobs/resources; the Pi-free native-build runner retains fixed jobs=1 and the same worker observations.

Physical presentation tests close and reap completed native/reference/replay processes at their final live interaction/event read, before independent variants or modes start. `PiTerminal.close()` retains session/workspace files; defer `dispose()`/`closeTerminals()` until the last borrower finishes and keep outer `finally` registration for failures. Later comparisons use detached real captures/traffic, never synthetic controls or post-close `events()` reads. Required simultaneous native/live active comparisons, normal quit/release checks and atomic same-session transitions remain intact. Keep references live when later checks actually resize/recolor/recapture them (for example shape-write and user Markdown controls); passive replay/native captures, including actual expanded states, can be retained after shutdown. Close each independent mode before the next starts, attempt every grouped cleanup and surface failures. Closing completed processes is a resource-ownership boundary, not a second scheduler or a reduction of semantic coverage. Runner cancellation controls explicitly abort a started child test through its public `AbortSignal`; they do not rely on Node cancelling a never-settling Promise when the event loop becomes idle, which differs between supported Node versions.

The worker collector uses Node's public `process.resourceUsage()` (CPU microseconds converted to milliseconds; maxRSS KiB converted to bytes). It checkpoints a private per-PID record at admission, once per second and at ordinary process exit. These records remain beside the report under the named `resources.observations` directory even on interruption. Final/partial/missing observations are distinct: an abrupt death may leave only the last checkpoint, and a worker that never reached admission has null metrics with an explicit reason. A checkpoint's high-water value covers that worker's lifetime **through its observation**, not an individual test phase. Collection adds no product instrumentation, signal handlers, heap dumps or automatic retries.

Worker CPU/RSS **exclude descendants**: Pi PTYs, helper and shared-host processes may consume substantially more RAM. Do not interpret the worker ranking as an exact ranking of complete test trees. On Linux inside the dedicated verified test scope, `aggregateBefore`/`aggregateAfter` and step snapshots record kernel `memory.peak`, `memory.events`, `pids.peak/events`, `cpu.stat`, effective affinity and limits. These are **scope-lifetime** measurements; a feature's types/Node/CLI stages share that scope. Do not subtract cumulative peaks or sum workers' independent peaks to invent per-case or aggregate memory. The outer scope receipt's `preCleanup` is sampled after the target command exits and before whole-scope teardown; `finalLifetime` is sampled after teardown. A removed cgroup can make final counters unavailable, so a pre-cleanup peak is not relabeled as a measured final cleanup peak; unavailable counters stay explicit. Non-Linux or non-dedicated scopes report aggregate collection unavailable, not zero.

To investigate a slow or RAM-intensive ordinary file, use its `rerun` argument array (retaining explicit name/skip/network filters) or select it explicitly with `--files` and `--jobs 1`, inside a **new** ordinary guard scope with a new receipt. The separate Pi-free native-build entry keeps its fixed selection: rerun that dedicated entry in a new scope rather than pretending its files are admitted by the Pi runner. Keep the same prepared Node/Pi/helper and resource limits. That bounded scope measures the focused runner **and all its descendants**, including launcher/cleanup overhead; it is not Pi-only RSS. Add an explicit name pattern for a case only when that pattern preserves its necessary setup/ordered scenario. Examine `activeTests`, the persisted test event stream and partial worker records if the run died. Regular reports have no automatic machine-dependent anomaly threshold. Detailed product CPU/allocation/GC profiling remains the separate opt-in [performance framework](performance-testing.md); it changes measurement identity and is not silently enabled for ordinary tests.
