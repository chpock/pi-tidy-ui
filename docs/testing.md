# Testing and coverage

This is the maintained guide to reproducing pi-tidy-ui checks, not a journal of past runs. Use a repository checkout; the npm package contains runtime code/documentation, not the harness or fixtures. Visual behavior is specified in the [presentation contracts](README.md#extension-host-and-presentation); the root [user guide](../README.md) explains everyday use, and integration boundaries are described in [architecture](architecture.md).

Current [platform support](releases.md#supported-platforms) is GNU Linux x64/ARM64, macOS x64/ARM64 and Windows x64. **Windows ARM64 is temporarily unsupported for the entire extension** because of disproportionate verification cost. Windows ARM64 stays in the central platform catalogue but is disabled unless repository Actions variable `CI_WINDOWS_ARM64=true`; enabling that platform or citing a historical pass does not establish restored support.

## Requirements and commands

- Node.js >=22.19.0. CI selects exact Node 22.19.0 and 26.7.0.
- An explicitly prepared Pi dependency graph. The compatibility matrix selects minimum Pi 1.0.1 and the exact version resolved once from npm's public `latest` dist-tag during workflow planning, never an independently moving tag or an installed CLI. CLI, SDK, TUI, AI/core, extension imports, type checks and child probes must use the selected coherent graph; Pi-family package version strings need not all be equal.
- For native preparation: provisioned Rust **1.99.0**, including rustfmt and Clippy, and platform compiler/linker prerequisites. User Cargo configuration is not an input.
- For physical CLI tests: POSIX, declared Python 3 with PTY support and the prepared CLI. Python runs with `-I -S`, excluding environment/user/global site startup customizers. No model credentials are needed: the driver uses an offline scripted provider.
- The Linux suspend entries under `cli/native/syntax/linux/` and `cli/shared/syntax/linux/` require real shell job control plus `/proc` stopped-helper evidence; they are platform-inapplicable elsewhere. Four independent transport/terminal-mode files each run SOURCE, STYLE and incremental append serially: all twelve semantic cases, 45-second case bounds and actual 4.5-second stopped intervals remain. They prove bounded wake recovery, physical current/new cards and idle/warm reuse; they do not mock request settlement or defer an already-delivered reply.
- For actual native/owned-syntax CLI tests: a verified same-source Occipital artifact. Only selected shared tests additionally require an explicit Subconscious host executable. Only selected installed-profile tests require `--integration`. Neither prerequisite is imposed by unrelated footer/editor/card tests. Native launch fixtures follow the documented [Occipital executable modes](occipital/runtime.md#executable-entry) and isolate process state with private working, HOME and XDG roots; the daemon has no `--config` argument.

### Real SDK fixture boundaries

- Render-row compatibility is checked against the actual selected SDK, including legacy mutable declarations and Pi 1.6.0's readonly return type. The editor geometry and user image fallback controls require the original frozen row arrays to pass through unchanged. The SDK checks run before the full unit suite in CI; a passing physical CLI run does not cover the type contract.
- The Follow Pi fallback check compares visible code foregrounds against the selected SDK's public `highlightCode` output and requires the card's neutral role only where the classifier emitted no foreground. The palette-recovery control supplies unstyled text explicitly; a Pi version that colors ordinary code text must not silently change the scope of that control.
- Offline tool fixtures import schema builders from the host's `typebox` package, not optional `pi-ai` re-exports.
- Prototype-based `InteractiveMode` fixtures initialize host-owned fields used by real public UI methods, including an empty `extensionDialogs` stack for the no-open-dialog state and an empty `pendingBashComponents` collection for queued-message construction. Native activity probes release their fixture-owned indicators in `finally` even after assertion failure; restoring Toolview deliberately does not dispose Pi's native activity clock.
- Prototype-publication fault controls cover tool, user, editor and shared-container hooks and throw only after earlier native hooks have actually been written. They require exact prior descriptors, including inherited methods with no own descriptor, and unchanged draft/paste/cursor state after failure. Native-status rebinding controls use the real SDK method and fail after placement has changed: rollback must restore the placement flag and rebind the same editor before releasing its presentation hooks, without disposing native activity or repeating the rebind on idempotent cleanup. Assertions inspect primitive identities and descriptor fields, not a live terminal graph.
- Late child admission controls use the selected SDK's `Container.addChild` with a synthetic tool whose callable update method cannot be wrapped, and a real `UserMessageComponent` with a test-induced exception after a hook write. They prove that the child stays attached and that previous descriptors and native rows are restored before test cleanup, with one warning and one owner-scoped compatibility failure. Separate controls require the original native add's exception and an exception from the already-entered warning path to propagate unchanged. Entry-level controls inject the same real-user fault after presentation attachment, before activation, during `describe`, and with a ready route. They check actual factory/describe/close counts, descriptor restoration before cleanup, rejected late acquisition, zero terminal-return acquisition with the native preference still On, and then successful explicit Reapply and normal terminal reentry. The ready-route control holds cleanup while Reapply attaches the replacement; the replacement must wait before acquiring. These injected faults are not evidence of a failure on an unmodified stock component.
- Queued performance correctness exercises the same native queue method in Native, Off and On, independently of the product queue fixture. Select `--suite groups --files harness/performance/sdk-driver.test.mjs` explicitly on each affected host/runtime profile when native queue construction changes: the standard `compatibility` suite includes product/integration and packaging harness files, not performance harness files.
- Same-default-editor controls exercise the selected SDK's actual raw or expanded transfer, preserve collapsed-paste/cursor/undo/history state and exact descriptors, and count public expansion calls separately from adapter validation. Raw matches require no extra expansion; expanded validation is bounded to rebinding, never warm frames. Foreign expanded-text methods/accessors receive no extra validation calls, and absent/additional transfers fail closed without changing the draft.
- The late-editor SDK controls start the adapter while Pi's selector occupies the input slot. Closing the selector through Pi attaches the same editor without an immediate rebind; one microtask allows the guarded native call to move the same live indicator to the separate status container. Opening another selector before that microtask keeps the selector mounted and blocks the rebind. A regression uses Escape in Pi's provider and authentication-method menus to cross this boundary: the second close must produce exactly one deferred rebind, preserve the current editor, draft, cursor and indicator, and show the indicator in actual rendered rows. After successful transfer an ordinary editor reattachment adds no rebinds. Restoring the installation before the first microtask allows synchronous native cleanup but no subsequent deferred route. The assertions use call counts and component identity, not elapsed time.
- Native-user and isolated stock-editor lifetime controls remove their first components, refresh native traversal and require collection while the adapter and a peer remain live; removed editor geometry cannot keep metadata visible. They advance a job and call GC before dereferencing, retaining only collected/not-collected booleans. The editor control deliberately has no remaining SDK owner: real `InteractiveMode` retains its default editor for reuse across selectors. A separate later-renderer control invalidates the previous native-status visibility sample and verifies that cleanup preserves the later method owner.
- Static host-separation controls permit narrow public application-context/configuration imports and generic terminal display utilities, while rejecting native component shapes and direct classification bindings in entry/application composition. Aliases, mixed and type-only imports, re-exports, literal dynamic loads and private SDK paths must follow the same boundary, including relative private TUI component paths; generic display utilities retain their narrow allowed bindings. Entry must not forward moved native bindings, and lower-layer owners must not import host implementations even for types. Moving the installer unchanged to an application file does not satisfy it. Reverse-direction controls reject native-host imports of application/source/funding owners or presenter implementations while allowing its narrow type-only presentation shapes and existing pure input/status projections.
- Source-execution fixtures supply the complete provider capability. Delivery/measurement wrappers around a real broker forward recovery, worker-unavailable and exhausted-route inputs to that broker, not dummy lifecycle implementations. Local/manual providers expose explicit unsupported lifecycle methods; factory/retirement/recovery evidence comes from actual broker/client controls. Direct suspension controls deliver the same generation-qualified retirement origin used by application composition. A stopped direct SOURCE observation must refuse without replacing retained input; its caller supplies the latest input after resume, while actual SDK updates use the existing deferred-reflection marker. Neutral-fallback initializing/unavailable controls expect one funded native source before readiness, but zero SOURCE/STYLE or Pi calls; Native Off expects no native source. They observe canonical admitted data rather than a card-side deferred-provider marker. Negotiated-cap card controls distinguish real Pi token colors from the peer's native default-code ranges; `ReadyCardPaint.origin` remains the selected palette origin, not a SOURCE executor tag. Pi transaction-lifetime/exception controls admit the independent native input before sampling their Pi baseline, retaining their original exact Pi charge/release assertions; Pi removal must not be mistaken for native-input removal. Startup input measurement expects one native and one Pi measurement, with no repeated measurements on equal aliases or warm demands. Empty local source exactness must not delay immediate classifier-free Pi rows. Separate healthy-route current/reused-key diagnostic controls require both accepted-result and permission observations, zero physical credit before permission delivery, coalesced notices and same-key reentry without overlap. These supplied-callback controls witness settlement ordering, not an ordinary UI race; an unavailable-route no-RPC assertion alone cannot prove the physical key gate. A separate disposed-owner control holds three known streams, requires two CLOSE jobs plus one queued cleanup at disposal, then settles the held jobs and verifies the final already-owed CLOSE, exact zero credit/bookkeeping and no new card admission. SOURCE/CLOSE physical-boundary controls use a real broker's synchronous retirement callback to observe released logical membership, still-held byte credit and same-key exclusion; callback observations are primitive and assertions run after delivery, so a callback failure cannot masquerade as a passing guard.
- Pure SOURCE/STYLE policy controls exercise purpose-specific satisfaction, refusal, provider and deadline projections independently of execution. Real owner/client controls additionally require useful STYLE-only recovery over retained scopes with zero SOURCE replay, and one actual failure-time deadline shared by the dispatched owner and a paused/late coalescer. Local rebinding must preserve that deadline; deterministic preflight denial has no timed retry. A queue visit to one parsed source on its unchanged route checks for one passive inspection, no promoting text-version reads, and one physical-key scan. A forced pool-pressure check after that SOURCE-only visit verifies that polling does not evict a more recently used peer. A second control holds both physical slots in another controller, attempts a first parse, forces pressure and releases the slots. The waiting input displaces an earlier text use and then parses once. A fresh peer borrow followed only by more queue visits keeps the peer instead. Byte-credit controls size a real waiting request, borrow a peer, and force pressure with the last slot still free or subsequently occupied. Neither case may displace the peer; the evicted, never-sent input remains eligible for fallback, not automatic native retry. A separate card-level control defers preparation of changed input, evicts its old text and checks the exact replacement sent after slots reopen. A refused input with no admitted snapshot is revisited without reading the retry clock. An incompatible route replacement without reobservation must instead validate the replacement generation before sending its text. With a native request slot available, revisiting an already published nonempty group must confirm its member colors without constructing retention or range accounting reports. The test does not cover the separate check made when all slots are occupied. A pressure control distinguishes a recently checked entry with no ranges from an evicted entry and from installed empty ranges. A separate zero-source group revisits an already published palette and observes the retained display without any request-eligibility reads of the provider or retry clock. After a malformed STYLE reply, a palette-only change also triggers a control that removes the last group member inside its selection callback. The empty group must publish the new palette without a second request for that member; when one member survives, only its missing context is requested. A same-key Bash rewrite inside the predicate after a local funding refusal must send no STYLE before the replacement SOURCE settles, then request its new context and publish its colors. These are controlled reentry checks, not observations of the stock palette predicate mutating sources. Pure checks do not replace these real scheduling/publication boundaries. Grouped worker-recovery fixtures explicitly queue their registered preparation before requiring whole-group paint; registration alone does not adopt standalone sources. Empty prepared targets use the ordinary pre-ready SOURCE record fee but no RPC/recovery interest. The parsed-to-empty controls require a current, exact empty display with no SOURCE acknowledgement or additional SOURCE/STYLE calls, both with a controlled peer and with the real helper. The controlled progression requires a fresh native acknowledgement on regrowth; the native empty-Bash tests separately retain acknowledgement on finalization with an empty suffix and nonempty total input. Terminal-stop controls distinguish immediate cancelled observation from completion of bounded connection cleanup before counting remaining timers. Broker observer controls validate every cold snapshot, including error sanitization, and require actual delivery of recovery admission after the acquisition guard clears; a raw cold-count range alone cannot witness that opportunity. Publication and guard-clear notices may coalesce, but warm snapshot/stat/repeated-start reads add exactly zero notices and factory calls. The recoverable-card completion control keeps its original client Promise through readiness, checks the exact foreign jobs/bytes and describe-only traffic while credit is held, and proves that foreign-owner disposal alone does not refund it. Only actual request settlement may wake one current SOURCE and the observed missing STYLE; the same observation must then include matching native acknowledgement, actual compiled native ranges for the current card and physical-credit release without another Pi classification. Synchronous preparation receipts are not asynchronous native-completion receipts: a prior `waiting` receipt need not be reissued when SOURCE/STYLE later update paint. Terminal-loss siblings separately retain their local-completion behavior while foreign requests remain held. Client snapshot assertions await client-level completion, including coalesced provider delivery; awaiting the broker's acquisition operation alone does not mean its cached client projection was delivered. Client palette/menu inspection controls preserve initial-shared history but create no native recovery demand; explicit Off→On preserves an existing service deadline, and due activation is not another automatic recovery cycle. Return-window tests count any legitimate preference probe before Off separately, then require no new episode/timer/probe from ordinary reactivation; service-spacing waits are not proof that no earlier preference tick occurred. The former lifetime owned-restart-limit control follows this selected pacing contract rather than expecting the removed limit. Paused-target and retired-reply controls separate truthful captured acknowledgement from current accepted classification/exactness instead of resetting execution evidence on every new target. Legacy parser-restart controls retain fresh parser/wire identities and prior committed semantics, but require minute-spaced later reconstruction rather than permanent exhaustion; repeated growth preserves that gate. Provider-change controls reject late adoption/useful-classification credit while automatically serving the already admitted unmet target, without requiring a redundant equal observation. Existing malformed-body and typed-temporary controls supply the paced-retry contrast. ### Ordinary feature work

Start with one explicit graph (Linux, Node 22.19.0, Pi 1.0.1), not the operator's Pi or the entire compatibility matrix. A fresh Git clone with its reachable release history/tags is sufficient: no historical `.test-artifacts`, repository `node_modules`, installed Pi or personal transcripts are needed. The preparer itself uses Node built-ins and installs the selected graph into its owned runtime; do not install a second graph in the checkout first. Provision Node/npm compatible with each other, Git and the platform tools below. On local Linux graphical sessions, wrap **all fallible test commands below** in the [verified ordinary scope](#local-memory-containment-and-assertion-diagnostics); raw runner examples show selection arguments, not permission to run uncontained.

```sh
npm run test:prepare -- --pi-version 1.0.1 --output /absolute/path/to/feature-inputs
INPUTS=/absolute/path/to/feature-inputs/inputs.json

# Tight edit loop: refresh sources without reinstalling/copying the sealed dependency tree.
node scripts/test/prepare.mjs --refresh-inputs "$INPUTS"
npm run test:group -- --inputs "$INPUTS" --groups footer --layer node

# Feature acceptance: types + common product SDK/logic/GC + smoke + affected real CLI.
npm run test:feature -- --inputs "$INPUTS" --features footer --refresh --output /absolute/path/to/footer-receipts
```

Replace `footer` with a comma-separated combination of `summaries,bash,edit,write,user,queued,editor,footer,layout,lifecycle,activity,settings,terminal-colors,logging,syntax,native,shared,profile,harness,delivery`. A coupled test belongs to one file but may be selected by multiple domains; the command de-duplicates it. `--features ''` is the common baseline. `--affected-only` is a local composition/debugging option that omits the common baseline and default type stage, not a CI selection mechanism or replacement for feature acceptance. Add `--check-types` to retain types with that local option. CI independently runs its fixed complete suites; a local feature command is not equivalent to full CI.

`--refresh`/`--refresh-inputs` recheck the selected Node/host, manifest/lock, complete owned dependency bytes and neutral runtime ancestry. They remove old source files (including deleted tests) before copying current sources. Each runtime owns its source inventory; failed replacement preparation cannot overwrite the surviving runtime's inventory, and an interrupted refresh retains attempted additions for later cleanup. The runner rejects that incomplete inventory before launching children; successful refresh restores execution. Legacy unsealed descriptors retain byte-checked execution but cannot refresh without one fresh preparation. Reports count dependency installations/copies and source copies. Changed graph inputs require preparation again; changed native inputs require a new verified helper. Refresh does not relabel an old helper's provenance or regenerate a source-bound consumer archive closure; after source changes, prepare that closure again before consumer execution. It requires a sealed graph from the current preparer; older inputs need one fresh preparation.

The 2–3-minute end-to-end target applies to the **local feature loop only**, not full CI. It is a guideline, not a timeout or pass condition; justified variation is acceptable. Include preparation and prerequisite costs, distinguish owned-cache/source-refresh runs from cold setup, and report longer required integrations rather than hiding them. Do not run full compatibility acceptance for a local presentation-only edit. The [structural catalogue](../scripts/test/catalog.mjs) discovers executable membership; feature subdirectories select local groups, not source-impact CI routes.

### Provision optional inputs from a fresh clone

Ordinary types/product/footer/editor preparation needs neither Rust nor a native/shared service. Physical CLI needs declared Python 3 (standard-library PTY on POSIX) and Bash for real job-control cases. If selecting another Node executable, `--node` selects that actual runtime; `--tools /absolute/tools.json` may supply an absolute `npm` JavaScript CLI entry compatible with it. No tool path or private tools map from a historical run is a prerequisite.

Native tests additionally need the pinned Rust **1.99.0** sysroot with rustfmt/Clippy and the host C/C++ compiler/linker. Provision it separately, never during test execution. For example, using an already provisioned explicit Rustup executable, install into fresh owned stores (not user defaults):

```sh
TEST_ROOT=/absolute/new-test-input-root
mkdir -p "$TEST_ROOT"
export RUSTUP_HOME="$TEST_ROOT/rustup" CARGO_HOME="$TEST_ROOT/cargo"
/absolute/rustup toolchain install 1.99.0 --profile minimal --component rustfmt --component clippy
RUST_ROOT=$(/absolute/rustup run 1.99.0 rustc --print sysroot)
# Supply --rust-root "$RUST_ROOT" --build-native to preparation, then execute offline.
```

For Linux x64 shared integration, use the same pinned public input as CI. This is explicit **preparation/network acquisition**, not runtime discovery or a download from inside a test:

```sh
mkdir -p "$TEST_ROOT/shared-host"
curl --fail --location --output "$TEST_ROOT/shared-host/host.zip" \
  https://github.com/cortexkit/subconscious/releases/download/subc-core-v0.20.83/ck-subc-linux-x64.zip
printf '%s  %s\n' c905fd8c5eba045c38fb61dd0c6c0ffc8254ae2cb0be50ef1017cde5470e62c4 \
  "$TEST_ROOT/shared-host/host.zip" | sha256sum --check
unzip -j "$TEST_ROOT/shared-host/host.zip" ck-subc -d "$TEST_ROOT/shared-host"
chmod 700 "$TEST_ROOT/shared-host/ck-subc"
# Supply --shared-host "$TEST_ROOT/shared-host/ck-subc" to preparation.
```

Shared fixtures explicitly set `port: 0` in their private `subc.jsonc`, in addition to private HOME/config/runtime/discovery roots. The pinned host [supports OS-assigned loopback ports and publishes the actual bound port](https://github.com/cortexkit/subconscious/blob/subc-core-v0.20.83/crates/subc-daemon/src/bootstrap.rs#L1438-L1501); no find-free-port probe, retry or cross-run lock is needed. The simultaneous real-host control `tests/cli/shared/syntax/shared-host-isolation.cli.test.mjs` verifies distinct published ports, independent helper processes and real traffic while both hosts remain live. Leaving the production default port implicit makes otherwise-private fixtures collide during parallel file execution.

All private Subconscious test-host launchers use [`sharedHostEnv`](../tests/fixtures/shared-host-environment.mjs), which composes the existing sanitized `childEnv` with `SUBC_CGROUP_PLACEMENT=disabled` and **`TOKIO_WORKER_THREADS=2`**. This explicit integration-fixture budget keeps hosts and managed helpers inside the verified aggregate scope and avoids multiplying CPU-count-sized async worker pools when independent files run concurrently. [Tokio's worker setting](https://docs.rs/tokio/1.52.3/tokio/runtime/struct.Builder.html#method.worker_threads) otherwise defaults to available cores; the fixture does not pin CPUs or change ordinary Node/Cargo, Occipital's existing worker/actor policy, production/user host settings or benchmark conditions. Shared integration therefore certifies the real host with two Tokio async workers, not its CPU-derived default pool size. Required concurrent hosts, physical jobs and peer progress remain real; the aggregate 2 GiB/128-task limits are unchanged. The environment regression checks polluted callers and an actual child, including that ordinary child environments do not acquire this host-only policy.

Suspend evidence records monotonic stopped/resume boundaries and asserts at least 4.5 seconds actually stopped. The fixture waits to a monotonic deadline, rescheduling only a positive remaining interval: a nominal `setTimeout(4500)` can return a fraction of a millisecond early. This keeps the existing 4-second request deadline plus full 500 ms margin, without shortening the pause or increasing the 45-second case bound.

That asset recipe establishes Linux x64 input provisioning only; other platforms require their own explicitly verified host input and are not covered by this archive. `--integration` installs the tracked audited `tests/fixtures/integration-profile/{package.json,package-lock.json}`; `--archives` prepares the consumer closure described below. Missing selected prerequisites fail before cases, never become successful skips.

### Clean-state harness acceptance

For changes to the harness itself, use a separate **real Git clone**, including the history/tags needed for native version stamping. Start with no generated artifacts, installed dependency tree, Pi settings or operator caches. Follow the ordinary preparation and verified-scope commands above/below, run types plus representative product/harness and real offline-provider CLI, then explicitly provision/build the optional native/shared lane and run it. Repeat prepared execution with `--network-isolated` on Linux. First installation may acquire declared public inputs; clean clone is not an air-gapped install.

The maintained tiny admitted-fixture controls exercise the **actual** `execute` API and runner CLI at jobs=1/2, including production resource preloads. Parent-held peer gates prove serialization/bounded overlap without speed thresholds; rejection, cancellation, abrupt startup and SDK-bootstrap failure preserve peer evidence. POSIX SIGINT/SIGTERM controls start two workers with real descendants and verify interruption reports, reaping and root cleanup; they do not establish Windows signal acceptance. Native-build fixture controls remain fixed jobs=1 and use inert Rust, not compiler acceptance.

This is a standalone acceptance procedure, **not** a discovered `tests/harness` case, automatic feature prerequisite or extra CI job. Never recursively clone/download/build native dependencies from a network-isolated ordinary test. A clone of HEAD cannot prove uncommitted candidate changes: before commit authorization, overlay only the reviewed intended source files/deletions, record the resulting exact source identity and label it prospective-clone evidence. Do not copy generated state or create a commit just for that proof. Final committed-clone evidence needs the separately authorized source commit.

### Prepare broader inputs, then execute

Preparation owns dependency resolution, allowed public-network acquisition and native building. It records source commit/tree identity, native-source `nativeTree`, exact Node executable/version, selected Pi packages/lock, declared tools and required artifact hashes in `inputs.json`. It materializes a test tree with its own dependency graph without changing repository manifests/lockfiles or user installations. Preparation uses owned npm/Cargo stores and clean configuration, not user credentials, proxies, `.npmrc`, Cargo config or incidental caches. Unsupported Node engines fail preparation rather than merely warning. Prepared source copies, including Cargo's working directory, live outside the checkout and its ancestor configuration search; the original checkout is not rewritten.

The corpus CSS transformer, `esbuild`, is a direct development dependency, not an extension runtime dependency or an assumed Pi transitive package. Baseline preparation installs the repository manifest/lock; alternate Pi profiles carry the same declared tool into their selected-host manifest. Changing these dependency declarations requires fresh preparation rather than source-only refresh. Parser references intentionally supplied by the selected host graph are described in the [corpus validation contract](../tests/fixtures/highlight-compare/README.md#source-data-and-parse-only-validation).

`npm run test:prepare -- ...` invokes the same preparer. Its default output is `.test-artifacts/harness/1.0.1` (or the selected Pi version); explicit separate outputs avoid mixing host/runtime inputs. For the broader native/Rust/shared/profile/consumer union, with the pinned Rust sysroot and shared host already provisioned:

```sh
node scripts/test/prepare.mjs --pi-version 1.0.1 \
  --rust-root /absolute/path/to/rust-1.99.0 --build-native \
  --integration --archives --shared-host /absolute/path/to/ck-subc \
  --output /absolute/path/to/prepared-pi-1.0.1 \
  --run-root /absolute/path/to/runtime-parent

npm run check -- --inputs /absolute/path/to/prepared-pi-1.0.1/inputs.json
npm test -- --inputs /absolute/path/to/prepared-pi-1.0.1/inputs.json
npm run test:native-release -- --inputs /absolute/path/to/prepared-pi-1.0.1/inputs.json
npm run test:rust-check -- --inputs /absolute/path/to/prepared-pi-1.0.1/inputs.json
```

Use separate output directories for each Node/Pi selection. To reuse the verified current-source helper in a second host graph, set `PI_VERSION` to the exact alternate version recorded by CI (not a tag/range):

```sh

  --native-inputs /absolute/path/to/prepared-pi-1.0.1/inputs.json \

A → B → A controls detect cross-version contamination. These examples select checks, not a claim of full compatibility acceptance. Execution rejects a changed tested commit/tree; source-only refresh is described below.

| --- | --- |

| `--tools FILE` | JSON of explicit absolute prerequisite tool paths, including the npm CLI JavaScript entry when needed |

| `--integration` | Prepare the locked, audited third-party profile for full terminal coverage |

The execution environment deliberately keeps `UV_THREADPOOL_SIZE=4`: controlled 4/16-thread comparisons did not establish a consistent cross-platform benefit or remove the Windows unpack bottleneck, so higher concurrency is not assumed to improve these workloads.

Preparation without native options supports types, product logic/SDK, smoke and affected UI/card/fallback-logging groups. Requirements come from discovered structural categories, not source-file impact or suite names alone. The complete `unit` union contains actual native and installed-profile integration tests and therefore needs their inputs; use `product`, groups or a feature command for local feature work. Every ordinary executed Occipital helper must match the tested commit and native source snapshot, not just `--version`. There is no published-binary fallback. A cached artifact is usable only when its recorded source and bytes still match.

Execution starts a fresh sanitized process tree **before** importing host/production modules, with owned HOME, agent/config/session/temp/cache roots outside the tested checkout and controlled tool PATH. Node startup controls, credentials, proxy settings, user Git/npm configuration and service-discovery state are not inherited. This guarantee concerns the spawned test tree, not the caller's already-running shell/npm process. The bootstrap validates actual Node identity, host manifests, CLI location and SDK/TUI class identity. Ordinary entries executed by Node's test runner import `tests/fixtures/test-guard.mjs` first so direct execution fails before any product or host module is evaluated. The harness checks this import order across the catalogue; Pi-free native-build tests use their separate bootstrap. Direct `node --test` or fixture invocation without the harness context is not a supported shortcut.

This is reproducible-input isolation, **not a security sandbox against malicious dependency code**. Environment allowlists, sentinels and network namespaces do not deny all host filesystem access. npm installation lifecycle scripts are disabled. Kernel memory/process containment is a separate safety boundary; neither it nor a passing hermeticity check certifies arbitrary dependency code as safe.

For changes to preparation, bootstrap, environment sanitization or child-launch boundaries, compare the relevant checks using identical prepared inputs under clean and deliberately polluted caller environments. Pollute fixture-owned HOME/Pi settings/extensions/auth, competing Pi/PATH entries, Node startup/module lookup, terminal/locale, Git/npm configuration, proxies, service discovery and caches as applicable. Use observable startup/configuration sentinels; require unchanged selected coverage and semantic results, no unintended execution/access effects inside the spawned test tree, and unchanged fixture configuration. The caller's already-running process is outside that guarantee. Compare outcomes and concrete counters, not timestamps, PIDs, temporary paths or timings. Exercise A → B → A when host-graph isolation is affected. This is harness validation, not a requirement to execute these controls for documentation-only changes.

Reports retain selected files and explicit filters, every observed test case, counts, runtime/host/source identities and setup/harness/product failure classification. Disposable execution environments are removed after success/failure; the report directory remains available for inspection. Each `scripts/test/run.mjs` invocation writes an atomically replaced `report.json`, a `*.progress.jsonl` stream for run/step start and completion, and—when Node's test runner executes cases—a `*.tests.jsonl` event stream. A timeout or external termination therefore leaves the last valid report plus complete progress records even when no final summary can be written. A POSIX regression holds a test with a real live timer, force-kills its separately owned whole process group and verifies the persisted start event remains readable and is reconstructed as an unfinished case. A never-settling Promise alone is not a valid hold: Node may cancel it when the event loop has no live work.

The Node event reporter records test dequeue/completion with workspace-relative file, test name, nesting/line where supplied by Node, status and Node's measured `duration_ms`. The final run report includes every completed case, currently active cases, the 20 slowest tests and 20 slowest suites; the console prints the top 10 slowest tests. A trailing incomplete JSONL record is identifiable and does not invalidate preceding events. `test:feature` additionally keeps its own `report.json` and `progress.jsonl`, atomically recording the currently running stage, its start/end time, status and selected child report/progress filenames. When a child runner throws after writing a classified report, the feature report preserves that child failure status/reason; only an exception without a classified child report becomes `harness-failed / runner-exception`. Native-build test runs use the same per-case reporter. For stable Rust `libtest`, individual cases and the Cargo step duration are recorded, but libtest does not expose reliable per-case elapsed times; the report states this limitation rather than inventing timings. Durations are measured on the current machine/run and locate bottlenecks; they are not portable performance thresholds.

On POSIX, interruption terminates the test process group, including descendants; Windows uses explicitly declared `taskkill /T`. Native build inputs and prepared dependency stores remain available for subsequent runs. Failed preparation removes only its newly allocated runtime tree; earlier successful inputs and explicit caches remain available. Runtime ancestry is checked again before execution, so later parent Git/Cargo configuration cannot become an undeclared test input. Physical selected-CLI/Python-startup controls belong to the harness CLI group, not the portable node layer. The optional `PiTerminal({ jobControl: true })` fixture uses the declared Bash and Python tools to launch Pi as a real foreground job after the shell prompt. Suspend checks must observe Bash's stopped-job state before `fg`, not rely on signaling an orphaned PTY group. Cleanup resumes/terminates the separately owned job group as well as the shell; complete validated group-ID records prevent empty/partial startup files from becoming process-group-zero signals. Reports explicitly distinguish inapplicable platform entries from performed checks; missing required inputs never become green skips.

Native-build controls use a **separate Pi-free descriptor**, not `prepare.mjs`'s general Pi inputs:

npm run test:rust-harness -- --inputs /absolute/path/to/native-build-inputs/inputs.json

`native-harness.mjs` uses the existing `prepare-native.mjs` descriptor (schema 1 / kind `native-build`) and Node's test runner for all `.test.ts` / `.test.mjs` files under `tests/native-build/`. ## Make shortcuts

GNU Make/POSIX-shell entry points route checks to the same runner. `make` prints help only. Supply absolute `INPUTS`; there is no helper discovery or implicit preparation during test execution. Optional `JOBS=N` forwards the same file bound for ordinary test/feature/focus/product/native/CLI/release targets; fixed type/Rust/consumer targets reject it instead of silently ignoring it. GNU Make's own `-j` is not a substitute for the runner's single bounded file pool.

| --- | --- |
| `make deps PI_VERSION=1.0.1 PREPARE_OUTPUT=...` | Prepare exact host dependencies; no implicit native build |
| `make build RUST_ROOT=... CARGO_HOME=...` | Explicit offline locked local release build and colocated copy; requires pinned sysroot and owned prefilled Cargo home with no user config |

| `make test-rust INPUTS=...` | Offline workspace tests and doctests |
| `make test-rust-harness INPUTS=...` | Native-build discovery including real Cargo ancestry/isolation; requires the separate `prepare-native.mjs` descriptor |

## Test selection and cadence

During the edit–test–fix loop, use affected node/CLI groups and strict types as relevant. Before delivery use common product checks plus affected integrations (`test:feature`); run offline Rust checks when native behavior is affected. `npm test` remains the complete ordinary Node/SDK/GC union, excluding separately executed inert delivery and native-build controls; `test:product` is the native/profile-independent product baseline. `test:native-release` is the inert delivery/release/Make union, not Pi-sensitive packaging or actual helper acceptance. The complete physical union is `--suite cli`; `terminal` and `syntax-terminal` remain local subset aliases. GC and truecolor are supplied by construction; a missing actual `global.gc` or required native/shared/integration input fails instead of dropping checks. Feature tags come from test-directory components: root-level `tests/integration/native/*.test.ts` cases are tagged `native`, not `syntax`, and root-level `tests/cli/shared/*.test.mjs` cases are tagged `shared`, not `syntax`. A syntax-only feature selection therefore misses those integration boundaries; select `native` and/or `shared` explicitly when changing their executable or fixture contracts. A test drain relying on `whenSettled()` must assert its `true` result; `false` denotes cancelled work, not successful completion. Whole-source visual comparisons use this passive boundary under the existing ten-second fixture deadline, then independently require publication coverage and every corpus entry's current palette, rule fingerprint, binding revision, complete/exact source version, text and valid range visits. Aggregate publication counts are assertions, not readiness signals; the observer must not repeatedly flush the queue.

Syntax composition has a static choice/provider dependency boundary and a compile-only consumer that rejects settings publication capabilities in client and runtime options. The GC cache-probe's native-option callback has an explicit return type, exposing extra literal properties that callback-return assignability would otherwise accept. The dependency controls exercise aliases, mixed/type-only imports, re-exports and literal dynamic/require routes; application preference coordination remains outside this syntax boundary. Palette-input and menu asset tests observe real provider/source/asset work, not disconnected store counters; actual initial settings reads and confirmations are measured through application-owner/default-factory controls. Preference-lifetime controls distinguish the requested native preference from actual client activation: a detached enablement or a no-op transition keeps a pending theme save, while later active-presentation attachment retires it at actual activation. ### Diagnostic test performance results

Pure SOURCE decision controls compare action and execution/priority projections for admitted versus unfunded input, old acknowledgements, held work, completion, scoped refusal, temporary retries, parser reconstruction, provider replacement and deliberate withdrawal. Physical presentation tests close and reap completed native/reference/replay processes at their final live interaction/event read, before independent variants or modes start. `PiTerminal.close()` retains session/workspace files; defer `dispose()`/`closeTerminals()` until the last borrower finishes and keep outer `finally` registration for failures. Runner cancellation controls explicitly abort a started child test through its public `AbortSignal`; they do not rely on Node cancelling a never-settling Promise when the event loop becomes idle, which differs between supported Node versions.

The worker collector uses Node's public `process.resourceUsage()` (CPU microseconds converted to milliseconds; maxRSS KiB converted to bytes). It checkpoints a private per-PID record at admission, once per second and at ordinary process exit. These records remain beside the report under the named `resources.observations` directory even on interruption. Final/partial/missing observations are distinct: an abrupt death may leave only the last checkpoint, and a worker that never reached admission has null metrics with an explicit reason. A checkpoint's high-water value covers that worker's lifetime **through its observation**, not an individual test phase. Collection adds no product instrumentation, signal handlers, heap dumps or automatic retries.

Worker CPU/RSS **exclude descendants**: Pi PTYs, helper and shared-host processes may consume substantially more RAM. Do not interpret the worker ranking as an exact ranking of complete test trees. On Linux inside the dedicated verified test scope, `aggregateBefore`/`aggregateAfter` and step snapshots record kernel `memory.peak`, `memory.events`, `pids.peak/events`, `cpu.stat`, effective affinity and limits. These are **scope-lifetime** measurements; a feature's types/Node/CLI stages share that scope. Do not subtract cumulative peaks or sum workers' independent peaks to invent per-case or aggregate memory. The outer scope receipt's `preCleanup` is sampled after the target command exits and before whole-scope teardown; `finalLifetime` is sampled after teardown. A removed cgroup can make final counters unavailable, so a pre-cleanup peak is not relabeled as a measured final cleanup peak; unavailable counters stay explicit. Non-Linux or non-dedicated scopes report aggregate collection unavailable, not zero.

To investigate a slow or RAM-intensive ordinary file, use its `rerun` argument array (retaining explicit name/skip/network filters) or select it explicitly with `--files` and `--jobs 1`, inside a **new** ordinary guard scope with a new receipt. The separate Pi-free native-build entry keeps its fixed selection: rerun that dedicated entry in a new scope rather than pretending its files are admitted by the Pi runner. Keep the same prepared Node/Pi/helper and resource limits. That bounded scope measures the focused runner **and all its descendants**, including launcher/cleanup overhead; it is not Pi-only RSS. Add an explicit name pattern for a case only when that pattern preserves its necessary setup/ordered scenario. Examine `activeTests`, the persisted test event stream and partial worker records if the run died. Regular reports have no automatic machine-dependent anomaly threshold. Detailed product CPU/allocation/GC profiling remains the separate opt-in [performance framework](performance-testing.md); it changes measurement identity and is not silently enabled for ordinary tests.

## Installed-extension profile and limits

The integration test reads the audited manifest/lock in `tests/fixtures/integration-profile/` through `integration-profile.mjs` and requires `--integration` preparation.
